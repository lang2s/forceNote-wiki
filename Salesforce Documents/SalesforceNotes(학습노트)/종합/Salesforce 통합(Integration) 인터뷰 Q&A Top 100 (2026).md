# Salesforce 통합(Integration) 인터뷰 Q&A Top 100 (2026)

> [!warning] 제3자 학습노트(면접 Q&A)를 한글로 변환한 **Tier 3** 자료입니다. 공식 소스와 대조되지 않았으니 정확도는 공식 문서로 검증하세요.

> 각 항목은 "질문 / 답변 / 팁" 구조이며, 코드는 원문 그대로 보존했습니다.

## 1. Salesforce 통합이란? 실시간 시나리오로 설명하라
**질문:** Salesforce 통합이란 무엇이며 실시간으로 어디에 썼나?
**답변:** Salesforce 통합은 API, 미들웨어, 이벤트를 사용해 실시간 또는 준실시간으로 데이터를 교환하기 위해 Salesforce를 외부 시스템과 연결하는 과정이다. 실시간 시나리오: 프로젝트에서 Salesforce를 외부 ERP와 통합했다. Opportunity가 Closed Won으로 표시되면 Salesforce가 REST API로 ERP에 주문 정보를 보냈고, ERP가 Order ID로 응답하면 이를 Salesforce에 다시 저장했다.
**팁:** 왜 통합이 필요했는지 항상 언급하라 / 데이터 흐름 방향을 설명하라 / 통합을 시작하는 트리거 지점을 추가하라.

## 2. Salesforce 통합의 종류는?
**질문:** 다양한 Salesforce 통합 유형을 나열할 수 있나?
**답변:** 크게 (1) 데이터 통합 – 시스템 간 데이터 동기화(예: 야간 배치), (2) 프로세스 통합 – 시스템 간 비즈니스 프로세스 트리거, (3) UI 통합 – 외부 UI를 Salesforce에 임베드, (4) 보안 통합 – Single Sign-On(SSO)으로 분류된다.
**팁:** 분류 + 예시를 제시하라 / 최소 3가지 유형을 기대한다.

## 3. 인바운드 vs 아웃바운드 통합의 차이는?
**질문:** 예시로 인바운드 vs 아웃바운드를 설명하라.
**답변:** 아웃바운드: Salesforce가 외부 시스템 호출을 시작(예: Salesforce가 청구 시스템에 Account 데이터 전송). 인바운드: 외부 시스템이 Salesforce 호출(예: 결제 시스템이 Salesforce의 인보이스 상태 갱신).
**팁:** 누가 호출을 시작하는지 언급하라 / 실제 비즈니스 시스템 예시를 추가하라.

## 4. Salesforce가 통합에 제공하는 API는?
**질문:** 어떤 Salesforce API를 다뤄봤나?
**답변:** REST API(경량, JSON 기반, 가장 흔함), SOAP API(엄격한 계약의 엔터프라이즈 통합), Bulk API(대용량 데이터), Streaming API(실시간 이벤트 기반 업데이트), Metadata API(메타데이터 프로그래밍 배포).
**팁:** REST + Bulk는 필수 언급 / 각 API를 왜 쓰는지 언급하라.

## 5. SOAP보다 REST API를 언제 쓰나?
**질문:** 왜 SOAP 대신 REST인가?
**답변:** 경량 통합이 필요할 때, XML보다 JSON이 선호될 때, 모바일·웹 앱이 관여될 때, 빠른 개발이 필요할 때 REST를 쓴다. 엄격한 WSDL 계약이 필요하거나 엔터프라이즈 레거시 시스템이 관여될 때 SOAP을 쓴다.
**팁:** REST = 속도 + 단순성 / SOAP = 계약 + 구조.

## 6. Salesforce 실시간 REST API 통합 흐름을 설명하라
**질문:** REST API 통합을 처음부터 끝까지 설명하라.
**답변:** (1) Salesforce 이벤트 발생(Trigger/Flow), (2) Apex가 HTTP 콜아웃 수행, (3) 외부 시스템이 요청 처리, (4) 응답이 Salesforce로 반환, (5) Salesforce가 레코드 갱신.
**팁:** 코드보다 흐름의 명확성이 더 중요 / 인증 단계를 언급하라.

## 7. Apex에서 HTTP 콜아웃을 어떻게 하나?
**질문:** Apex에서 REST 콜아웃을 어떻게 하는지 보여라.
**답변:**
```apex
Http http = new Http();
HttpRequest req = new HttpRequest();
req.setEndpoint('callout:ERP_Named_Credential/orders');
req.setMethod('POST');
req.setHeader('Content-Type', 'application/json');
req.setBody(JSON.serialize(orderData));
HttpResponse res = http.send(req);
if(res.getStatusCode() == 200){
System.debug(res.getBody());
}
```
**팁:** 항상 Named Credentials를 쓰라 / 오류 처리를 언급하라.

## 8. Named Credential이란? 왜 중요한가?
**질문:** Named Credentials란?
**답변:** Named Credentials는 엔드포인트 URL, 인증 정보, OAuth 토큰을 안전하게 저장한다. 자격 증명 하드코딩을 없애고 콜아웃을 단순화한다.
**팁:** 보안 + 유지보수성 답변 / OAuth 지원을 언급하라.

## 9. Salesforce 통합에 쓰이는 인증 방식은?
**질문:** 사용한 인증 유형을 설명하라.
**답변:** OAuth 2.0, Basic Authentication, JWT Bearer Flow, SAML(SSO용). REST 통합에는 OAuth가 가장 흔하다.
**팁:** OAuth가 기대된다 / 토큰 기반 보안을 언급하라.

## 10. Salesforce의 OAuth 2.0 흐름은?
**질문:** OAuth 흐름을 간단히 설명하라.
**답변:** OAuth 2.0은 안전한 토큰 기반 접근을 허용한다. 흐름: (1) 사용자/시스템이 인가 요청, (2) Salesforce가 액세스 토큰 발급, (3) 토큰으로 API 호출, (4) 토큰 만료 후 갱신.
**팁:** 설명을 단순하게 / 토큰 생애주기에 집중하라.

## 11. Salesforce 콜아웃 한도는?
**질문:** 통합에 어떤 한도가 적용되나?
**답변:** 트랜잭션당 최대 100개 콜아웃, 최대 타임아웃 120초, 같은 트랜잭션에서 DML 이후 콜아웃 불가.
**팁:** 콜아웃 + DML 순서를 항상 언급하라 / 한도 질문은 흔한 함정이다.

## 12. 트리거에서 콜아웃을 어떻게 처리하나?
**질문:** 트리거가 콜아웃을 할 수 있나?
**답변:** 아니다, 트리거는 직접 콜아웃을 할 수 없다. @future(callout=true), Queueable Apex, Platform Events를 쓴다.
**팁:** 전형적인 인터뷰 질문 / 비동기 옵션을 명확히 언급하라.

## 13. 콜아웃에서 @future vs Queueable 차이는?
**질문:** 어떤 비동기 옵션을 선호하나?
**답변:** Queueable Apex를 선호한다. 복잡한 객체 지원, 작업 체이닝 가능, 더 나은 모니터링 때문. @future는 단순하지만 제한적이다.
**팁:** Queueable = 현대적 접근 / 체이닝 이점을 언급하라.

## 14. Platform Event란? 어디에 쓰이나?
**질문:** 시나리오로 Platform Events를 설명하라.
**답변:** Platform Events는 이벤트 기반 아키텍처를 가능하게 한다. 시나리오: Salesforce에서 주문이 생성되면 Platform Event가 발행되고, 외부 시스템이 구독해 비동기로 처리한다.
**팁:** 느슨하게 결합된(loosely coupled) 시스템을 언급하라 / 이벤트 기반이 트렌드다.

## 15. Platform Events vs Streaming API 차이는?
**질문:** Platform Events와 Streaming API를 비교하라.
**답변:** Platform Events는 커스텀 이벤트, Streaming API는 표준/커스텀 오브젝트 변경에 동작, Platform Events가 더 확장성 있다.
**팁:** 현대 설계에서는 Platform Events가 선호된다.

## 16. 통합에서 오류를 어떻게 처리하나?
**질문:** 외부 시스템이 실패하면?
**답변:** try-catch 블록, 로깅 오브젝트, 재시도 메커니즘, Dead-letter queue 패턴으로 처리한다.
**팁:** 오류 처리는 경험을 보여준다 / 로깅 전략을 언급하라.

## 17. 실패한 통합을 어떻게 재시도하나?
**질문:** 재시도 메커니즘을 설명하라.
**답변:** 재시도 횟수가 있는 Queueable Apex, Scheduled 작업, Platform Events 리플레이로 구현한다.
**팁:** 재시도 로직 = 운영 준비성.

## 18. Bulk API란? 언제 쓰나?
**질문:** 예시로 Bulk API를 설명하라.
**답변:** Bulk API는 대용량 데이터에 쓴다. 시나리오: 레거시 CRM에서 200만 건의 Account를 Salesforce로 마이그레이션.
**팁:** 비동기 처리를 언급하라 / 데이터 볼륨 수치를 써라.

## 19. Bulk API vs REST API 차이는?
**질문:** Bulk vs REST?
**답변:** REST API → 실시간, 소량 데이터. Bulk API → 대용량 데이터, 비동기.
**팁:** 답을 짧고 명료하게.

## 20. External Object와 Salesforce Connect란?
**질문:** Salesforce Connect를 써봤나?
**답변:** Salesforce Connect는 External Object를 사용해 데이터를 Salesforce에 저장하지 않고 외부 데이터에 실시간 접근한다.
**팁:** 데이터 복제가 없음을 언급하라 / 사용 사례를 명확히 설명하라.

## 21. Salesforce 통합 패턴이란? 예시로 설명하라
**질문:** 실제 사용 사례로 통합 패턴을 설명할 수 있나?
**답변:** 통합 패턴은 Salesforce를 외부 시스템과 통합하는 표준 아키텍처 접근이다. 흔한 패턴: Remote Process Invocation, Request & Reply, Fire and Forget, Batch Data Synchronization, Event-Driven Integration. 예: Salesforce가 ERP에 주문 정보를 보내고 확인을 기다리면 → Request & Reply.
**팁:** 최소 3개 패턴을 명명하라 / 각 패턴을 비즈니스 시나리오와 연결하라.

## 22. Remote Process Invocation – Request & Reply 패턴을 설명하라
**질문:** Request & Reply 통합이란?
**답변:** Salesforce가 외부 시스템에 요청을 보내고 응답을 동기적으로 기다린다. 시나리오: Salesforce가 주문 확정 전 카드 정보 검증을 위해 결제 게이트웨이를 호출.
**팁:** 동기 동작을 언급하라 / 타임아웃 위험을 강조하라.

## 23. Fire and Forget 통합 패턴이란?
**질문:** 예시로 Fire and Forget을 설명하라.
**답변:** Salesforce가 외부 시스템에 데이터를 보내지만 응답을 기다리지 않는다. 시나리오: Lead 생성 시 Salesforce가 분석용 마케팅 도구로 데이터 전송.
**팁:** 비동기를 강조하라 / 응답에 의존하지 않음.

## 24. 동기 통합을 언제 피해야 하나?
**질문:** 동기 통합이 나쁜 생각인 경우는?
**답변:** 외부 시스템 응답이 느릴 때, 대량 트랜잭션일 때, 타임아웃 위험이나 사용자 경험 영향이 있을 때 피해야 한다.
**팁:** 사용자 경험을 언급하라 / 성능 영향이 중요.

## 25. Salesforce의 이벤트 기반 아키텍처란?
**질문:** 이벤트 기반 통합을 설명하라.
**답변:** 이벤트 기반 아키텍처는 이벤트를 사용해 시스템 간 액션을 비동기로 트리거한다. Salesforce는 Platform Events와 Change Data Capture(CDC)를 쓴다.
**팁:** 느슨한 결합을 언급하라 / 이벤트 기반 = 현대 아키텍처.

## 26. Change Data Capture(CDC)란?
**질문:** CDC란 무엇이며 어떻게 쓰나?
**답변:** CDC는 레코드가 생성·갱신·삭제·복원될 때마다 이벤트를 발행한다. 시나리오: 외부 데이터 웨어하우스가 Account 변경을 수신해 준실시간으로 데이터를 동기화.
**팁:** CDC는 오브젝트 변경에 동작 / 리플레이 기능을 언급하라.

## 27. Platform Events vs CDC 차이는?
**질문:** Platform Events vs CDC?
**답변:** Platform Events → 커스텀 비즈니스 이벤트. CDC → 오브젝트의 데이터 변경 추적. CDC는 자동 생성, Platform Events는 개발자 정의.
**팁:** 누가 이벤트를 발행하는지 명확히 / 매우 흔한 질문이다.

## 28. 미들웨어란? 왜 필요한가?
**질문:** 통합에 왜 미들웨어가 필요한가?
**답변:** 미들웨어는 Salesforce와 외부 시스템 사이의 중개자 역할을 한다. 데이터 변환, 오케스트레이션, 오류 처리, 재시도 메커니즘을 담당한다.
**팁:** 시스템 분리에 집중하라 / 확장성을 언급하라.

## 29. MuleSoft를 써봤나? 시나리오를 설명하라
**질문:** 프로젝트에서 MuleSoft 사용을 설명하라.
**답변:** 예. ERP·결제 시스템과 Salesforce를 통합하는 데 MuleSoft를 썼다. 시나리오: Salesforce가 주문 정보 전송 → MuleSoft가 데이터 변환 → ERP가 주문 처리 → MuleSoft가 응답을 다시 전송.
**팁:** 왜 MuleSoft를 택했는지 설명하라 / 변환 로직을 언급하라.

## 30. API-Led Connectivity란?
**질문:** API-Led 아키텍처를 설명하라.
**답변:** API-Led Connectivity는 통합을 System API, Process API, Experience API로 분리한다. 재사용성과 확장성을 개선한다.
**팁:** MuleSoft가 좋아하는 질문 / 계층을 명확히 설명하라.

## 31. Salesforce 통합을 어떻게 보호하나?
**질문:** 통합 엔드포인트를 어떻게 보호하나?
**답변:** OAuth 2.0, Named Credentials, IP 화이트리스트, TLS 암호화, 프로필·권한 제한으로 보장한다.
**팁:** 보안 답변은 다계층이어야 한다 / Salesforce와 외부 시스템 양쪽을 언급하라.

## 32. JWT Bearer Flow란?
**질문:** JWT 인증을 설명하라.
**답변:** JWT Bearer Flow는 사용자 상호작용 없는 서버 간 OAuth 흐름이다. Salesforce가 신뢰된 시스템과 통합할 때 쓴다.
**팁:** 사용자 로그인 없음을 언급하라 / 머신 간 통합에 쓰인다.

## 33. Salesforce 데이터를 외부 시스템에 어떻게 노출하나?
**질문:** 외부 시스템이 Salesforce 데이터에 어떻게 접근하나?
**답변:** REST API, 커스텀 Apex REST 서비스, External Services, Platform Events로 노출할 수 있다.
**팁:** Apex REST = 커스터마이징 / 사용 사례를 언급하라.

## 34. Apex REST란? 언제 쓰나?
**질문:** 예시로 Apex REST를 설명하라.
**답변:** Apex REST는 개발자가 커스텀 REST 엔드포인트를 노출하게 한다.
```apex
@RestResource(urlMapping='/orders/*')
global with sharing class OrderService {
@HttpPost
global static void createOrder() {
RestRequest req = RestContext.request;
String body = req.requestBody.toString();
}
}
```
**팁:** 커스텀 비즈니스 로직을 언급하라 / 보안은 개발자 책임.

## 35. Apex REST vs Salesforce REST API 차이는?
**질문:** Apex REST vs 표준 REST API를 비교하라.
**답변:** Salesforce REST API → 표준 오브젝트의 CRUD. Apex REST → 커스텀 로직과 검증.
**팁:** 짧고 날카롭게 / 커스텀 로직이 핵심 차이.

## 36. 통합에서 큰 페이로드를 어떻게 처리하나?
**질문:** 페이로드 크기가 거대하면?
**답변:** 데이터 청킹, Bulk API 사용, 비동기 처리, 지원되면 압축으로 처리한다.
**팁:** 거버너 한도를 언급하라 / 성능 인식을 보여라.

## 37. Composite API란?

**답변:** Composite API는 단일 요청으로 여러 REST API 호출을 허용한다. 네트워크 호출을 줄이고 성능을 개선한다.
**팁:** API 호출 최적화를 언급하라 / 모바일 앱에 좋다.

## 38. API 버전을 어떻게 관리하나?
**질문:** API 버전이 바뀌면 어떻게 되나?
**답변:** 엔드포인트의 명시적 버전 지정, 하위 호환성, 업그레이드 전 테스트로 처리한다.
**팁:** 버전 관리는 성숙도를 보여준다 / 회귀 테스트를 언급하라.

## 39. Salesforce에서 통합을 어떻게 모니터링하나?
**질문:** 통합 실패를 어떻게 추적하나?
**답변:** 디버그 로그, 커스텀 로깅 오브젝트, Event Monitoring, 미들웨어 대시보드로 모니터링한다.
**팁:** 로깅 전략이 중요 / 가능하면 알림을 언급하라.

## 40. 확장성을 위한 통합 설계는?
**질문:** 통합 확장성을 어떻게 보장하나?
**답변:** 비동기 처리, 이벤트 기반 아키텍처, 벌크 작업, 미들웨어 사용으로 보장한다.
**팁:** 확장성 = 비동기 + 분리 / 항상 볼륨 처리를 언급하라.

## 41. 통합에서 멱등성(idempotency)이란? 왜 중요한가?
**질문:** 실제 운영 예시로 멱등성을 설명하라.
**답변:** 멱등성은 동일한 요청이 여러 번 와도 같은 결과를 내고 중복 레코드를 만들지 않도록 한다. 시나리오: 외부 시스템이 실패한 요청을 재시도해 같은 Order 페이로드를 다시 보내면, 멱등성 키로 Salesforce가 Order를 하나만 생성하도록 보장한다.
**팁:** 시니어 수준 통합 지식을 알리는 질문 / 항상 재시도 시나리오를 언급하라.

## 42. Salesforce에서 멱등성을 어떻게 구현하나?
**질문:** 중복 요청을 기술적으로 어떻게 처리하나?
**답변:** External ID, 고유 키, 커스텀 멱등성 테이블로 구현한다. 예: External_Order_Id__c를 고유 키로 저장하고 insert 대신 upsert.
**팁:** upsert를 언급하라 / 고유 제약이 핵심.

## 43. upsert란? 통합에서 어떻게 쓰나?
**질문:** 시나리오로 upsert를 설명하라.
**답변:** upsert는 External ID를 기준으로 레코드가 없으면 insert, 있으면 update한다. 시나리오: ERP에서 온 고객 데이터가 기존 Account를 갱신하거나 새로 생성.
**팁:** External ID 설명은 필수 / 데이터 동기화 사용 사례를 언급하라.

## 44. 통합에서 중복 레코드를 어떻게 방지하나?
**질문:** 외부 시스템의 중복을 어떻게 피하나?
**답변:** External ID, Matching Rule, Duplicate Rule, 멱등성 키로 방지한다.
**팁:** 다계층 방어 접근을 보여라 / External ID가 가장 흔한 답.

## 45. 통합에서 부분 실패를 어떻게 처리하나?
**질문:** 일부는 성공, 일부는 실패하면?
**답변:** 트랜잭션 수준 오류 처리, 실패 레코드 로깅, 실패한 레코드만 재시도로 처리한다.
**팁:** 부분 실패 처리는 운영 경험을 보여준다 / 벌크 작업을 언급하라.

## 46. 겪은 실제 운영 통합 실패를 설명하라
**질문:** 통합 실패와 해결을 설명하라.
**답변:** ERP 시스템이 다운되어 Salesforce 콜아웃이 실패했다. 해결: 비동기 처리로 전환, 재시도 메커니즘 구현, 리플레이용 실패 로깅.
**팁:** 인터뷰어는 실제 실패 스토리를 좋아한다 / 항상 수정 + 예방을 설명하라.

## 47. Salesforce 통합에서 타임아웃 이슈를 어떻게 처리하나?
**질문:** 외부 시스템이 느리면?
**답변:** 비동기 처리, Fire-and-forget 패턴, Circuit Breaker 패턴으로 처리한다.
**팁:** 사용자 경험을 언급하라 / 비동기가 가장 안전한 접근.

## 48. Circuit Breaker 패턴이란?
**질문:** 통합에서 Circuit Breaker를 설명하라.
**답변:** Circuit Breaker는 시스템이 반복적으로 실패할 때 통합 호출을 멈춰 연쇄 실패를 방지한다.
**팁:** 고급 아키텍처 지식을 보여준다 / 모니터링 임계값을 언급하라.

## 49. 대용량 데이터 통합을 어떻게 처리하나?
**질문:** 수백만 건을 동기화해야 하면?
**답변:** Bulk API, Batch Apex, 미들웨어 오케스트레이션, 적용 가능한 경우 CDC를 쓴다.
**팁:** 수치가 중요: "수백만"이라 말하라 / 비동기 도구를 언급하라.

## 50. 통합에 가장 영향을 주는 거버너 한도는?
**질문:** 통합에 중요한 한도는?
**답변:** 콜아웃 한도(트랜잭션당 100), Heap size, CPU 시간, DML 한도.
**팁:** 콜아웃 + Heap size가 핵심 / 한도 인식 설계를 언급하라.

## 51. 벌크화를 위한 통합 설계는?
**질문:** 통합을 벌크 안전하게 어떻게 만드나?
**답변:** 루프 안 콜아웃을 피하고, 컬렉션을 쓰며, 배치 처리한다.
**팁:** Apex 베스트 프랙티스와 겹친다 / 거버너 한도를 언급하라.

## 52. Platform Events나 CDC의 Replay ID란?

**팁:** Replay ID = 신뢰성 / 실시간 동기화에 중요.

## 53. 통합에서 데이터 변환을 어떻게 처리하나?
**질문:** 데이터를 어디서 변환하나?
**답변:** 미들웨어(선호), Apex(단순할 때), 매핑 로직으로 처리한다.
**팁:** 미들웨어 변환이 베스트 프랙티스 / Salesforce에서 무거운 로직을 피하라.

## 54. 스키마 불일치란? 어떻게 처리하나?
**질문:** 외부 스키마가 바뀌면?
**답변:** 버전 API, 계약 검증, 하위 호환성으로 처리한다.
**팁:** 계약 기반 통합을 언급하라 / 안정성 마인드를 보여준다.

## 55. Salesforce 통합을 어떻게 테스트하나?
**질문:** 콜아웃을 어떻게 테스트하나?

**팁:** HTTPCalloutMock은 필수 / 테스트는 자주 질문된다.

## 56. HTTP 콜아웃용 테스트 클래스를 작성하라
**질문:** 모의(mock) 콜아웃 예시를 보여라.
**답변:**
```apex
@isTest
class OrderServiceTest {
class MockResponse implements HttpCalloutMock {
public HTTPResponse respond(HTTPRequest req) {
HttpResponse res = new HttpResponse();
res.setStatusCode(200);
res.setBody('{"status":"success"}');
return res;
}
}
@isTest static void testCallout() {
Test.setMock(HttpCalloutMock.class, new MockResponse());
Test.startTest();
// call method
Test.stopTest();
}
}
```
**팁:** Test.startTest()를 반드시 포함 / 모의 응답이 필수.

## 57. API 속도 제한(rate limit)을 어떻게 처리하나?
**질문:** API 한도를 초과하면?
**답변:** 요청 스로틀링, 큐 기반 처리, 사용량 모니터링으로 처리한다.
**팁:** 속도 제한은 양쪽 모두에 영향 / 미들웨어 도움을 언급하라.

## 58. 통합에서 백프레셔(back-pressure)란?
**질문:** 백프레셔를 설명하라.
**답변:** 백프레셔는 시스템이 과부하될 때 실패를 막기 위해 데이터 흐름을 제어한다.
**팁:** 고급 아키텍처 주제 / 드물지만 인상적인 답변.

## 59. 시스템 간 데이터 일관성을 어떻게 보장하나?
**질문:** 일관성을 어떻게 유지하나?
**답변:** External ID, 최종 일관성(eventual consistency), 조정(reconciliation) 작업으로 유지한다.
**팁:** 최종 일관성을 언급하라 / 항상 진정한 실시간인 시스템은 없다.

## 60. 최종 일관성(eventual consistency)이란?
**질문:** 최종 일관성을 설명하라.
**답변:** 최종 일관성은 시스템이 즉시 동기화되지 않더라도 시간이 지나면 수렴한다는 의미다.
**팁:** 중요한 분산 시스템 개념 / 인터뷰어가 좋아하는 용어.

## 61. Salesforce에서 인바운드 통합을 어떻게 보호하나?
**질문:** 신뢰된 시스템만 Salesforce를 호출하도록 어떻게 보장하나?
**답변:** OAuth 2.0, JWT Bearer Flow, Named Credentials, IP 화이트리스트, 프로필·Permission Set 제한으로 보호한다.
**팁:** OAuth를 먼저 언급하라 / 다계층 보안을 기대한다.

## 62. Salesforce의 아웃바운드 통합을 어떻게 보호하나?
**질문:** Salesforce가 외부 시스템을 어떻게 안전하게 호출하나?
**답변:** Named Credentials, OAuth 토큰, TLS 암호화, 인증서 기반 인증으로 처리한다.
**팁:** Named Credentials는 필수 답 / 인증서는 고급 지식을 보여준다.

## 63. OAuth와 JWT Bearer Flow 차이는?
**질문:** OAuth vs JWT?
**답변:** OAuth는 사용자 상호작용 필요, JWT Bearer Flow는 서버 간이며 사용자 없음, JWT는 신뢰된 시스템에 더 빠르고 안전하다.
**팁:** JWT = 사용자 로그인 없음 / 백엔드 통합에 JWT를 쓰라.

## 64. Single Sign-On(SSO)이란? 통합과 어떤 관계인가?
**질문:** Salesforce 맥락에서 SSO를 설명하라.
**답변:** SSO는 한 번 로그인으로 여러 시스템에 접근하게 한다. Salesforce에서는 SAML, OAuth, OpenID Connect로 Identity Provider와 통합한다.
**팁:** SSO = 아이덴티티 통합 / 프로토콜을 명확히 언급하라.

## 65. Salesforce에서 SAML과 OAuth 차이는?
**질문:** SAML vs OAuth?
**답변:** SAML은 XML 기반이며 엔터프라이즈 SSO에, OAuth는 토큰 기반이며 API 접근에 쓰인다.
**팁:** SAML = 인증(authentication) / OAuth = 인가(authorization).

## 66. Identity Provider(IdP)와 Service Provider(SP)란?
**질문:** IdP와 SP 역할을 설명하라.
**답변:** Identity Provider는 사용자를 인증하고, Service Provider는 접근을 부여한다. Salesforce는 IdP와 SP 둘 다 될 수 있다.
**팁:** 아이덴티티 기본을 확인하는 질문 / 역할을 명확히 하라.

## 67. Salesforce를 외부 ID 제공자와 어떻게 통합하나?
**질문:** 외부 SSO를 어떻게 설정하나?
**답변:** SAML 설정, Auth Provider, Connected App으로 통합한다.
**팁:** Connected App을 언급하라 / 아이덴티티 질문은 시니어 역할에 흔하다.

## 68. Connected App이란?
**질문:** Connected App 사용을 설명하라.
**답변:** Connected App은 외부 앱이 OAuth와 API로 Salesforce에 연결하는 방식을 정의한다. Scope, 토큰 정책, 접근 권한을 제어한다.
**팁:** Scope가 중요 / 토큰 정책은 성숙도를 보여준다.

## 69. Salesforce에서 API 접근을 어떻게 제어하나?
**질문:** API 사용을 어떻게 제한하나?
**답변:** 프로필·Permission Set, OAuth scope, Connected App 정책으로 제어한다.
**팁:** 최소 권한 원칙 / 보안 우선 마인드.

## 70. OAuth scope란? 왜 중요한가?
**질문:** OAuth scope를 설명하라.
**답변:** OAuth scope는 애플리케이션이 Salesforce에서 무엇에 접근할 수 있는지 정의한다. 예: 읽기 전용 접근, 전체 접근, refresh token 접근.
**팁:** Scope 오용은 보안 위험 / 최소 권한을 언급하라.

## 71. 통합된 시스템의 접근을 어떻게 취소하나?
**질문:** 시스템 접근을 어떻게 비활성화하나?
**답변:** OAuth 토큰 취소, Connected App 비활성화, Permission Set 제거로 취소한다.
**팁:** 취소는 종종 잊힌다 / 좋은 보안 위생 질문.

## 72. 인증서 기반 인증이란?
**질문:** 통합에서 인증서 사용을 설명하라.
**답변:** 인증서 기반 인증은 비밀번호 대신 공개/비공개 키를 쓴다. JWT Bearer Flow, Mutual TLS에 쓰인다.
**팁:** 인증서 = 강력한 보안 / 로테이션을 언급하라.

## 73. 통합에서 시크릿 로테이션을 어떻게 처리하나?
**질문:** 자격 증명을 어떻게 로테이션하나?
**답변:** Named Credentials 갱신, 인증서 로테이션, 토큰 만료 정책으로 처리한다.
**팁:** 보안 + 운영 답변 / 로테이션은 감사에 중요.

## 74. Mutual TLS(mTLS)란?
**질문:** mTLS를 설명하라.
**답변:** Mutual TLS는 인증서를 사용해 클라이언트와 서버를 모두 인증한다.
**팁:** 고급 보안 주제 / 양방향 신뢰를 언급하라.

## 75. 흔한 통합 보안 취약점은?
**질문:** 어떤 보안 이슈를 봤나?
**답변:** 하드코딩된 자격 증명, 과도한 OAuth scope, IP 제한 누락, 로깅 부재.
**팁:** 피해야 할 실수를 언급하라 / 실무 인식을 보여준다.

## 76. Salesforce 통합을 어떻게 감사(audit)하나?
**질문:** 통합 활동을 어떻게 감사하나?
**답변:** Event Monitoring, Setup Audit Trail, API 사용 리포트로 한다.
**팁:** 컴플라이언스 질문 / 로그와 리포트를 언급하라.

## 77. Salesforce의 Event Monitoring이란?
**질문:** Event Monitoring을 설명하라.
**답변:** Event Monitoring은 보안·성능 분석을 위해 사용자와 API 활동을 추적한다.
**팁:** 감사에 유용 / API 이벤트를 언급하라.

## 78. 통합에서 겪은 실제 보안 이슈를 설명하라
**질문:** 보안 사건을 설명하라.
**답변:** 외부 시스템이 과도한 OAuth scope를 사용했다. 해결: scope 축소, 토큰 재생성, Connected App 정책 갱신.
**팁:** 정직한 사건 설명 / 항상 개선 조치를 언급하라.

## 79. 흔한 통합 인터뷰 함정은?
**질문:** 인터뷰어가 묻는 함정 질문은?
**답변:** 트리거 안 콜아웃, 콜아웃 전 DML, 비동기 처리 누락, 오류 로깅 부재.
**팁:** 자신 있게 언급하라 / 인터뷰 인식을 보여준다.

## 80. 인터뷰에서 통합 아키텍처를 어떻게 설명하나?
**질문:** 아키텍처를 어떻게 명확히 설명하나?
**답변:** 관련 시스템, 데이터 흐름, 동기 유형, 오류 처리, 보안을 설명한다.
**팁:** 답변을 구조화하라 / 다이어그램이 머릿속에 도움.

## 81. 통합을 처음부터 어떻게 설계하나?
**질문:** 새 Salesforce 통합을 어떻게 설계하겠는가?
**답변:** 구조화된 접근: (1) 비즈니스 요구사항 이해, (2) 시스템과 데이터 흐름 식별, (3) 통합 패턴 선택, (4) 동기 유형 결정(실시간 vs 비동기), (5) 오류 처리와 보안 정의, (6) 모니터링과 확장성 계획.
**팁:** 구조화된 사고를 보여라 / 도구로 바로 뛰어들지 마라.

## 82. 실시간과 배치 통합을 어떻게 결정하나?
**질문:** 언제 실시간 vs 배치를 고르나?
**답변:** 즉각적 응답이 필요할 때 실시간을, 대용량 데이터이고 즉각적 비즈니스 의존성이 없을 때 배치를 고른다.
**팁:** 사용자 경험을 언급하라 / 데이터 볼륨이 중요.

## 83. 올바른 통합 패턴을 어떻게 선택하나?
**질문:** 통합 패턴을 어떻게 선택하나?
**답변:** 데이터 볼륨, 지연 허용도, 실패 영향, 결합 요구사항을 고려한다.
**팁:** 패턴 선택 = 아키텍처 성숙도 / 트레이드오프를 언급하라.

## 84. Salesforce를 레거시 시스템과 어떻게 통합하나?
**질문:** 외부 시스템이 레거시면?
**답변:** 추상화를 위한 미들웨어, 배치나 파일 기반 통합, 의존성을 줄이는 느슨한 결합을 쓴다.
**팁:** 레거시 시스템은 느리고 경직됨 / 미들웨어가 친구다.

## 85. SOAP에서 REST로 통합을 어떻게 마이그레이션하나?
**질문:** SOAP 통합을 마이그레이션해봤나?
**답변:** 접근: 기존 WSDL 분석, REST 대응 식별, 두 시스템 병행 실행, 점진적 폐기.
**팁:** 병행 실행이 위험을 줄인다 / 마이그레이션 계획이 핵심.

## 86. 멀티-org Salesforce 설정의 통합을 어떻게 설계하나?
**질문:** 여러 Salesforce org가 있으면?
**답변:** Hub-and-spoke 모델, 미들웨어 중심 통합, 중앙화된 아이덴티티 관리로 설계한다.
**팁:** 멀티-org는 복잡 / 거버넌스가 중요.

## 87. 통합에서 버전 업그레이드를 어떻게 처리하나?
**질문:** Salesforce가 업그레이드되면?
**답변:** API 버전 고정(pinning), 회귀 테스트, 샌드박스 검증으로 처리한다.
**팁:** 절대 맹목적으로 자동 업그레이드하지 마라 / 테스트가 장애를 막는다.

## 88. 무손실(zero data loss)을 어떻게 설계하나?
**질문:** 데이터 손실이 없도록 어떻게 보장하나?
**답변:** 신뢰성 있는 큐, 재시도 메커니즘, 이벤트 리플레이, 조정 작업을 쓴다.
**팁:** 무손실은 이상적 목표 / 복구를 위해 설계하라.

## 89. 시스템 간 데이터를 어떻게 조정(reconcile)하나?
**질문:** 데이터 정확성을 어떻게 검증하나?
**답변:** 스케줄 비교 작업, 체크섬, 리포트·대시보드를 쓴다.
**팁:** 조정은 종종 잊힌다 / 금융 시스템에 필수.

## 90. 스키마 진화(schema evolution)를 어떻게 처리하나?
**질문:** 데이터 모델이 바뀌면?
**답변:** 하위 호환 API, 버전 계약, 폐기(deprecation) 정책으로 처리한다.
**팁:** 스키마 변경은 불가피 / 소통이 핵심.

## 91. 통합 설계에 존재하는 트레이드오프는?
**질문:** 어떤 타협을 하나?
**답변:** 일관성 vs 가용성, 실시간 vs 성능, 복잡성 vs 유연성.
**팁:** 시스템 설계 질문 / 완벽한 해법은 없다.

## 92. 최종 일관성을 비즈니스 사용자에게 어떻게 설명하나?
**질문:** 기술적 지연을 어떻게 설명하나?
**답변:** 시스템이 서로 다른 속도로 갱신되지만 시간이 지나면 올바르게 동기화된다고 설명한다.
**팁:** 기술을 비즈니스 언어로 번역하라 / 소통이 중요.

## 93. 통합을 엔드투엔드로 어떻게 테스트하나?
**질문:** 통합을 어떻게 검증하나?
**답변:** 샌드박스 간 테스트, 모의 서비스, 운영 스모크 테스트를 쓴다.
**팁:** E2E 테스트가 중요 / 롤백 계획을 포함하라.

## 94. 통합에서 롤백을 어떻게 처리하나?
**질문:** 뭔가 잘못되면?
**답변:** 보상 트랜잭션(compensation transaction), 데이터 버저닝, 수동 오버라이드 절차로 처리한다.
**팁:** 롤백 ≠ 삭제 / 보상 로직이 핵심.

## 95. 통합에서 어떤 KPI를 추적하나?
**질문:** 성공을 어떻게 측정하나?
**답변:** 성공률, 지연시간(latency), 실패율, 재시도 횟수.
**팁:** 지표는 운영 성숙도를 보여준다 / 대시보드를 언급하라.

## 96. 통합을 어떻게 문서화하나?
**질문:** 문서를 어떻게 유지하나?
**답변:** API 명세, 데이터 매핑, 시퀀스 다이어그램으로 한다.
**팁:** 문서화는 의존성을 줄인다 / 인터뷰어가 좋아하는 답변.

## 97. Salesforce 통합의 안티패턴은?
**질문:** 무엇을 피해야 하나?
**답변:** 트리거 안 콜아웃, 자격 증명 하드코딩, 동기 벌크 처리, 오류 처리 부재.
**팁:** 안티패턴은 쉬운 탈락 포인트 / 자신 있게 언급하라.

## 98. 통합을 어떻게 미래 대비(future-proof)하나?
**질문:** 미래를 위해 어떻게 설계하나?
**답변:** 느슨한 결합, 이벤트 기반 아키텍처, 버전 API를 쓴다.
**팁:** 미래 대비는 시니어성을 보여준다 / 강한 의존성을 피하라.

## 99. 복잡한 통합을 인터뷰어에게 어떻게 설명하나?
**질문:** 복잡성을 어떻게 명확히 설명하나?
**답변:** 단순한 흐름 설명, 비즈니스 우선 언어, 명확한 실패 처리를 쓴다.
**팁:** 명확함이 복잡함을 이긴다 / 자신감이 중요.

## 100. 왜 우리가 당신에게 중요한 통합을 맡겨야 하나?
**질문:** 통합 중심 역할에 왜 적합한가?
**답변:** 안전하고, 확장 가능하며, 관측 가능하고, 회복탄력적인 통합을 설계하기 때문이다. 그리고 성공 경로뿐 아니라 실패 처리에 집중한다.
**팁:** 마무리 질문 / 신뢰성과 주인의식으로 연결하라.
