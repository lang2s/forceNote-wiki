# Salesforce 인터뷰 준비 2026 — 시나리오 기반 질문 Top 100+ (실무·경험 기반)

> [!warning] 제3자 학습노트(면접 Q&A)를 한글로 변환한 **Tier 3** 자료입니다. 공식 소스와 대조되지 않았으니 정확도는 공식 문서로 검증하세요.

> 각 항목은 "그들이 물어본 것 / 내가 인터뷰에서 답한 것 / 팁" 구조이며, 코드는 원문 그대로 보존했습니다.

## 1. 운영 환경에서 검증 규칙(Validation Rule) 실패 처리
**질문:**

배포한 검증 규칙이 운영에서 사용자를 막고 있다. 어떻게 하겠는가?
**답변:**

먼저 오류 메시지와 규칙 로직을 확인해 영향받는 사용자를 파악한다. 비즈니스를 막을 만큼 치명적이면 검증 규칙을 일시적으로 비활성화한다. 그다음 Custom Permission이나 Custom Setting으로 우회 메커니즘을 만들어 관리자나 특정 프로필이 막히지 않게 한다. 이후 규칙을 수정하고 적절한 테스트와 함께 재배포한다.
**팁:**

Custom Permission을 이용한 우회(2026 베스트 프랙티스)를 언급하라 / "규칙을 삭제한다"고 말하지 마라 / 운영 안전성 사고를 보여라.

## 2. Profile vs Permission Set – 실제 프로젝트 결정
**질문:**

Profile 대신 Permission Set은 언제 사용하나?
**답변:**

Profile은 기본 접근 권한을 정의하고, Permission Set은 프로필을 복제하지 않고도 추가 권한을 부여할 때 사용한다. 실제 프로젝트에서는 프로필을 최소화하고 "Report Viewer", "Integration User" 같은 역할 기반 접근에 Permission Set을 쓴다.
**팁:**

"프로필 하나, Permission Set 다수"라고 말하라 / 확장성 사고를 기대한다.

## 3. 공유 규칙(Sharing Rule)을 적용했는데도 레코드 접근 불가
**질문:**

공유 규칙을 적용해도 사용자가 레코드를 못 본다. 왜인가?
**답변:**

먼저 OWD를 확인한다. 그다음 공유 규칙 조건이 레코드와 일치하는지 검증한다. 역할 계층, 수동 공유, 오브젝트 Read 권한도 확인한다.
**팁:**

항상 "OWD → Sharing Rule → Role Hierarchy → Object Permission" 순서로 말하라 / 전형적인 실무 관리자 이슈다.

## 4. Flow vs Validation Rule – 무엇을 쓸까?
**질문:**

Validation Rule 대신 Flow는 언제 쓰나?
**답변:**

Validation Rule은 단순 조건에 적합하다. Flow는 여러 오브젝트, 복잡한 조건, 동적 메시지가 필요할 때 더 낫다.
**팁:**

"Flow가 Validation Rule을 대체한다"고 말하지 마라 / 정의가 아닌 의사결정을 설명하라.

## 5. Data Loader가 "INSUFFICIENT_ACCESS"로 실패
**질문:**

Data Loader 작업이 접근 오류로 실패했다. 어떻게 해결하나?
**답변:**

오브젝트 권한, 필드 수준 보안(FLS), 레코드 소유권을 확인한다. 필요하면 임시 접근 권한이 있는 Permission Set을 할당하고 작업을 재시도한다.
**팁:**

필드 수준 보안을 언급하라 / 실제 마이그레이션 경험을 보여준다.

## 6. 운영 환경 NullPointerException
**질문:**

Apex 코드가 운영에서 NullPointerException을 던진다. 어떻게 처리하나?
**답변:**

변수 접근 전에 null 체크를 추가하고 방어적 프로그래밍을 한다. 디버그 로그를 검토해 어떤 변수가 null인지 파악하고 적절한 오류 처리를 추가한다.
**팁:**

항상 "방어적 프로그래밍(defensive programming)"을 언급하라 / 운영 안전 마인드를 좋아한다.

## 7. 루프 안의 SOQL 쿼리 – 어떻게 할까?
**질문:**

기존 코드에서 루프 안에 SOQL 쿼리를 발견했다.
**답변:**

쿼리를 루프 밖으로 옮기고 Map으로 결과를 저장해 코드를 벌크화한다. 거버너 한도 예외를 피한다.
```apex
Map<Id, Account> accMap = new Map<Id, Account>(
[SELECT Id, Name FROM Account WHERE Id IN :accIds]
);
```
**팁:**

항상 거버너 한도를 언급하라 / 가능하면 짧은 코드 예제를 제시하라.

## 8. List vs Set vs Map – 실제 사용
**질문:**

실제 프로젝트에서 Map을 어디에 썼나?
**답변:**

중복 쿼리를 피하고 Id를 키로 레코드를 빠르게 가져오기 위해 Map을 썼다. 특히 트리거와 배치 로직에서.
**팁:**

교과서적 답변을 하지 마라 / 트리거나 배치 작업을 언급하라.

## 9. Custom Exception – 언제, 왜?
**질문:**

Custom Exception을 써본 적 있나?
**답변:**

예. Validation Rule이나 Flow로 처리할 수 없는 비즈니스 검증이 있을 때 사용했다. Custom Exception은 의미 있는 오류 메시지를 주고 실행을 중단시킨다.
**팁:**

"비즈니스 수준 검증"이라고 말하라 / 깔끔한 코딩 관행을 보여준다.

## 10. Apex에서 대용량 데이터 처리
**질문:**

Apex에서 수백만 건의 레코드를 어떻게 처리하나?
**답변:**

적절한 scope size로 Batch Apex를 쓰고 동기 처리를 피한다. 쿼리가 선택적(selective)이 되도록 보장한다.
**팁:**

Batch Apex + Async를 언급하라 / "트리거를 쓴다"고 말하지 마라.

## 11. 트리거가 재귀적 업데이트를 유발
**질문:**

트리거가 계속 반복 실행된다. 어떻게 멈추나?
**답변:**

헬퍼 클래스에 static Boolean 변수를 써서 재귀를 방지한다.
```apex
public class TriggerHandler {
public static Boolean isExecuting = false;
}
```
**팁:**

static 변수 답변이 기대된다 / 핸들러 패턴을 언급하라.

## 12. Before vs After 트리거 – 비즈니스 사례
**질문:**

after 대신 before 트리거는 언제 쓰나?
**답변:**

Before 트리거는 필드 값을 갱신할 때, After 트리거는 관련 레코드를 생성·갱신해야 할 때 쓴다.
**팁:**

간결하고 자신 있는 설명이 이긴다.

## 13. 오브젝트당 트리거 하나 – 왜?
**질문:**

왜 오브젝트당 트리거 하나인가?
**답변:**

유지보수성을 높이고 실행 순서 문제를 피한다. 로직은 핸들러 클래스로 제어한다.
**팁:**

"확장성"과 "제어"를 언급하라.

## 14. 대량 업로드에서 트리거 실패
**질문:**

단건은 동작하는데 대량 업로드에서 트리거가 실패한다.
**답변:**

코드가 벌크화되지 않았다. 단건 로직을 컬렉션 기반 처리로 교체한다.
**팁:**

대량 업로드 실패는 실제 운영 사례다 / 인터뷰어가 좋아한다.

## 15. 트리거 vs Flow – 무엇을 고를까?
**질문:**

왜 항상 트리거 대신 Flow를 쓰지 않나?
**답변:**

Flow는 단순 로직에 선호되지만, 복잡한 로직·성능·고급 제어가 필요하면 트리거가 필요하다.
**팁:**

극단적인 진술 없이 균형 잡힌 답변.

## 16. LWC가 갱신된 데이터를 반영하지 않음
**질문:**

레코드 업데이트 후 LWC UI가 새로고침되지 않는다.
**답변:**

구현에 따라 refreshApex() 또는 Lightning Data Service를 사용한다.
**팁:**

LDS를 언급하라 / 최신 LWC 지식을 보여준다.

## 17. LWC에서 Apex 호출
**질문:**

LWC에서 Apex를 어떻게 호출하나?
**답변:**

읽기 전용에는 @wire를, 저장·갱신 같은 액션에는 명령형(imperative) 호출을 쓴다.
**팁:**

문법만 설명하지 마라 / 사용 결정을 설명하라.

## 18. LWC에서 오류 처리
**질문:**

서버 오류를 UI에 어떻게 표시하나?
**답변:**

catch 블록에서 오류를 잡아 ShowToastEvent로 토스트 메시지를 표시한다.
**팁:**

사용자 경험을 언급하라 / UI 성숙도를 본다.

## 19. LWC 성능 이슈
**질문:**

LWC가 느리다. 어떻게 하겠는가?
**답변:**

서버 호출을 줄이고, cacheable Apex 메서드를 쓰며, 재렌더링을 최적화한다.
**팁:**

"cacheable=true"라고 말하라 / 2026에는 성능 사고가 중요하다.

## 20. LWC 보안
**질문:**

LWC에서 보안을 어떻게 보장하나?
**답변:**

Apex에서 CRUD와 FLS 체크를 강제하고 민감한 데이터를 클라이언트에 노출하지 않는다.
**팁:**

보안 인식 = 시니어 마인드.

## 21. "Non-Selective Query"로 SOQL 실패
**질문:**

비선택적 필터 때문에 운영에서 SOQL이 실패한다. 어떻게 하겠는가?
**답변:**

WHERE 절을 분석해 Id, Lookup 필드, External Id 같은 인덱스 필드를 쓰도록 한다. 필요하면 Salesforce Support에 커스텀 인덱스를 요청한다. Batch Apex로 쿼리를 작은 청크로 나눌 수도 있다.
**팁:**

항상 "인덱스 필드"라고 말하라 / Salesforce Support 인덱스 요청 언급 / 대용량 데이터 경험을 보여준다.

## 22. 트리거에서 SOQL 101 오류
**질문:**

트리거가 "Too many SOQL queries: 101"을 던진다. 어떻게 해결하나?
**답변:**

루프 안에서 SOQL이 실행되어 발생한다. 한 번만 쿼리하고 Map으로 데이터에 효율적으로 접근하도록 리팩터링한다.
**팁:**

"벌크화(bulkification)"를 명확히 말하라 / 가장 흔한 운영 버그 중 하나다.

## 23. SOQL vs SOSL – 실제 사용 사례
**질문:**

SOQL 대신 SOSL은 언제 쓰나?
**답변:**

글로벌 검색 기능처럼 여러 오브젝트·필드에서 텍스트를 검색할 때 SOSL을 쓴다. 단일 오브젝트의 구조화된 데이터 조회에는 SOQL이 낫다.
**팁:**

정의가 아닌 비즈니스 사용 사례를 제시하라 / "여러 오브젝트"를 명시하라.

## 24. 대용량 조직에서 쿼리 최적화
**질문:**

큰 조직에서 SOQL 쿼리를 어떻게 최적화하나?
**답변:**

선택적 필터를 쓰고, SELECT *를 피하며, 반환 필드를 제한하고, 인덱스 컬럼을 쓰며, 가능한 곳에 LIMIT을 적용한다.
**팁:**

시니어 인터뷰에서 최적화 마인드가 중요 / "거버너 한도를 늘린다"고 말하지 마라.

## 25. 쿼리에서 삭제된 레코드 처리
**질문:**

삭제된 레코드를 어떻게 쿼리하나?
**답변:**

ALL ROWS 키워드를 쓰고 IsDeleted = true로 필터링한다.
```apex
SELECT Id, Name FROM Account WHERE IsDeleted = true ALL ROWS
```
**팁:**

휴지통(recycle bin) 시나리오를 언급하라 / 관리자+개발자 지식 중첩을 보여준다.

## 26. 왜 비동기 Apex가 필요했나
**질문:**

프로젝트에서 왜 비동기 Apex를 썼나?
**답변:**

동기 Apex는 엄격한 거버너 한도가 있다. 비동기 Apex는 더 높은 한도와 통합·데이터 처리 같은 장시간 작업에 더 나은 성능을 제공한다.
**팁:**

정의가 아닌 한도를 이야기하라 / 추론을 원한다.

## 27. @future vs Queueable – 실제 결정
**질문:**

왜 @future 대신 Queueable을 선택했나?
**답변:**

Queueable은 체이닝, 복잡한 데이터 타입, @future보다 나은 모니터링을 지원한다.
**팁:**

"체이닝(chaining)"을 자신 있게 말하라 / 2026에는 Queueable이 선호된다.

## 28. 밤에 비동기 작업 실패 – 어떻게 할까?
**질문:**

새벽 3시에 배치 작업이 실패했다. 어떻게 디버그하나?
**답변:**

AsyncApexJob 로그를 확인하고, 디버그 로그를 검토하며, execute 메서드 안에 오류 처리를 추가한다. 이해관계자에게 알리고 필요시 작업을 재실행한다.
**팁:**

주인의식과 운영 책임을 보여라 / 기술뿐 아니라 운영적 답변.

## 29. Future 메서드가 실행되지 않음
**질문:**

future 메서드가 실행되지 않는다. 왜인가?
**답변:**

다른 future 메서드에서 호출, 비동기 한도 초과, @future 어노테이션 누락 등이 원인일 수 있다.
**팁:**

비동기 제약을 언급하라 / 깊은 플랫폼 이해를 보여준다.

## 30. Queueable 체이닝 – 사용 사례
**질문:**

Queueable 체이닝을 써본 적 있나?
**답변:**

예. 데이터 정리 후 통합 콜아웃처럼 단계별로 레코드를 처리할 때 썼다.
```apex
System.enqueueJob(new FirstJob());
```
**팁:**

단계 기반 비즈니스 흐름을 제시하라 / 실제 프로젝트 경험을 보여준다.

## 31. Batch Apex는 언제 썼나?
**질문:**

Batch Apex를 사용한 실제 시나리오를 설명하라.
**답변:**

데이터 마이그레이션 중 한도에 걸리지 않고 수백만 건의 레거시 레코드를 갱신하기 위해 Batch Apex를 썼다.
**팁:**

"수백만"을 자신 있게 언급하라 / Batch = 항상 대용량 데이터.

## 32. Batch scope size 결정
**질문:**

배치 scope size를 어떻게 정하나?
**답변:**

로직 복잡도와 DML 작업 수에 따라 정한다. 보통 200~500 사이.
**팁:**

고정 답은 없다, 추론을 보여라 / "기본값만"이라고 말하지 마라.

## 33. Batch 작업 vs Scheduled 작업
**질문:**

배치와 스케줄 Apex의 차이는?
**답변:**

Scheduled Apex는 특정 시간에 실행되고, Batch Apex는 대용량 데이터를 청크로 처리한다. 둘을 함께 쓰는 경우가 많다.
**팁:**

"Scheduled Batch"라고 말하라 / 실무 패턴.

## 34. Batch execute에서 오류 처리
**질문:**

배치에서 부분 실패를 어떻게 처리하나?
**답변:**

try-catch 블록을 쓰고 전체 배치를 멈추는 대신 실패한 레코드를 재시도용으로 로깅한다.
**팁:**

오류 격리가 핵심 / 신뢰성 마인드를 보여준다.

## 35. Batch vs Queueable – 어느 게 빠른가?
**질문:**

Batch와 Queueable 중 어느 게 빠른가?
**답변:**

중소 데이터셋에는 Queueable이 빠르다. 매우 큰 데이터에는 Batch가 낫다.
**팁:**

절대적 답을 피하라 / 맥락 기반 비교.

## 36. 트리거에서 DML 한도 초과
**질문:**

트리거가 DML 한도를 초과한다. 고쳐라.
**답변:**

불필요한 DML 작업을 줄이고 로직을 컬렉션으로 옮긴다. 트랜잭션당 오브젝트당 DML 하나를 보장한다.
**팁:**

"벌크 DML"을 언급하라 / 최적화 능력을 본다.

## 37. CPU 시간 한도 초과
**질문:**

운영에서 CPU 시간 한도를 초과했다. 왜인가?
**답변:**

비효율적 루프, 재귀 트리거, 복잡한 로직이 원인이다. 루프를 최적화하고 무거운 로직을 비동기 처리로 옮긴다.
**팁:**

CPU 이슈 = 나쁜 로직 / "최적화 + 비동기"라고 말하라.

## 38. Mixed DML 오류
**질문:**

Mixed DML 오류란 무엇이며 어떻게 해결하나?
**답변:**

Setup 오브젝트와 비-Setup 오브젝트를 함께 갱신할 때 발생한다. @future나 Queueable Apex로 해결한다.
**팁:**

매우 흔한 실무 오류 / 비동기 해법이 기대된다.

## 39. 통합 호출에서 한도 처리
**질문:**

콜아웃 한도를 어떻게 처리하나?
**답변:**

콜아웃을 배치 처리하고, 비동기 Apex를 쓰며, 필요시 재시도 로직을 구현한다.
**팁:**

재시도 메커니즘을 언급하라 / 통합 성숙도를 보여준다.

## 40. 데이터 손실 없이 운영 이슈 디버깅
**질문:**

운영 이슈를 어떻게 안전하게 디버그하나?
**답변:**

특정 사용자에 대한 디버그 로그를 쓰고, 데이터 변경을 피하며, 배포 전 샌드박스에서 수정을 테스트한다.
**팁:**

운영 안전 답변이 중요 / "운영에서 바로 테스트한다"고 말하지 마라.

## 41. 실시간 통합 vs 배치 통합
**질문:**

배치 통합 대신 실시간 통합은 언제 고르나?
**답변:**

주문 생성이나 결제 확인처럼 즉각적인 데이터 일관성이 필요할 때 실시간 통합을 고른다. 야간 데이터 동기화나 리포팅 데이터 적재 같은 비핵심 업데이트에는 배치 통합이 낫다.
**팁:**

항상 비즈니스 긴급성과 연결하라 / 기술만 설명하지 마라.

## 42. REST vs SOAP – 무엇을 왜 썼나?
**질문:**

REST와 SOAP 중 어느 통합을 썼나?
**답변:**

주로 REST를 썼다. 가볍고 유지보수가 쉬우며 널리 지원되기 때문이다. SOAP은 외부 시스템이 WSDL 기반 계약을 명시적으로 요구할 때만 썼다.
**팁:**

현대 프로젝트에서는 REST가 기본이라고 말하라 / SOAP은 레거시 또는 요구사항 기반.

## 43. 트리거에서 콜아웃 – 어떻게 처리했나?
**질문:**

레코드 생성 시 외부 시스템을 호출해야 한다. 트리거는 콜아웃을 직접 할 수 없다. 어떻게 하겠는가?
**답변:**

Database.AllowsCallouts가 있는 Queueable Apex로 콜아웃을 호출한다. 트리거는 레코드 ID만 수집해 비동기 처리로 넘긴다.
```apex
public class IntegrationJob implements Queueable, Database.AllowsCallouts {
public void execute(QueueableContext qc) {
// HTTP callout logic
}
}
```
**팁:**

비동기 + 콜아웃 인터페이스를 언급하라 / 흔한 운영 패턴.

## 44. Named Credentials – 왜 중요한가?
**질문:**

왜 Named Credentials를 썼나?
**답변:**

Named Credentials는 엔드포인트 URL과 인증 정보를 안전하게 저장한다. 자격 증명 하드코딩을 없애고 토큰 관리를 단순화한다.
**팁:**

"보안 + 유지보수성"이라고 말하라 / 2026 인터뷰에서 매우 중요.

## 45. 프로젝트에서 사용한 OAuth 흐름
**질문:**

어떤 OAuth 흐름을 왜 썼나?
**답변:**

서버 간 통합에 OAuth 2.0 JWT Bearer Flow를 썼다. 사용자 상호작용이 없고 더 안전하기 때문이다.
**팁:**

JWT 흐름은 시니어 수준 노출을 보여준다 / OAuth 종류만 나열하지 마라.

## 46. 통합 실패를 우아하게 처리
**질문:**

외부 시스템이 다운되면 어떻게 되나?
**답변:**

실패를 로깅하고, 페이로드를 저장하며, scheduled나 queueable 작업으로 재시도한다. 알림이나 대시보드로 비즈니스 사용자에게 알린다.
**팁:**

재시도 + 로깅은 필수 / 회복탄력성 사고를 보여준다.

## 47. 외부 API의 타임아웃 또는 500 오류
**질문:**

외부 API가 타임아웃이나 500 오류를 반환한다. 어떻게 하겠는가?
**답변:**

try-catch 블록으로 처리하고, 응답을 로깅하며, 지수 백오프(exponential backoff)로 재시도 로직을 구현한다.
**팁:**

백오프 전략을 언급하라 / 견고성을 본다.

## 48. 벌크 콜아웃 제약
**질문:**

Salesforce에서 벌크 콜아웃을 어떻게 처리하나?
**답변:**

레코드를 배치로 처리하고 레코드당이 아닌 배치당 콜아웃 하나를 만든다. 필요하면 작업을 여러 Queueable 실행으로 나눈다.
**팁:**

레코드당 콜아웃을 피하라 / 거버너 한도 인식이 핵심.

## 49. 인바운드 통합 – 외부 시스템 호출
**질문:**

외부 시스템이 어떻게 Salesforce로 데이터를 푸시하나?
**답변:**

적절한 인증과 검증을 갖춘 Apex REST 클래스로 노출한 REST API를 통해서.
```apex
@RestResource(urlMapping='/account/create')
global with sharing class AccountAPI {
@HttpPost
global static void createAccount() {
// request handling
}
}
```
**팁:**

보안 검증을 언급하라 / Apex REST는 널리 쓰인다.

## 50. 인바운드 API 보안
**질문:**

인바운드 Apex REST API를 어떻게 보호하나?
**답변:**

OAuth 인증, IP 화이트리스트를 쓰고, 처리 전 요청 페이로드를 검증한다.
**팁:**

보안 답변에 가중치가 크다 / "개방형 API"라고 말하지 마라.

## 51. CRUD와 FLS – 어디서 강제하나?
**질문:**

CRUD와 필드 수준 보안을 어디서 체크하나?
**답변:**

특히 LWC나 API로 데이터를 노출할 때 Schema 메서드로 Apex에서 CRUD와 FLS를 강제한다.
**팁:**

LWC + API에 필수 / 컴플라이언스 인식을 보여준다.

## 52. with sharing vs without sharing – 결정
**질문:**

왜 with sharing을 썼나?
**답변:**

with sharing은 레코드 수준 보안을 존중한다. 비즈니스 규칙이 허용하는 시스템 수준 작업에만 without sharing을 쓴다.
**팁:**

"최소 권한 원칙"을 말하라 / 보안 마인드가 중요.

## 53. LWC에서 무단 데이터 접근 방지
**질문:**

LWC가 제한된 데이터를 노출하지 않도록 어떻게 보장하나?
**답변:**

Apex 계층에서 데이터를 필터링하고, FLS를 강제하며, 불필요한 필드를 클라이언트로 보내지 않는다.
**팁:**

서버 측 제어가 핵심 / UI만 신뢰하지 마라.

## 54. Shield Platform Encryption – 써봤나?
**질문:**

암호화된 필드를 다뤄봤나?
**답변:**

예. 민감 필드에 Shield Platform Encryption을 썼다. 검색·리포팅 제한 같은 한계를 고려했다.
**팁:**

한계를 언급하라 / 엔터프라이즈 노출을 보여준다.

## 55. Login IP Relaxation – 언제 필요한가?
**질문:**

Login IP Relaxation은 언제 쓰나?
**답변:**

IP 범위가 자주 바뀌는 신뢰된 통합 사용자나 회사 네트워크에 쓴다.
**팁:**

남용하지 마라 / 보안 트레이드오프 설명이 중요.

## 56. Single Sign-On (SSO) 시나리오
**질문:**

Salesforce에서 SSO는 어떻게 동작하나?
**답변:**

Salesforce가 Service Provider 역할을 하고 SAML이나 OAuth로 인증하는 Identity Provider에 의존한다.
**팁:**

고수준 설명이면 충분 / 아키텍처 사고를 기대한다.

## 57. JWT vs Web Server OAuth Flow
**질문:**

JWT와 Web Server Flow의 차이는?
**답변:**

JWT는 서버 간 통신에, Web Server Flow는 사용자 로그인과 동의가 필요할 때 쓴다.
**팁:**

간결하고 정확한 답이 이긴다 / 이론을 너무 많이 풀지 마라.

## 58. Integration User 설정 – 베스트 프랙티스
**질문:**

Integration User를 어떻게 구성하나?
**답변:**

최소 권한의 전용 사용자를 만들고, Permission Set을 할당하며, Named Credentials를 활성화한다.
**팁:**

관리자 사용자를 절대 쓰지 마라 / 감사와 보안이 중요.

## 59. 토큰 만료 처리
**질문:**

OAuth 토큰이 만료되면 어떻게 되나?
**답변:**

refresh token이 있으면 Salesforce가 자동으로 토큰을 갱신한다. 없으면 재인증이 필요하다.
**팁:**

refresh token을 언급하라 / 실제 OAuth 사용을 보여준다.

## 60. 운영에서 겪은 실제 통합 이슈
**질문:**

운영에서 겪은 실제 통합 이슈를 설명하라.
**답변:**

외부 시스템이 페이로드 형식을 바꿔 실패가 발생했다. 파싱 로직을 갱신하고, 검증을 추가하며, 하위 호환성을 구현했다.
**팁:**

실제 사건 스토리가 가장 중요 / 주인의식과 학습이 핵심.

## 61. LWC vs Aura – 왜 프로젝트에서 LWC인가?
**질문:**

왜 프로젝트가 Aura에서 LWC로 마이그레이션했나?
**답변:**

LWC는 더 나은 성능, 최신 JavaScript 표준, Lightning Web Security로 향상된 보안을 제공한다. Aura는 유지보수가 어렵고 복잡한 UI에서 느렸다.
**팁:**

"성능 + 유지보수성"이라고 말하라 / Aura가 "구식"이라 하지 말고 "레거시"라 하라.

## 62. Lightning Data Service vs Apex 호출
**질문:**

Apex 대신 Lightning Data Service는 언제 쓰나?
**답변:**

표준 CRUD 작업에는 LDS를 쓴다. 캐싱·보안·UI 새로고침을 자동 처리하기 때문이다. 복잡한 비즈니스 로직에는 Apex를 쓴다.
**팁:**

LDS = 버그 감소 / 아키텍처 사고를 기대한다.

## 63. Cacheable Apex – 언제 쓰고 언제 안 쓰나?
**질문:**

왜 모든 Apex 메서드가 cacheable일 수 없나?
**답변:**

cacheable 메서드는 읽기 전용이어야 한다. 데이터가 변하거나 사용자 컨텍스트에 동적으로 의존하면 캐싱이 오래된 데이터(stale data) 문제를 일으킬 수 있다.
**팁:**

"읽기 전용 제약"을 언급하라 / cacheable=true를 맹목적으로 쓰지 마라.

## 64. 레코드 저장 후 LWC가 갱신되지 않음
**질문:**

LWC가 데이터를 저장하지만 UI가 갱신되지 않는다. 고쳐라.
**답변:**

wired 메서드를 쓸 때는 refreshApex()를 쓰거나 자동 새로고침을 위해 Lightning Data Service에 의존한다.
**팁:**

refreshApex가 기대 답변 / 실전 LWC 경험을 보여준다.

## 65. LWC 간 데이터 전달
**질문:**

두 LWC 간 통신은 어떻게 하나?
**답변:**

부모-자식 통신에는 custom event를, 관련 없는 컴포넌트에는 Lightning Message Service를 쓴다.
**팁:**

LMS는 시니어 역할에 중요 / "전역 변수"라고 말하지 마라.

## 66. 느린 LWC 페이지 로드 – 진단
**질문:**

LWC 때문에 Lightning 페이지가 느리게 로드된다. 어떻게 고치나?
**답변:**

서버 호출을 줄이고, Apex 쿼리를 결합하며, 캐싱을 활성화하고, 불필요한 재렌더링을 피한다.
**팁:**

성능 튜닝은 핫토픽 / 서버 왕복(round trip)을 언급하라.

## 67. 불필요한 재렌더링 방지
**질문:**

LWC에서 불필요한 재렌더링을 어떻게 피하나?
**답변:**

tracked 속성을 불필요하게 수정하지 않고 불변(immutable) 데이터 패턴을 쓴다.
**팁:**

깊은 JS 이해를 보여준다 / 드물지만 인상적인 답변.

## 68. LWC에서 대용량 데이터셋 표시
**질문:**

LWC에서 수천 건의 레코드를 어떻게 표시하나?
**답변:**

한 번에 모두 로드하지 않고 페이지네이션이나 지연 로딩(lazy loading)을 쓴다.
**팁:**

절대 모든 데이터를 로드하지 마라 / UI 확장성이 중요.

## 69. 검색 입력 디바운싱
**질문:**

LWC에서 검색 입력을 어떻게 최적화하나?
**답변:**

디바운싱을 구현해 키 입력마다 Apex 호출이 발생하지 않게 한다.
**팁:**

프런트엔드 최적화는 성숙도를 보여준다 / 인터뷰어가 좋아한다.

## 70. 동시 사용자 액션 처리
**질문:**

여러 사용자가 같은 레코드를 갱신한다. 충돌을 어떻게 처리하나?
**답변:**

Salesforce 레코드 잠금(record locking)에 의존하고 충돌 시 의미 있는 오류 메시지를 보여준다.
**팁:**

레코드 잠금을 언급하라 / 실제 멀티유저 시나리오.

## 71. LWC에서 XSS 방지
**질문:**

LWC는 XSS를 어떻게 방어하나?
**답변:**

LWC는 Lightning Web Security를 쓰고 DOM 업데이트를 자동 정화(auto-sanitize)해 스크립트 주입을 방지한다.
**팁:**

"자동 정화"라고 말하라 / 보안 질문이 중요.

## 72. UI에서 필드 수준 보안 표시
**질문:**

LWC UI에서 FLS를 어떻게 존중하나?
**답변:**

Apex에서 FLS를 강제하고, 보안을 자동 존중하는 LDS를 쓴다.
**팁:**

서버 측 강제가 필수 / UI만의 체크는 불충분.

## 73. 무단 Apex 접근 처리
**질문:**

사용자가 권한 없이 Apex를 호출하면?
**답변:**

Salesforce가 예외를 던진다. 또한 사전에 권한을 체크하고 UI에서 오류를 우아하게 처리한다.
**팁:**

오류 처리가 중요 / 보안 인식을 평가한다.

## 74. LWC가 너무 많은 데이터 노출
**질문:**

UI에 불필요한 데이터 노출을 어떻게 방지하나?
**답변:**

Apex에서 필요한 필드만 보내고 전체 SObject 반환을 피한다.
**팁:**

최소 페이로드 = 더 나은 성능 + 보안 / 좋은 아키텍처 답변.

## 75. Lightning Record Page 최적화
**질문:**

Lightning Record Page를 어떻게 최적화하나?
**답변:**

컴포넌트 수를 제한하고, 무거운 LWC를 피하며, 조건부 표시(conditional visibility)를 쓴다.
**팁:**

관리자+개발자 혼합 질문 / 플랫폼 지식을 보여준다.

## 76. LWC에서 우아한 오류 처리
**질문:**

LWC에서 오류를 어떻게 우아하게 처리하나?
**답변:**

토스트 메시지를 보여주고, 오류를 로깅하며, 원시 예외 대신 사용자 친화적 메시지를 제공한다.
**팁:**

UX 사고가 중요 / UI에 기술 용어를 피하라.

## 77. UI에서 부분 성공 처리
**질문:**

일부 레코드는 성공, 일부는 실패한다. 어떻게 처리하나?
**답변:**

요약 메시지를 보여주고 실패한 레코드의 재시도를 허용한다.
**팁:**

부분 성공 처리 = 실무 UI / 사용자 공감을 보여준다.

## 78. 오프라인 또는 네트워크 실패 처리
**질문:**

네트워크가 실패하면 UI가 어떻게 동작하나?
**답변:**

오류 메시지를 보여주고 중복 액션을 방지한다. 중요한 액션에는 재시도를 허용한다.
**팁:**

신뢰성 사고 / 매우 강력한 실무 답변.

## 79. 클라이언트 측 오류 로깅
**질문:**

클라이언트 측 오류를 어떻게 추적하나?
**답변:**

JavaScript에서 오류를 잡아 Apex나 외부 모니터링 도구로 로그를 보낸다.
**팁:**

관측성(observability) 마인드를 보여준다 / 드물지만 인상적.

## 80. 운영에서 고친 실제 UI 버그
**질문:**

고친 실제 UI 이슈를 설명하라.
**답변:**

Apex의 null 데이터로 컴포넌트가 실패했다. 방어적 체크를 추가하고 오류 처리를 개선했다.
**팁:**

실제 스토리가 중요 / 학습과 개선을 보여라.

## 81. 운영 배포 실패 – 첫 조치
**질문:**

운영 배포가 실패했다. 먼저 무엇을 하겠는가?
**답변:**

먼저 배포 오류 로그를 확인해 테스트 실패, 의존성 누락, 권한 이슈 중 무엇인지 파악한다. 무작정 재시도하지 않는다. 근본 원인을 찾아 샌드박스에서 고치고 재배포한다.
**팁:**

근본 원인 분석 먼저 / "빨리 다시 배포한다"고 말하지 마라.

## 82. Change Set vs SFDX – 무엇을 썼나?
**질문:**

Change Set과 SFDX 중 무엇을 썼나?
**답변:**

CI/CD 파이프라인에 SFDX를 썼다. 자동화, 버전 관리, 더 나은 롤백을 지원하기 때문이다. Change Set은 작은 관리자 수준 변경에만 썼다.
**팁:**

2026에는 SFDX가 기대된다 / 자동화를 명확히 언급하라.

## 83. 테스트 커버리지로 배포 차단
**질문:**

테스트 커버리지 때문에 배포가 차단된다. 어떻게 처리하나?
**답변:**

더미 테스트를 추가하는 대신 실제 로직을 커버하는 의미 있는 테스트 클래스를 작성한다. 전체 75% 이상, 신규 코드에 대한 적절한 커버리지를 보장한다.
**팁:**

양보다 질 / 인터뷰어는 가짜 테스트를 싫어한다.

## 84. 배포 중 데이터 의존성 이슈
**질문:**

데이터 누락으로 배포가 실패했다. 해법은?
**답변:**

테스트에서 하드코딩된 데이터 의존성을 제거하고 @testSetup으로 테스트 클래스 안에서 테스트 데이터를 생성한다.
**팁:**

@testSetup이 중요 / 안정적 배포 사고를 보여준다.

## 85. 운영 핫픽스 – 어떻게 처리하나?
**질문:**

즉시 수정이 필요한 치명적 운영 이슈. 무엇을 하나?
**답변:**

핫픽스 브랜치를 만들어 최소한의 변경을 구현하고, 철저히 테스트하고, 배포한 뒤, main 브랜치로 머지백한다.
**팁:**

핫픽스 브랜치 전략이 기대됨 / 리스크 최소화가 중요.

## 86. 따른 Git 브랜칭 전략
**질문:**

어떤 Git 브랜칭 전략을 썼나?
**답변:**

main과 release 브랜치를 둔 feature 브랜치를 따랐다. 각 기능은 개발·리뷰·PR로 머지했다.
**팁:**

코드 리뷰를 언급하라 / 팀 협업을 보여준다.

## 87. 머지 충돌 해결
**질문:**

머지 충돌을 어떻게 처리하나?
**답변:**

충돌 파일을 분석하고, 양쪽 변경을 이해하고, 신중히 해결한 뒤, 푸시 전에 테스트를 돌린다.
**팁:**

"force push"라고 말하지 마라 / 신중한 해결이 핵심.

## 88. main 브랜치에 실수로 커밋
**질문:**

실수로 main 브랜치에 커밋했다. 어떻게 하겠는가?
**답변:**

영향에 따라 즉시 커밋을 되돌리거나 핫픽스를 만들고, 이후 올바른 브랜칭 프로세스를 따른다.
**팁:**

주인의식이 중요 / 실수 + 복구가 인터뷰어에게 인상을 준다.

## 89. 코드 리뷰 피드백 – 어떻게 대응했나
**질문:**

코드 리뷰 피드백을 어떻게 다루나?
**답변:**

피드백을 객관적으로 검토하고, 코드 품질을 개선하며, 필요할 때만 논의한다.
**팁:**

팀 마인드가 중요 / 자존심 없는 답변 선호.

## 90. Git 롤백 시나리오
**질문:**

배포가 이슈를 일으켰다. 어떻게 롤백하나?
**답변:**

Git에서 커밋을 revert하고 운영을 수동으로 바꾸는 대신 안정 버전을 재배포한다.
**팁:**

UI가 아닌 Git으로 롤백 / 규율을 보여준다.

## 91. 운영 작업 모니터링
**질문:**

운영 작업을 어떻게 모니터링하나?
**답변:**

AsyncApexJob, 디버그 로그, 이메일 알림, 대시보드를 모니터링한다.
**팁:**

사전 모니터링이 중요 / 실패 후 대응만 하지 마라.

## 92. 비즈니스의 운영 버그 보고
**질문:**

비즈니스가 버그를 보고한다. 프로세스는?
**답변:**

단계를 수집하고, 샌드박스에서 재현하고, 근본 원인을 파악하고, 고치고, 테스트하고, 배포한다.
**팁:**

구조화된 접근 / 소통이 중요.

## 93. 데이터 손상 이슈
**질문:**

버그로 데이터가 손상됐다. 어떻게 하겠는가?
**답변:**

추가 처리를 멈추고, 백업이나 익스포트에서 데이터를 복원하고, 수정을 배포한다.
**팁:**

피해 통제(damage control) 먼저 / 책임감을 보여준다.

## 94. 운영 성능 저하
**질문:**

사용자가 Salesforce가 느리다고 불평한다. 무엇을 확인하나?
**답변:**

느린 SOQL, 비동기 작업 부하, 통합, 최근 배포를 확인한다.
**팁:**

성능 트리아지 마인드 / 플랫폼 상태를 본다.

## 95. 배포 후 릴리스 실패
**질문:**

배포 후 릴리스가 실패했다. 어떻게 대응하나?
**답변:**

즉시 소통하고, 필요하면 롤백하며, 다음 시도 전에 실패를 분석한다.
**팁:**

소통이 수정만큼 중요 / 리더십 답변.

## 96. 효과적인 테스트 클래스 작성
**질문:**

좋은 테스트 클래스란?
**답변:**

긍정·부정 시나리오를 커버하고, 현실적인 데이터를 쓰며, 비즈니스 결과를 검증한다.
**팁:**

"커버리지만을 위한" 마인드를 피하라 / 비즈니스 로직 검증이 중요.

## 97. 테스트에서 콜아웃 모킹
**질문:**

콜아웃을 어떻게 테스트하나?
**답변:**

HttpCalloutMock으로 테스트 중 응답을 시뮬레이션한다.
**팁:**

통합 테스트에 필수 / 완성도를 보여준다.

## 98. 운영에서만 실패하는 테스트
**질문:**

샌드박스에서는 통과하지만 운영에서 실패한다. 왜인가?
**답변:**

데이터 차이, 권한, 또는 관리되지 않는 패키지(unmanaged package) 동작 때문.
**팁:**

운영은 샌드박스와 다르다 / 경험 기반 답변.

## 99. 테스트 건너뛰기 – 허용되나?
**질문:**

배포에서 테스트를 건너뛸 수 있나?
**답변:**

validated deployment를 쓰는 특정 경우에만 가능하지만 베스트 프랙티스는 아니다.
**팁:**

지름길을 권하지 마라 / 품질 우선 답변.

## 100. 운영에서 배운 가장 큰 교훈
**질문:**

운영에서 배운 가장 큰 교훈은?
**답변:**

절대 가정하지 마라. 항상 엣지 케이스를 테스트하고, 능동적으로 모니터링하며, 일찍 소통하라.
**팁:**

성찰이 중요 / 인터뷰어는 성숙함을 높이 산다.
