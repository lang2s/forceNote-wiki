# 필수 Salesforce 관리자(Admin) 면접 질문 (반드시 알아야 할 것)

> [!warning] 제3자 학습노트(면접 Q&A)를 한글로 변환한 **Tier 3** 자료입니다. 공식 소스와 대조되지 않았으니 정확도는 공식 문서로 검증하세요.

## 1. 레코드 공유와 보안

**Q1: Salesforce에서 공개(public)와 비공개(private) 레코드 공유의 차이는?**

- **공개(Public):** 모든 사용자가 자신의 프로필 권한과 공유 규칙에 따라 레코드를 볼 수 있습니다. 예를 들어 공개 공유 모델에서는 특정 공유 규칙이 제한하지 않는 한 모든 사용자가 모든 레코드를 볼 수 있습니다.
- **비공개(Private):** 레코드는 레코드 소유자와 특정 공유 권한이 있는 사람에게만 표시됩니다.

**Q2: 공유 규칙(Sharing Rule)이란?**

공유 규칙은 평소에는 접근할 수 없는 레코드에 특정 사용자가 접근할 수 있도록 부여하는 데 사용됩니다. 조직 수준에서 정의되며 기준(criteria)이나 소유권을 기반으로 할 수 있습니다.

## 2. Custom Settings와 Custom Metadata

**Q1: Custom Settings와 Custom Metadata Type의 차이는?**

- **Custom Settings:** 커스텀 오브젝트와 유사하지만, 데이터가 캐시되어 쿼리 없이 접근할 수 있어 더 빠릅니다. 일반적으로 자주 변경되지 않는 구성이나 데이터에 사용됩니다.
- **Custom Metadata Type:** 역시 커스텀 오브젝트와 유사하지만 배포 및 업그레이드가 가능합니다. 환경 전반에 걸쳐 재사용 가능한 메타데이터 구성을 만들 수 있습니다.

**Q2: Apex에서 Custom Metadata에 어떻게 접근하나요?**

SOQL 쿼리 구문을 사용해 접근할 수 있습니다:

```apex
List<CustomMetadataType__mdt> metadataRecords = [SELECT MasterLabel, Field__c FROM CustomMetadataType__mdt];
```

## 3. Record Type, 레이아웃, Dynamic Form

**Q1: Salesforce의 Record Type이란?**

Record Type을 사용하면 프로필에 따라 사용자에게 서로 다른 비즈니스 프로세스, 선택 목록 값, 페이지 레이아웃을 제공할 수 있습니다. 예를 들어 Opportunity가 "New Business"인지 "Renewal"인지에 따라 다른 페이지 레이아웃을 가질 수 있습니다.

**Q2: 페이지 레이아웃과 Dynamic Form의 차이는?**

- **페이지 레이아웃(Page Layout):** 페이지에 어떤 필드, 섹션, 버튼, 링크가 나타나는지와 이 요소들의 배치를 제어합니다.
- **Dynamic Form:** 레코드 페이지를 커스터마이징하는 더 유연한 방식으로, 코드 없이 특정 기준에 따라 필드와 섹션을 조건부로 표시할 수 있습니다.

## 4. 사용자 관리

**Q1: 프로필과 권한 집합의 차이는?**

- **프로필(Profile):** 사용자의 기본 권한(오브젝트·필드 CRUD 접근 등)을 정의합니다. 사용자는 프로필을 하나만 가질 수 있습니다.
- **권한 집합(Permission Set):** 프로필 자체를 변경하지 않고 프로필 위에 추가 권한을 제공합니다. 사용자는 여러 권한 집합을 가질 수 있습니다.

**Q2: Salesforce의 User License(사용자 라이선스)란?**

사용자 라이선스는 Salesforce, Salesforce Platform, Chatter Free 등 사용자가 이용할 수 있는 기준 기능과 기능성을 정의합니다. 할당된 기능과 접근을 기반으로 사용자가 Salesforce에서 무엇을 할 수 있는지 결정합니다.

## 5. 동결(Freeze) vs 비활성화(Deactivate)

**Q1: 사용자 동결과 비활성화의 차이는?**

- **동결(Freezing):** 사용자가 Salesforce에 로그인하는 것을 일시적으로 막지만, 권한과 데이터 접근은 유지합니다.
- **비활성화(Deactivating):** 사용자를 완전히 비활성화하여 조직 접근을 막습니다. 비활성화된 사용자는 로그인할 수 없으며, 다른 활성 사용자와 공유되지 않는 한 데이터 접근도 제거됩니다.

## 6. Scoping Rules와 Duplicate Rules

**Q1: Salesforce의 Duplicate Rule이란?**

중복 레코드 생성을 방지하는 데 도움을 줍니다. 중복을 식별하는 기준을 정의하고, 중복이 발견되었을 때 취할 조치(차단 또는 사용자 경고)를 설정합니다.

**Q2: Duplicate Rule의 Scoping Rule이란?**

Scoping Rule은 중복 검사 대상이 되는 데이터 집합을 정의합니다. 예를 들어 특정 Account, 지역, 레코드 타입 내에서만 중복을 검사하도록 설정할 수 있습니다.

## 7. 관계와 데이터 모델

**Q1: Lookup, Master-Detail, Junction 관계란?**

- **Lookup 관계:** 한 오브젝트가 다른 오브젝트를 참조할 수 있는 일대일(one-to-one) 관계입니다.
- **Master-Detail 관계:** 자식 레코드의 라이프사이클이 부모에 묶이는 강하게 결합된 일대다(one-to-many) 관계입니다.
- **Junction 관계:** 두 개의 Master-Detail 관계를 사용해 생성하는 다대다(many-to-many) 관계입니다.

**Q2: Self-Lookup 관계란?**

오브젝트가 자기 자신을 참조하는 Lookup 필드를 가질 때 발생하며, 같은 오브젝트의 다른 레코드에 레코드를 연결할 수 있게 합니다.

## 8. 리포트와 대시보드

**Q1: Report와 Dashboard의 차이는?**

- **리포트(Reports):** 표(tabular), 요약(summary), 행렬(matrix), 결합(joined) 형식의 원시 데이터입니다. 데이터를 필터링, 그룹화, 요약할 수 있습니다.
- **대시보드(Dashboards):** 여러 리포트를 시각적으로 표현하여, 그래프·차트·표로 핵심 지표를 한눈에 추적할 수 있게 합니다.

## 9. 승인 프로세스

**Q1: Salesforce 승인 프로세스의 유형은?**

- **표준 승인 프로세스:** 관리자가 Opportunity를 검토·승인하는 등 사전 정의된 단계와 규칙 세트.
- **커스텀 승인 프로세스:** 회사 요구에 맞춘, 커스터마이징 가능한 규칙·액션·단계를 가진 프로세스.

**Q2: 승인 프로세스는 몇 단계까지 가질 수 있나요?**

승인 프로세스는 여러 단계를 가질 수 있으며, 각 단계는 "Submit for approval", "Manager Approval", "Final Approval" 같은 승인 주기의 한 단계에 해당합니다. 명확한 제한은 없지만 일반적으로 1~10단계를 가집니다.

## 10. 검증 규칙(Validation Rule)

**Q1: Validation Rule이란?**

Salesforce에 입력된 데이터가 지정된 기준을 충족하도록 보장하여, 유효하지 않은 데이터로 레코드를 저장하지 못하게 합니다. 데이터가 조건을 충족하지 않으면 오류 메시지를 반환합니다.

**Q2: Validation Rule의 일반적인 사용 사례는?**

- 필수 필드가 비어 있지 않도록 보장
- 이메일 주소가 올바른 형식을 따르도록 검증
- Opportunity나 Contract에서 시작 날짜가 종료 날짜보다 앞서도록 보장

## 11. Public Group, Queue, List View

**Q1: Public Group이란?**

공유 규칙, 리포트, 대시보드에서 레코드 접근을 부여하는 데 사용할 수 있는 사용자 집합입니다. 개별 사용자, 역할, 다른 그룹의 모음입니다.

**Q2: Queue와 List View의 차이는?**

- **Queue:** 사용자 그룹이 작업해야 하는 레코드(예: Case, Lead)를 관리하는 데 사용됩니다. Queue의 레코드는 처리를 위해 특정 사용자에게 할당됩니다.
- **List View:** 사용자 정의 기준에 따라 레코드 집합을 필터링하고 표시하는 방법을 제공합니다. 표 형식으로 데이터를 표시합니다.

## 프로젝트 기반 설명

### 1. 레코드 공유와 보안

**Q1: 여러 부서가 있는 Salesforce 조직에서 레코드 수준 보안을 어떻게 구현하나요?**

- 부서 역할에 따라 오브젝트와 필드 접근을 제어하기 위해 **프로필**을 구현합니다.
- 모든 사용자에게 모든 것을 개방하지 않고 부서별로 관련 레코드에 접근하도록 **공유 규칙**을 사용합니다.
- 같은 부서의 상위 사용자가 하위 사용자가 소유한 레코드에 접근하도록 **역할 계층**을 사용합니다.
- 부서에 따라 민감한 정보를 특정 사용자로부터 숨기기 위해 **필드 수준 보안**을 사용합니다.
- 더 세밀한 제어가 필요한 복잡한 경우 **Apex Managed Sharing**을 사용할 수 있습니다.

### 2. Custom Settings와 Custom Metadata

**Q1: 프로젝트에서 구성 관리를 위해 Custom Metadata를 어떻게 사용하나요?**

여러 환경(샌드박스, 운영 등)에 걸쳐 재사용 가능하고 배포 가능한 구성이 필요한 프로젝트의 경우:

- 각 구성 요구사항에 대해 **Custom Metadata Type**을 만듭니다.
- 임계값, 승인 설정, 외부 시스템 API 키 같은 값을 custom metadata에 저장합니다.
- 하드코딩된 설정 없이 동적으로 기능을 커스터마이징하기 위해 Apex나 Lightning 컴포넌트에서 custom metadata 값을 쿼리하고 적용합니다.
- 변경 집합(change sets)이나 Salesforce DX를 사용해 한 환경에서 다른 환경으로 Custom Metadata 레코드를 배포합니다.

**Q2: 프로젝트에서 사용자별 구성을 저장하는 데 Custom Settings를 사용할 수 있나요?**

네, Custom Settings는 배포가 필요 없을 수 있는 사용자별/프로필별 구성을 저장하는 데 이상적입니다. 애플리케이션 전체 구성에는 List Custom Settings를, 개별 사용자나 프로필별 데이터에는 Hierarchy Custom Settings를 사용해 데이터를 캐싱함으로써 성능을 개선합니다.

### 3. Record Type, 레이아웃, Dynamic Form

**Q1: 다단계 승인 프로세스에서 사용자를 위한 동적 페이지 레이아웃을 어떻게 구현하나요?**

- **Record Type**을 사용해 승인 프로세스의 단계("Draft", "In Review", "Approved" 등)를 구분합니다.
- 각 Record Type에 단계별로 관련 필드를 보여주는 고유한 **페이지 레이아웃**을 할당합니다.
- 레코드 값이나 사용자 입력에 따라 필드를 조건부로 표시/숨김하도록 **Dynamic Form**을 사용해 더 효율적인 양식을 만듭니다.
- 조건에 따라 특정 필드에 대한 가시성 규칙을 설정하여, 사용자가 각자의 단계에 관련된 필드만 보도록 할 수 있습니다.

### 4. 사용자 관리

**Q1: 대규모 Salesforce 프로젝트에서 여러 부서에 걸친 사용자 접근과 권한을 어떻게 관리하나요?**

- 각 사용자가 필요한 오브젝트·필드·데이터에만 접근하도록 부서나 직무별로 **프로필**을 정의합니다.
- 프로필을 수정하지 않고 추가 기능 접근이 필요한 사용자에게 **권한 집합**을 할당합니다.
- 관리자나 감독자가 부하 직원이 소유한 레코드에 접근하도록 **역할 계층**을 사용합니다.
- 부서 간 협업을 위해 **Public Group**과 **공유 규칙**을 사용해, 서로 다른 부서 사용자가 공유 기준에 따라 필요한 레코드에 접근하도록 합니다.
- 신규 사용자 온보딩 시 적절한 프로필·역할·권한을 할당하는 표준 사용자 설정 프로세스를 따라야 합니다.

### 5. 동결 vs 비활성화

**Q1: 사용자 비활성화 프로세스 구현 시 비즈니스 운영 중단을 최소화하려면?**

- 먼저 사용자를 **동결(freeze)**하여 로그인을 막고, 기존 작업과 레코드의 재할당 필요 여부를 확인합니다.
- 비활성화 전에 열린 작업이나 활성 레코드(Opportunity, Case 등)를 다른 활성 사용자나 Queue로 재할당합니다.
- 모든 레코드가 이전되고 사용자의 워크플로우가 종료된 후에만 사용자를 비활성화합니다.
- 사용자가 동결/비활성화될 때 다른 사용자가 변경 사항을 인지하도록 적절한 이메일 알림을 설정합니다.

### 6. Scoping Rules와 Duplicate Rules

**Q1: 여러 채널의 Lead가 포함된 프로젝트에서 중복 관리를 어떻게 구현하나요?**

- Lead 데이터(이메일, 전화번호 등)를 기반으로 **Duplicate Rule**을 정의합니다. **Matching Rule**을 사용해 Lead가 중복으로 간주되는 시점(예: 동일 이메일/전화번호)을 결정합니다.
- **Scoping Rule**을 사용해 서로 다른 Lead 소스 채널에 걸친 중복 검사 범위를 설정합니다(예: 같은 Lead 소스 내에서만 검사).
- 중복이 발견되면 입력을 막는 **Block**이나 사용자에게 알리는 **Alert** 같은 액션을 사용합니다.
- 데이터가 쌓이면서 정확도를 높이기 위해 이 규칙들을 정기적으로 모니터링하고 개선합니다.

### 7. 관계와 데이터 모델

**Q1: 각 제품이 여러 관련 문서와 태그를 가질 수 있는 프로젝트의 데이터 모델을 어떻게 설계하나요?**

- 제품이 삭제되면 관련 문서도 모두 삭제되도록 Product와 Document 간에 **Master-Detail 관계**를 사용합니다.
- 태그의 경우, Product와 Tag 간 다대다 관계를 만들기 위해 **Junction Object**를 사용합니다. 이를 통해 제품이 여러 태그와 연결되고, 태그가 여러 제품에 재사용될 수 있습니다.
- 레코드 라이프사이클에 영향을 주지 않고 한 오브젝트가 다른 오브젝트를 참조해야 할 때는 **Lookup 관계**를 사용할 수 있습니다.

### 8. 리포트와 대시보드

**Q1: Opportunity와 거래를 추적하는 실시간 영업 대시보드를 어떻게 구현하나요?**

- 다양한 단계에 걸친 Opportunity 단계, 매출, 성사율을 추적하는 **리포트**를 만듭니다.
- 전환율, 총 매출, 예상 매출 같은 차트·그래프·KPI를 보여주는 실시간 데이터 시각화를 위해 **Dynamic Dashboard**를 사용합니다.
- **Interactive Filters**를 사용해 특정 지역, 제품 라인, 영업 담당자별로 데이터를 필터링할 수 있게 합니다.
- 효과적인 실시간 추적을 위해 데이터가 자주 업데이트되도록 하고, **Report Subscriptions**를 통해 중요한 변화나 기회를 사용자에게 알립니다.

### 9. 승인 프로세스

**Q1: 다단계 승인과 조건부 단계 같은 복잡한 워크플로우가 포함된 승인 프로세스를 어떻게 설계하나요?**

- 단계("Initial Approval", "Manager Approval", "Final Approval" 등)를 정의하는 **커스텀 승인 프로세스**를 만듭니다.
- 조건(예: Opportunity Value > $10,000)에 따라 어떤 레코드가 프로세스에 진입하는지 정의하는 **진입 기준**을 사용합니다.
- 레코드 필드 값이나 사용자 역할에 따라 특정 단계를 건너뛰거나 추가하는 **동적 승인 단계**를 구현합니다(예: 고가치 Opportunity의 경우 임원이 관리자 대신 승인).
- 승인을 진행하고 사용자에게 알리기 위해 이메일 알림, 필드 업데이트 같은 **자동화 액션**을 사용합니다.

### 10. 검증 규칙

**Q1: Salesforce 프로젝트에서 데이터 품질을 보장하기 위해 검증 규칙을 어떻게 구현하나요?**

- Opportunity의 Close Date가 Created Date보다 빠르지 않도록 하는 등 올바른 데이터 입력을 강제하는 **검증 규칙**을 만듭니다.
- 특정 제품에 대해 사전 정의된 임계값보다 큰 할인을 막는 등 수식을 사용해 특정 값을 제한합니다.
- 사용자가 복잡한 데이터를 입력할 수 있는 프로젝트에서는, 검증 피드백을 더 유용하고 친절하게 만들기 위해 커스텀 오류 메시지를 만드는 것을 고려합니다.
- 워크플로우에 부정적 영향을 주지 않도록 배포 전에 샌드박스 환경에서 모든 검증 규칙을 테스트합니다.

### 11. Public Group, Queue, List View

**Q1: 고객 서비스 프로젝트에서 Queue와 List View를 사용해 Case 관리 솔루션을 어떻게 구현하나요?**

- 고객 서비스 담당자의 주의가 필요한 Case를 관리하기 위해 **Queue**를 사용합니다. 기준에 따라 Case를 특정 Queue에 할당합니다(예: 높은 우선순위 Case는 "High Priority" Queue로).
- 우선순위, 상태, Case 소유자 같은 중요한 요소에 따라 Case를 필터링하고 표시하는 **List View**를 만듭니다.
- 협업이 필요한 관련 팀(영업, 지원 등) 간에 Case 접근을 공유하기 위해 **Public Group**을 설정합니다.
- 적시에 해결되지 않은 Case가 자동으로 상위 Queue나 관리자에게 재할당되도록 **에스컬레이션 규칙(Escalation Rules)**을 구현합니다.
