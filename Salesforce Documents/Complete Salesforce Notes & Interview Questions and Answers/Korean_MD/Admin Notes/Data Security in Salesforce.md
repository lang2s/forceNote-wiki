# Salesforce의 데이터 보안(Data Security)

> [!warning] 제3자 학습노트(면접 Q&A)를 한글로 변환한 **Tier 3** 자료입니다. 공식 소스와 대조되지 않았으니 정확도는 공식 문서로 검증하세요.

## 데이터 보안이란?

여러분과 회사가 저장하거나 공유하는 민감한 정보를 보호하는 것입니다. 모든 조직에 중요하며, 특히 금융·헬스케어·소매 같은 규제 산업에서 핵심적입니다. 데이터 보안은 보안 조치나 도구만이 아니라 마음가짐이기도 합니다.

Salesforce는 세 가지 수준의 보안을 사용합니다: 1) 오브젝트 수준, 2) 필드 수준, 3) 레코드 수준.

## Layer 1: 오브젝트 수준 보안

접근 허용 전, Salesforce는 사용자가 해당 유형의 오브젝트를 볼 권한이 있는지 먼저 확인합니다. 프로필과 권한 집합 두 가지 구성으로 관리합니다.

오브젝트 수준에서 CREATE/READ/EDIT/DELETE 권한을 주면 사용자는 자신이 만든 레코드만 삭제할 수 있고, 다른 사용자(관리자 등)가 만든 것은 삭제할 수 없습니다.

**오브젝트 수준 주요 권한:**
- **Read:** 레코드 보기
- **Create:** 새 레코드 추가
- **Edit:** 기존 레코드 수정
- **Delete:** 레코드 제거
- **View All:** 다른 공유 규칙과 무관하게 그 오브젝트의 모든 레코드 보기
- **Modify All:** 그 오브젝트의 모든 레코드 편집·삭제

**View All이란?** 소유권·공유 설정과 무관하게 특정 오브젝트의 모든 레코드를 볼 수 있게 함. 예: Accounts에 View All이 있으면 다른 사용자가 private으로 표시한 것을 포함해 모든 Account를 볼 수 있음.

**Modify All이란?** View All보다 한 단계 위로, 공유 규칙·소유권과 무관하게 특정 오브젝트의 모든 레코드를 편집·삭제·소유권 이전 가능. 사실상 그 오브젝트에 대한 관리자 수준.

**왜 사용하나?** 관리자, 데이터 관리자, 감사자 같은 슈퍼 유저에게 부여(대량 데이터 관리, 시스템 전체 리포트, 데이터 정리).

**표준 권한과의 차이:** 표준 권한(Read, Edit, Create, Delete)은 공유 규칙·소유권에 의해 제한됨. View All·Modify All은 이를 무시하고 모든 레코드에 전역 접근 제공.

## Layer 2: 필드 수준 보안

사용자가 특정 필드를 보고 편집하는 접근을 제한합니다. 프로필과 권한 집합이 제어합니다. 개별 필드에 read·write 권한을 부여하거나 hidden으로 완전히 숨길 수 있습니다(API 포함 모든 진입점에서 접근 불가). 페이지 레이아웃에서 필드를 제거하는 대신 필드 수준 보안 사용이 권장됩니다.

- **Visible:** 사용자가 UI에서 필드를 보고 편집 가능(오브젝트·레코드 수준 권한이 있다면). 표시하지 않으면 모든 인터페이스(UI, 리포트, API)에서 완전히 숨겨짐.
- **Read-Only:** 필드를 볼 수 있지만 편집 불가. 다른 권한을 무시함(오브젝트·레코드 수준 edit 권한이 있어도 수정 불가).

| Visible | Read-Only | 결과 |
|---|---|---|
| Yes | No | 보기·편집 가능 |
| Yes | Yes | 보기만 가능(읽기 전용) |
| No | No | 완전히 숨김 |
| No | Yes | 완전히 숨김 |

## 권한 집합(Permission Set)

특정 도구·기능에 접근을 부여하는 권한·설정의 모음. 프로필 변경 없이 사용자 접근을 확장하므로 권장됩니다.

- **프로필:** 사용자의 기준 접근 수준 정의(오브젝트·필드·앱 접근).
- **권한 집합:** 프로필에 정의된 것 위에 추가 권한 제공.

권한 집합은 오브젝트 수준 접근을 재정의할 수 있지만 추가 접근만 부여(프로필이 이미 부여한 접근을 제한할 수 없음).

**제한:** 최대 1,000개 권한 집합 생성. 접근 회수가 아닌 부여만 가능. 사용자당 권한 집합 그룹 최대 10개. 권한 집합 그룹당 최대 100개 권한 집합 추가.

**Permission Set Group:** 여러 권한 집합을 담는 폴더 같은 것. 개별 할당 대신 그룹 전체를 한 번에 할당해 시간 절약·정리.

## Layer 3: 레코드 수준 보안

어떤 개별 레코드를 사용자가 보기·편집·삭제·공유할 수 있는지 결정합니다.

예: Blood Donor 오브젝트의 OWD가 Private이고 프로필 수준에서 Read/Create/Edit를 주면, 사용자는 자신이 만든 레코드만 편집할 수 있고 시스템 관리자가 만든 것은 볼 수 없음. Public Read/Write이면 관리자가 만든 것도 보고 편집 가능.

**핵심 구성 요소:**

1. **프로필·권한 집합:** 오브젝트 기준 접근 정의(특정 레코드 접근은 제어 안 함).
2. **OWD:** 조직 전체 레코드 기준 접근. Private(소유 레코드만), Public Read Only(모두 보기·소유만 편집), Public Read/Write(모두 보기·편집), Controlled by Parent(부모 오브젝트가 결정). OWD가 Private/Read Only이면 소유하지 않은 레코드 접근에 프로필·역할 계층·공유 규칙 등 추가 권한 필요. 프로필이 OWD보다 넓은 접근 제공 가능(예: View All/Modify All).
3. **Role Hierarchy:** 상위 사용자가 하위 사용자 소유 레코드 접근(예: 영업 관리자가 담당자 Opportunity 접근).
4. **Sharing Rules:** OWD에 대한 예외로 특정 사용자·그룹에 추가 접근(Public Group/역할 공유, 기준 기반 공유).
5. **Manual Sharing:** "Full Access"나 "Sharing" 권한이 있으면 특정 레코드를 수동 공유.
6. **Territory Management(선택):** 역할 대신 영역 기반 접근(지리적 분산 영업에 이상적).
7. **Apex Sharing(프로그래밍):** 커스텀 공유 로직을 코드로 정의.

## Sharing Rule

사용자·그룹에 공유 접근을 확장하는 데 사용. 역할·권한 집합으로 접근할 수 없는 레코드에 추가 접근 수준 정의. OWD가 Private/Read Only일 때 특히 유용.

**핵심:** 소유권·기준 기반 동적 공유. 레코드 수준 접근 부여(이미 부여된 접근 제한 불가). Read-Only 또는 Read/Write만 부여(전체 제어 불가).

**유형:**
1. **소유자 기반:** 특정 사용자가 소유한 레코드를 다른 사용자·그룹과 공유. 예: 영업 관리자의 Opportunity를 마케팅팀과 공유.
2. **기준 기반:** 특정 기준(필드 값)을 충족하는 레코드 공유. 예: "Priority = High" Case를 고객 지원팀과 공유.

**모범 사례:** OWD·역할 계층 너머로 접근 확장이 필요할 때만 사용. 단순하게 조직 구조에 맞춤. 정기 검토·감사.
