## 아이콘 시스템

### 왜 prebuild 코드젠인가

lightning-base-components 패키지는 아이콘 SVG를 **1,614개의 개별 `.html` 템플릿 파일**로 보관한다. 이걸 Vite transform 파이프라인이 런타임에 하나씩 변환하면 (특히 클라우드 환경에서) 극도로 느리다. Starter Kit은 빌드 전에 이 HTML들을 **icon set당 1개씩, 총 4개의 단일 JS 파일**로 미리 컴파일(AOT)한다.

`scripts/prebuild-icons.mjs` 헤더 주석 (verbatim):

```js
/**
 * Pre-compiles LWC icon SVG HTML templates into bundled JS modules.
 *
 * Instead of Vite serving 1,614 individual .html files through its transform
 * pipeline at runtime (which is extremely slow in cloud environments), this
 * script compiles them ahead of time into 4 single JS files — one per icon set.
 *
 * Usage: node scripts/prebuild-icons.mjs
 */
```

이 스크립트는 `npm run prebuild-icons`로 직접, 또는 `dev`/`build` 스크립트의 선행 단계로 실행된다 (`package.json`의 `"dev": "node scripts/prebuild-icons.mjs && vite"`). 출력은 `src/build/generated/`에 떨어지며 **수정 금지(do not edit)** 생성물이다.

### 코드젠: ICON_SETS → @lwc/template-compiler

핵심은 `@lwc/template-compiler`의 `compile`로 각 `.html`을 컴파일한 뒤, set별로 묶어 export하는 것이다.

`scripts/prebuild-icons.mjs` 발췌 (verbatim):

```js
import { compile } from '@lwc/template-compiler';
import fs from 'fs';
import path from 'path';

const ICON_SETS = [
    {
        name: 'utility',
        dir: 'node_modules/lightning-base-components/src/lightning/iconSvgTemplatesUtility/buildTemplates/utility',
        output: 'src/build/generated/iconSvgUtility.js',
    },
    {
        name: 'standard',
        dir: 'node_modules/lightning-base-components/src/lightning/iconSvgTemplatesStandard/buildTemplates/standard',
        output: 'src/build/generated/iconSvgStandard.js',
    },
    {
        name: 'doctype',
        dir: 'node_modules/lightning-base-components/src/lightning/iconSvgTemplatesDoctype/buildTemplates/doctype',
        output: 'src/build/generated/iconSvgDoctype.js',
    },
    {
        name: 'action',
        dir: 'node_modules/lightning-base-components/src/lightning/iconSvgTemplatesAction/buildTemplates/action',
        output: 'src/build/generated/iconSvgAction.js',
    },
];
```

각 set의 컴파일 루프 (verbatim):

```js
for (let i = 0; i < htmlFiles.length; i++) {
    const file = htmlFiles[i];
    const filePath = path.join(iconSet.dir, file);
    const html = fs.readFileSync(filePath, 'utf8');
    const baseName = path.basename(file, '.html');
    const exportName = `${iconSet.name}_${baseName}`;

    const result = compile(html, filePath, {});
    ...
    let code = result.code;

    // Strip implicit CSS imports (the icon templates don't have CSS)
    code = code.replace(/import _implicitStylesheets from [^\n]+\n/g, '');
    ...
    // Rename 'tmpl' function and all references to a unique name
    const uniqueName = `tmpl_${i}`;
    ...
}
```

컴파일된 코드는 (1) 암묵적 CSS import 제거, (2) 중복 `lwc` import 제거(파일 상단에 하나만 둠), (3) `tmpl` 함수명을 `tmpl_${i}`로 유니크화, (4) `$fragment` 변수 충돌 회피 처리를 거친 뒤, set별 default export 객체로 묶인다. 출력 파일 첫 줄은 항상 다음으로 시작한다:

```js
// Auto-generated by scripts/prebuild-icons.mjs — do not edit
import { freezeTemplate, parseFragment, registerTemplate, sanitizeAttribute } from 'lwc';
```

실행 종료 시 set별 로그를 찍는다: `✓ ${iconSet.name}: ${htmlFiles.length} icons → ${iconSet.output}`.

### Vite alias 체인: lightning/iconSvgTemplates* → shims → generated

런타임에 `lightning-icon`이 `import lightning/iconSvgTemplatesUtility` 같은 specifier로 템플릿을 요구하면, Vite 플러그인이 이를 **node_modules의 원본 HTML이 아니라** Starter Kit의 사전 컴파일 번들로 리다이렉트한다. 그래야 빌드 중 패키지의 HTML이 컴파일되지 않아 parse5 오류를 피한다.

`vite-plugins/icon-templates.js` 헤더 주석 (verbatim):

```js
/**
 * Vite plugin and config for lightning-base-components icon templates.
 *
 * Redirects all icon template imports (LTR, RTL, and the package's internal
 * ./buildTemplates/templates) to our pre-compiled bundles so the package's HTML
 * in node_modules is never compiled (avoids parse5 errors in build).
 */
```

먼저 가로챌 specifier 목록 — `ICON_TEMPLATE_DIR_NAMES` (12개, verbatim):

```js
const ICON_TEMPLATE_DIR_NAMES = [
  'iconSvgTemplatesStandard',
  'iconSvgTemplatesStandardRtl',
  'iconSvgTemplatesUtility',
  'iconSvgTemplatesUtilityRtl',
  'iconSvgTemplatesDoctype',
  'iconSvgTemplatesDoctypeRtl',
  'iconSvgTemplatesAction',
  'iconSvgTemplatesActionRtl',
  'iconSvgTemplatesCustom',
  'iconSvgTemplatesCustomRtl',
  'iconSvgTemplates',
  'iconSvgTemplatesRtl',
];

/** Paths to exclude from LWC compilation so the package's icon template HTML is never compiled. */
export const iconTemplateExcludeDirs = ICON_TEMPLATE_DIR_NAMES.map((dir) => path.join(lbcRoot, dir));
```

alias 맵 — 12개 specifier 전체 (verbatim):

```js
const srcLightning = path.join(projectRoot, 'src/build/lightning-icon/shims');

/** Alias map: lightning/iconSvgTemplates* specifier -> path to our pre-compiled bundle. */
export const iconTemplateAliases = {
  'lightning/iconSvgTemplatesUtility': path.join(srcLightning, 'iconSvgTemplatesUtility/iconSvgTemplatesUtility.js'),
  'lightning/iconSvgTemplatesStandard': path.join(srcLightning, 'iconSvgTemplatesStandard/iconSvgTemplatesStandard.js'),
  'lightning/iconSvgTemplatesDoctype': path.join(srcLightning, 'iconSvgTemplatesDoctype/iconSvgTemplatesDoctype.js'),
  'lightning/iconSvgTemplatesAction': path.join(srcLightning, 'iconSvgTemplatesAction/iconSvgTemplatesAction.js'),
  'lightning/iconSvgTemplatesStandardRtl': path.join(srcLightning, 'iconSvgTemplatesStandard/iconSvgTemplatesStandard.js'),
  'lightning/iconSvgTemplatesUtilityRtl': path.join(srcLightning, 'iconSvgTemplatesUtility/iconSvgTemplatesUtility.js'),
  'lightning/iconSvgTemplatesDoctypeRtl': path.join(srcLightning, 'iconSvgTemplatesDoctype/iconSvgTemplatesDoctype.js'),
  'lightning/iconSvgTemplatesActionRtl': path.join(srcLightning, 'iconSvgTemplatesAction/iconSvgTemplatesAction.js'),
  'lightning/iconSvgTemplatesCustom': path.join(srcLightning, 'iconSvgTemplatesStandard/iconSvgTemplatesStandard.js'),
  'lightning/iconSvgTemplatesCustomRtl': path.join(srcLightning, 'iconSvgTemplatesStandard/iconSvgTemplatesStandard.js'),
  'lightning/iconSvgTemplates': path.join(srcLightning, 'iconSvgTemplatesStandard/iconSvgTemplatesStandard.js'),
  'lightning/iconSvgTemplatesRtl': path.join(srcLightning, 'iconSvgTemplatesStandard/iconSvgTemplatesStandard.js'),
};
```

이 맵은 LTR·RTL·Custom·기본 12개 specifier를 모두 커버한다. 4개 실체 번들(utility/standard/doctype/action)만 존재하므로, RTL variant는 같은 LTR 번들로, Custom·기본(`iconSvgTemplates`)·RTL 기본은 모두 Standard 번들로 매핑된다. 또한 `iconTemplateExcludeDirs`(위 `ICON_TEMPLATE_DIR_NAMES` 기반)로 패키지의 원본 HTML 디렉터리 12곳을 LWC 컴파일 대상에서 제외한다.

플러그인 본체 — `enforce: 'pre'`로 다른 resolver보다 먼저 동작하며, alias 외에도 패키지 내부의 `./buildTemplates/templates` 상대 import까지 가로챈다 (verbatim):

```js
export function resolveIconTemplatesPlugin() {
  const defaultBundle = iconTemplateAliases['lightning/iconSvgTemplatesStandard'];
  return {
    name: 'resolve-icon-templates',
    enforce: 'pre',
    resolveId(id, importer) {
      const resolved = iconTemplateAliases[id];
      if (resolved) return resolved;
      if (importer && id === './buildTemplates/templates' && importer.includes('lightning-base-components')) {
        for (const [key, bundlePath] of BUNDLE_BY_IMPORTER_KEY) {
          if (importer.includes(key)) return bundlePath;
        }
        return defaultBundle;
      }
      return null;
    },
  };
}
```

### shim 모듈 — 얇은 재export 계층

alias가 가리키는 shim은 생성된 번들을 그대로 재export하는 한 줄짜리 모듈이다. `src/build/lightning-icon/shims/`에는 4개 shim이 있다 (utility / standard / doctype / action).

`src/build/lightning-icon/shims/iconSvgTemplatesUtility/iconSvgTemplatesUtility.js` (verbatim):

```js
// Local override — resolves to pre-compiled bundle instead of 749 individual HTML files
import templates from '../../../generated/iconSvgUtility.js';
export default templates;
```

각 shim 주석에 명시된 개별 HTML 파일 수(= 해당 set의 아이콘 수): **utility 749, standard 632, doctype 46, action 187**.

### `<lightning-icon>` 사용

아이콘은 `lightning-icon`에 `icon-name="set:name"` 형식(예: `standard:account`, `utility:download`, `doctype:pdf`)으로 지정한다. `src/modules/page/iconTest/iconTest.html`에서는 `for:each`로 동적 바인딩한다 (verbatim):

```html
<template for:each={standardIcons} for:item="icon">
    <div key={icon.name} class="icon-item">
        <lightning-icon icon-name={icon.name} size="small"></lightning-icon>
        <span class="icon-item__label">{icon.label}</span>
    </div>
</template>
```

여기서 `icon.name`은 `iconTest.js`에서 `standard:${name}` 형태로 생성된다 (verbatim 발췌):

```js
const STANDARD_ICONS = [
    'account', 'contact', 'lead', 'opportunity', 'case', 'task', 'event',
    ...
].map(name => ({ name: `standard:${name}`, label: name }));
```

따라서 정적으로 쓰면 `<lightning-icon icon-name="standard:account" size="small"></lightning-icon>` 형태가 된다. `lightning-button`/`lightning-button-icon`도 동일하게 `icon-name="utility:new_window"` 같은 형식을 받는다.

> README "Icons": prebuild는 `npm run dev` 또는 `npm run build`로 실행되어 `src/build/generated/`를 갱신한다. Vite가 `lightning/iconSvgTemplates*`를 `src/build/lightning-icon/shims/` 아래 shim으로 해석하며, **그 폴더에 무관한 코드를 추가하지 말 것**.

## 모달

### LightningModal 확장 패턴

모달은 raw SLDS 마크업이 아니라 `lightning/modal`의 `LightningModal`을 **확장**해 만든다. 본문은 `lightning-modal-header` / `lightning-modal-body` / `lightning-modal-footer` 슬롯으로 구성하고, 닫을 때 `this.close(value)`로 결과를 반환한다.

`src/modules/ui/demoModal/demoModal.js` (verbatim):

```js
import LightningModal from 'lightning/modal';

/**
 * Demo modal component that extends LightningModal.
 * Opened imperatively via DemoModal.open({ label: '...', size: 'medium' }).
 * Use for demonstrating modal header, body, and footer with Lightning Base Components.
 */
export default class DemoModal extends LightningModal {
    handleCancel() {
        this.close();
    }

    handleConfirm() {
        this.close('confirmed');
    }
}
```

`close()`는 결과 없이 닫고, `close('confirmed')`처럼 인자를 주면 그 값이 `.open()`의 Promise 결과가 된다.

`src/modules/ui/demoModal/demoModal.html` (verbatim):

```html
<template>
    <lightning-modal-header label="Demo Modal">
        This is a demo modal built with Lightning Base Components.
    </lightning-modal-header>
    <lightning-modal-body>
        <p class="slds-p-around_small">
            Click <strong>Confirm</strong> to close with a result, or <strong>Cancel</strong> to dismiss.
        </p>
    </lightning-modal-body>
    <lightning-modal-footer>
        <lightning-button
            label="Cancel"
            variant="neutral"
            onclick={handleCancel}
            title="Cancel">
        </lightning-button>
        <lightning-button
            label="Confirm"
            variant="brand"
            onclick={handleConfirm}
            title="Confirm"
            class="slds-m-left_x-small">
        </lightning-button>
    </lightning-modal-footer>
</template>
```

### 명령형 오픈 — `.open({size, label, ...props})`

모달은 템플릿에 마크업으로 두지 않고 `MyModal.open({ ... })`로 명령형 호출한다. 반환값은 Promise이며, 모달이 `close(value)`로 닫힐 때 그 value로 resolve된다.

단순 오픈 — `src/modules/page/home/home.js` (verbatim):

```js
import DemoModal from 'ui/demoModal';
...
    handleOpenModal() {
        DemoModal.open({
            size: 'medium',
            label: 'Demo Modal',
        });
    }
```

### 커스텀 @api prop 전달 + 결과 await

`.open()`에 넘기는 객체는 `size`/`label` 같은 LightningModal 표준 옵션뿐 아니라 **모달이 `@api`로 선언한 커스텀 prop**도 함께 받는다. 호출부에서 `await`하면 사용자가 입력한 결과를 받아 후처리할 수 있다.

`src/modules/page/builder/builder.js` (verbatim 발췌):

```js
import BuilderSettingsModal from 'ui/builderSettingsModal';
...
    async handleSettings() {
        const result = await BuilderSettingsModal.open({
            size: 'small',
            label: 'Page Settings',
            pageName: this.pageName,
        });
        if (result === undefined) return;
        this.pageName = result || DEFAULT_PAGE_NAME;
        try {
            localStorage.setItem(STORAGE_KEY_PAGE_NAME, this.pageName);
        } catch {
            /* empty */
        }
    }
```

여기서 `pageName`은 모달 클래스의 `@api` prop이며, 취소 시 `result === undefined`로 분기한다.

모달 측 — `src/modules/ui/builderSettingsModal/builderSettingsModal.js` (verbatim):

```js
import { api } from 'lwc';
import LightningModal from 'lightning/modal';

export default class BuilderSettingsModal extends LightningModal {
    @api pageName = '';

    _value = '';

    connectedCallback() {
        this._value = this.pageName;
    }

    get inputValue() {
        return this._value;
    }

    handleNameChange(event) {
        this._value = event.detail.value;
    }

    handleCancel() {
        this.close();
    }

    handleSave() {
        this.close((this._value || '').trim());
    }
}
```

### raw slds-modal 금지

README "Using this as a template" / AGENTS.md "Modals" 규칙 (verbatim 요지):

> **Modals:** For modal dialogs, extend `LightningModal` from `lightning/modal` and use the in-repo example as your starting point: `src/modules/ui/demoModal/`. ### 알림(Toast) 패턴

모달과 마찬가지로 일시적 알림도 raw 마크업이 아니라 base 모듈을 명령형으로 호출한다. `lightning/toast`를 import한 뒤 `Toast.show({ label, message, variant, mode })`로 띄운다.

`src/modules/page/home/home.js` (verbatim — import + 모든 `Toast.show` 호출):

```js
import Toast from 'lightning/toast';
...
    handleButtonClick() {
        Toast.show({ label: 'Button clicked', message: 'Base button was clicked.', variant: 'info', mode: 'dismissible' });
    }

    handleSuccessButton() {
        Toast.show({ label: 'Success', message: 'Success button was clicked.', variant: 'success', mode: 'dismissible' });
    }

    handleNeutralButton() {
        Toast.show({ label: 'Neutral', message: 'Neutral button was clicked.', variant: 'info', mode: 'dismissible' });
    }

    handleBrandButton() {
        Toast.show({ label: 'Brand', message: 'Brand button was clicked.', variant: 'info', mode: 'dismissible' });
    }

    handleDestructiveButton() {
        Toast.show({ label: 'Destructive', message: 'Destructive button was clicked.', variant: 'error', mode: 'dismissible' });
    }
```

- `variant`: 이 repo에서 쓰인 값은 `info` / `success` / `error` 세 가지. (`mode`는 전부 `dismissible`.)
- `label`은 토스트 제목, `message`는 본문이다.

> ⚠️ **번들 주의:** `lightning/toast`, `lightning/toastContainer`, `lightning/showToastEvent`는 `vite.config.js`의 `optimizeDeps.exclude`에 등록되어 Vite의 의존성 사전 번들링에서 제외된다 (`lightning/modal` 등 다른 오버레이 모듈과 함께). 즉 이 모듈들은 LWC 런타임이 직접 해석하도록 두며 esbuild pre-bundle 대상에서 빠진다.

## 폼

### Lightning Base Component 폼 요소 전수

AGENTS.md "Forms" 규칙 (verbatim):

> Use Lightning Base Component form elements (`lightning-input`, `lightning-combobox`, `lightning-radio-group`, `lightning-textarea`, `lightning-select`) for all form inputs. Do not use raw `<input>`, `<select>`, or `<textarea>`. Use correct input `type` (e.g., `type="email"`) and `read-only` mode for data display.

`src/modules/page/home/`에서 실제로 사용되는 폼 요소 (repo 내 예시 있음):

| 요소 | 용도 | home에서의 type/속성 |
|---|---|---|
| `lightning-input` (text) | 텍스트 입력 | `value` + `onchange` |
| `lightning-input type="email"` | 이메일 | placeholder만 (바인딩 없음) |
| `lightning-input type="tel"` | 전화번호 | placeholder만 |
| `lightning-input type="date"` | 날짜 선택 | `value={dateValue}` |
| `lightning-input type="toggle"` | 토글 스위치 | `checked={toggleValue}` |
| `lightning-checkbox-group` | 다중 선택 | `options` + `value`(배열) |
| `lightning-radio-group` | 단일 선택 | `options` + `value` |
| `lightning-combobox` | 드롭다운 | `options` + `value` |
| `lightning-slider` | 슬라이더 | `value` + `min`/`max`/`step` |
| `lightning-textarea` | 여러 줄 텍스트 | `value` + `onchange` |

```html
</lightning-input>
```

> ⚠️ **`lightning-select` 주의:** AGENTS.md "Forms" 목록에는 `lightning-select`가 권장 요소로 들어 있으나, **이 repo에는 `lightning-select` 사용 예시가 없다**(드롭다운은 `lightning-combobox`로 구현). `lightning-select`를 쓰려면 공식 컴포넌트 라이브러리 문서를 따로 참조해야 한다.

### event.detail.value vs event.detail.checked

핸들러에서 변경값을 읽을 때, 대부분의 요소는 `event.detail.value`를, **토글/체크 형태는 `event.detail.checked`**를 쓴다.

`src/modules/page/home/home.js` (verbatim 발췌):

```js
handleInputChange(event) {
    this.inputValue = event.detail.value;
}

handleCheckboxChange(event) {
    this.checkboxGroupValues = event.detail.value;   // 다중 선택값은 value(배열)
}

handleSliderChange(event) {
    this.sliderValue = event.detail.value;
}

handleToggleChange(event) {
    this.toggleValue = event.detail.checked;          // 토글은 checked(boolean)
}
```

`checkbox-group`은 선택된 값들의 **배열**을 `event.detail.value`로 주는 반면, `type="toggle"`은 단일 boolean을 `event.detail.checked`로 준다 — 둘을 혼동하지 말 것.

### read-only 데이터 표시 패턴

데이터를 **표시 전용**으로 보여줄 때도 raw HTML 대신 base component에 `read-only`를 붙인다. `src/modules/page/contactDetail/contactDetail.html`은 필드 타입에 따라 `lwc:if`로 `lightning-textarea`와 `lightning-input`을 분기한다 (verbatim):

```html
<template for:each={cardFields} for:item="field">
    <lightning-textarea
        lwc:if={field.isTextarea}
        key={field.key}
        class={field.cssClass}
        label={field.label}
        value={field.value}
        read-only>
    </lightning-textarea>
    <lightning-input
        lwc:else
        key={field.key}
        label={field.label}
        value={field.value}
        type={field.type}
        read-only>
    </lightning-input>
</template>
```

긴 텍스트(`isTextarea`)는 `lightning-textarea read-only`, 그 외(`lwc:else`)는 `lightning-input read-only`로 동일 데이터를 표시 전용 렌더한다. contactDetail은 또한 데이터 없을 때를 `<template lwc:if={hasContact}>` / `<template lwc:else>`로 분기해 "Contact not found" 일러스트를 띄운다.

## 배포 (GitHub Pages)

### `npm run deploy` — 단일 경로

배포 경로는 **`npm run deploy` 하나뿐**이다. 이는 hash 라우팅 production 빌드를 만든 뒤 `dist/`를 `origin`의 `gh-pages` 브랜치에 push한다. 이 repo는 Pages에 GitHub Actions를 쓰지 않는다.

`package.json` scripts (verbatim 발췌):

```json
"prebuild-icons": "node scripts/prebuild-icons.mjs",
"build": "node scripts/prebuild-icons.mjs && vite build",
"build:gh-pages": "node scripts/prebuild-icons.mjs && vite build --mode gh-pages",
"deploy": "npm run build:gh-pages && gh-pages -d dist --nojekyll",
```

즉 `deploy` = `build:gh-pages`(prebuild-icons → `vite build --mode gh-pages`) 실행 후 `gh-pages -d dist --nojekyll`. `--nojekyll`은 `_`로 시작하는 자산이 Jekyll에 의해 무시되지 않도록 `.nojekyll` 파일을 둔다.

### hash 라우팅 — `.env.gh-pages`

기본 `npm run dev` / `npm run build`는 일반 path URL(`/settings`)을 쓴다. 정적 호스팅인 GitHub Pages에서는 새로고침·딥링크가 404 나므로, gh-pages 모드만 **hash URL**(`…/your-repo/#/settings`)로 전환한다. 이는 `--mode gh-pages`가 읽는 환경 파일로 제어된다.

`.env.gh-pages` (verbatim):

```
# Used only when building with: vite build --mode gh-pages (npm run build:gh-pages / deploy)
VITE_ROUTER_MODE=hash
```

> README "Routing" 경고: hash 없는 path 북마크(`…/your-repo/settings`)는 Pages에서 여전히 404가 난다.

### 1회성 설정 (one-time setup)

README "GitHub Pages" (verbatim):

> **One-time setup**
> 1. Configure Git so you can **`git push` to `origin`**.
> 2. Run **`npm run deploy`** once so branch **`gh-pages`** exists on the remote.
> 3. On GitHub: **Settings → Pages** → **Build and deployment** → **Deploy from a branch** → Branch **`gh-pages`**, folder **`/` (root)** → Save.
>
> **Ongoing:** run **`npm run deploy`** whenever you want to publish a new build.

라이브 URL은 GitHub 게시 후 **Settings → Pages**에 표시되며(호스트명은 플랜·조직 설정에 따라 다름), path 라우팅을 로컬에서 검증하려면 `npm run build` 후 `npm run preview`, gh-pages 번들을 미리 보려면 `npm run build:gh-pages` 후 `npm run preview`를 쓴다.

### 다른 remote / URL로 push

기본 push 대상은 `origin`이지만 `gh-pages` CLI는 대체 타깃을 받는다 (verbatim):

> **Another remote or URL:** `npx gh-pages -d dist -o <remote-name>` or `npx gh-pages -d dist -r https://github.com/org/repo.git`.

`-o <remote-name>`는 다른 remote 이름, `-r <url>`은 임의의 repo URL로 직접 push한다.

## SLDS Agent Skills & 도구

### afv-library 스킬 동기화 — sync-afv-skills.mjs

UI 작업용 SLDS 스킬은 `.agent/skills/` 아래에 둔다. 그중 `afv-library/` 하위는 `forcedotcom/afv-library` repo의 `develop` 브랜치에서 **`npm install` 시(postinstall)** 복사되며 gitignore된다. 수동 갱신은 `npm run skills:sync`.

`scripts/sync-afv-skills.mjs` 핵심 (verbatim 발췌):

```js
const DEST_BASE = path.join(REPO_ROOT, '.agent', 'skills', 'afv-library');

const REPO_URL = 'https://github.com/forcedotcom/afv-library.git';
const BRANCH = 'develop';
const SKILL_NAMES = [
    'applying-slds',
    'uplifting-components-to-slds2',
    'validating-slds',
];
...
runGit(['clone', '--depth', '1', '--branch', BRANCH, REPO_URL, cloneDir]);
...
for (const name of SKILL_NAMES) {
    const src = path.join(skillsRoot, name);
    ...
    const dest = path.join(DEST_BASE, name);
    fs.rmSync(dest, { recursive: true, force: true });
    fs.cpSync(src, dest, { recursive: true });
}
```

`git`을 `--depth 1`로 얕게 clone해 임시 디렉터리에 받은 뒤 `skills/<name>` 3개 폴더를 `.agent/skills/afv-library/`로 복사하고, 끝나면 임시 디렉터리를 정리한다(`finally`). 요구사항: PATH의 git + GitHub 네트워크 접근.

### 5개 스킬 테이블

`.agent/skills/`에는 afv-library에서 동기화되는 3개 + repo에 직접 포함(shipped)되는 2개, 총 5개 스킬이 있다. AGENTS.md "SLDS Agent Skills" 테이블 (verbatim):

| Skill | `SKILL.md` | When to use |
|-------|------------|-------------|
| applying-slds | `.agent/skills/afv-library/applying-slds/SKILL.md` | Default for SLDS-backed UI: blueprints, hooks, utilities, icons, LBC choice. |
| uplifting-components-to-slds2 | `.agent/skills/afv-library/uplifting-components-to-slds2/SKILL.md` | Migration and fixes from SLDS 1 to 2; linter violations and hook/token replacements. |
| validating-slds | `.agent/skills/afv-library/validating-slds/SKILL.md` | Compliance audit or scored quality report, not for implementing or fixing UI. |
| repo-setup | `.agent/skills/repo-setup/SKILL.md` | Set up a GitHub repo: detects host from origin remote, prerequisites, repo creation, initial push. Use when the user mentions saving or backing up their work. |
| first-time-deploy | `.agent/skills/first-time-deploy/SKILL.md` | Publish to GitHub Pages. Repeat deploys: just `npm run deploy`. First time: runs repo-setup, then deploys and configures Pages. Use when the user asks about deploying or sharing a link with a PM, stakeholder, etc. |

- 앞 3개(`applying-slds`/`uplifting-components-to-slds2`/`validating-slds`)는 afv-library `develop`에서 동기화 — `afv-library/` 하위 경로.
- 뒤 2개(`repo-setup`/`first-time-deploy`)는 이 프로젝트에 직접 포함 — `.agent/skills/<skill-id>/` 직속.
- UI 작업(마크업·CSS·레이아웃·아이콘·LBC vs 블루프린트) 시 **`applying-slds/SKILL.md`를 먼저 읽고 따른다** — SLDS를 기억으로 즉흥 작성 금지.

### SLDS Linter

`.html`/`.css`를 변경하면 작업 완료 전 변경한 각 파일에 SLDS Linter를 돌린다. AGENTS.md "SLDS linter" (verbatim):

```bash
npx @salesforce-ux/slds-linter@latest lint <path-to-changed-file>
```

> 보고된 이슈는 가능한 한 수정하고, 고칠 수 없으면 그 사실을 간단히 밝힌다.

### Salesforce DX MCP

`mcp.json`은 AI 보조 개발용 Salesforce DX MCP 서버를 자동 구성한다. MCP를 지원하는 에디터(Claude Code, Cursor, Copilot 등)가 자동 인식하며 별도 설정이 필요 없다 — `npx`로 on-demand 실행된다.

`mcp.json` (verbatim):

```json
{
  "mcpServers": {
    "SalesforceDX": {
      "type": "stdio",
      "command": "npx",
      "args": [ "-y", "@salesforce/mcp@latest", 
                "--orgs", "ALLOW_ALL_ORGS",
                "--toolsets", "code-analysis,lwc-experts",
                "--tools", "guide_design_general,guide_figma_to_lwc_conversion",
                "--allow-non-ga-tools"]
    }
  }
}
```

AGENTS.md "LWC troubleshooting": Salesforce DX MCP는 **LWC 프레임워크·플랫폼 한정 이슈**(`@api`, `@wire`, lifecycle, events, org-only 동작)에만 선택적으로 사용한다.
