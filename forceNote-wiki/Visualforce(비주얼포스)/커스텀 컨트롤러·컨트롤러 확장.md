# 커스텀 컨트롤러 · 컨트롤러 확장 (Visualforce)

> Visualforce는 Salesforce Classic 시대의 UI 프레임워크로, 신규 개발은 Lightning Web Components를 권장한다. 단 버튼/탭 오버라이드·VF 대시보드 컴포넌트 등 일부 기능은 여전히 VF에 의존하며, 본 가이드 v67.0 Summer '26은 현행 유지보수 버전이다.

> 표준 컨트롤러로 부족할 때 Apex로 페이지 로직을 직접 구현(custom controller)하거나 표준/커스텀 컨트롤러를 확장(controller extension)하는 방법 — 생성자 규약, action/getter/setter, 리스트 컨트롤러, 실행 순서, 보안, read-only mode, transient, 테스트, 종합 예제까지 전수.

---

## 1. 커스텀 컨트롤러 vs 컨트롤러 확장

표준 컨트롤러는 표준 페이지와 동일한 로직을 포함하므로 대부분의 필요 기능을 제공한다. 다음의 경우 Apex로 custom controller 또는 controller extension을 작성한다.

- 기존 기능 오버라이드
- 앱 네비게이션 커스터마이즈
- callout / Web service 사용
- 페이지 정보 접근 방식을 더 세밀하게 제어

| 유형 | 정의 | 사용 시점 |
|---|---|---|
| **Custom controller** | 표준 컨트롤러를 활용하지 않고 페이지의 모든 로직을 구현하는 Apex 클래스 | 페이지를 **전적으로 system mode**로 실행하고 싶을 때 — 현재 사용자의 권한·필드수준보안(FLS)을 강제하지 않음 |
| **Controller extension** | 표준 또는 커스텀 컨트롤러의 기능을 확장하는 Apex 클래스 | ① 표준 컨트롤러의 빌트인 기능을 활용하되 edit/view/save/delete 등 하나 이상의 action을 오버라이드할 때 ② 새 action을 추가할 때 ③ 사용자 권한을 존중하는 VF 페이지를 만들고 싶을 때 |

controller extension 클래스 자체는 system mode로 실행되지만, **표준 컨트롤러를 확장하면 그 표준 컨트롤러의 로직은 system mode가 아니라 user mode로 실행**되어 현재 사용자의 권한·FLS·sharing rule이 적용된다.

### system mode caveat 와 `with sharing`

> **Note:** Custom controller와 controller extension 클래스는 system mode로 실행되어 user permissions와 FLS를 무시한다. 그러나 클래스 정의에 `with sharing` 키워드를 써서 사용자의 조직 전체 기본값(OWD)·역할 계층·sharing rule을 존중할지 선택할 수 있다.

이 caveat는 §2(custom controller)·§3(controller extension)에도 동일하게 반복 적용된다. `with sharing` / `without sharing` / `inherited sharing` 키워드의 메커니즘 자체는 [[Apex 언어 기초 — 제어 흐름과 클래스]] 참조.

## 2. 커스텀 컨트롤러 만들기 (Build a Custom Controller)

커스텀 컨트롤러는 외부 top-level 클래스에 대해 **기본 무인자(no-argument) 생성자**를 사용하는 Apex 클래스다.

**생성 절차 (Setup):**

1. Setup에서 Quick Find에 `Apex Classes` 입력 → Apex Classes 선택.
2. New 클릭.
3. Version Settings로 Apex·API 버전 지정(관리형 패키지 설치 시 각 패키지 버전도). 기본값 권장.
4. 클래스 에디터에 Apex 코드 입력. 단일 클래스는 최대 100만 자(주석·테스트 메서드·`@isTest` 클래스 제외).
5. Save(또는 Quick Save). 저장 전 컴파일 성공 필수.

### 예제 1 — 단순 커스텀 컨트롤러

```apex
public class MyController {
    private final Account account;
    public MyController() {
        account = [SELECT Id, Name, Site FROM Account
            WHERE Id = :ApexPages.currentPage().getParameters().get('id')];
    }
    public Account getAccount() {
        return account;
    }
    public PageReference save() {
        update account;
        return null;
    }
}
```

```html
<apex:page controller="MyController" tabStyle="Account">
    <apex:form>
        <apex:pageBlock title="Congratulations {!$User.FirstName}">
            You belong to Account Name: <apex:inputField value="{!account.name}"/>
            <apex:commandButton action="{!save}" value="save"/>
        </apex:pageBlock>
    </apex:form>
</apex:page>
```

커스텀 컨트롤러는 `<apex:page>`의 `controller` 속성으로 연결한다. 메서드는 `{! }` 표기로 참조 — `getAccount`는 `<apex:inputField>`의 value가, `save`는 `<apex:commandButton>`의 action이 참조한다.

> **Note:** 다른 Apex 클래스처럼 모든 custom controller는 system mode로 실행되어 현재 사용자 자격증명을 쓰지 않고 권한·FLS를 적용하지 않는다. `with sharing` 키워드로 OWD·역할 계층·sharing rule 존중 여부를 선택할 수 있다.

### 예제 2 — 신규 레코드 생성용 `NewAndExistingController`

URL의 `id` 파라미터 유무로 신규/기존 레코드를 분기하고, 저장 후 표준 view 페이지로 네비게이트한다.

```apex
public class NewAndExistingController {
    public Account account { get; private set; }
    public NewAndExistingController() {
        Id id = ApexPages.currentPage().getParameters().get('id');
        account = (id == null) ? new Account() :
            [SELECT Name, Phone, Industry FROM Account WHERE Id = :id];
    }
    public PageReference save() {
        try {
            upsert(account);
        } catch(System.DMLException e) {
            ApexPages.addMessages(e);
            return null;
        }
        // After successful Save, navigate to the default view page
        PageReference redirectSuccess = new
            ApexPages.StandardController(Account).view();
        return (redirectSuccess);
    }
}
```

```html
<apex:page controller="NewAndExistingController" tabstyle="Account">
    <apex:form>
        <apex:pageBlock mode="edit">
            <apex:pageMessages/>
            <apex:pageBlockSection>
                <apex:inputField value="{!account.name}"/>
                <apex:inputField value="{!account.phone}"/>
                <apex:inputField value="{!account.industry}"/>
            </apex:pageBlockSection>
            <apex:pageBlockButtons location="bottom">
                <apex:commandButton value="Save" action="{!save}"/>
            </apex:pageBlockButtons>
        </apex:pageBlock>
    </apex:form>
</apex:page>
```

## 3. 컨트롤러 확장 만들기 (Building a Controller Extension)

controller extension은 **타입 `ApexPages.StandardController` 또는 `CustomControllerName` 단일 인자를 받는 생성자**를 포함하는 Apex 클래스다. `CustomControllerName`은 확장 대상 커스텀 컨트롤러명이다.

```apex
public class myControllerExtension {
    private final Account acct;
    // The extension constructor initializes the private member
    // variable acct by using the getRecord method from the standard
    // controller.
    public myControllerExtension(ApexPages.StandardController stdController) {
        this.acct = (Account)stdController.getRecord();
    }
    public String getGreeting() {
        return 'Hello ' + acct.name + ' (' + acct.id + ')';
    }
}
```

```html
<apex:page standardController="Account" extensions="myControllerExtension">
    {!greeting} <p/>
    <apex:form>
        <apex:inputField value="{!account.name}"/> <p/>
        <apex:commandButton value="Save" action="{!save}"/>
    </apex:form>
</apex:page>
```

extension은 `<apex:page>`의 `extensions` 속성으로 연결한다. `{!greeting}`은 extension의 `getGreeting`을 참조한다. Account 표준 컨트롤러와 함께 동작하므로 표준 컨트롤러 메서드도 사용 가능하다 — `<apex:inputField>` value는 표준 기능으로 account name을 조회하고, `<apex:commandButton>`은 표준 account save 메서드를 참조한다.

### 다중 확장 + 메서드 오버라이드

단일 페이지에 쉼표 구분 리스트로 여러 extension을 정의하면 동명 메서드 오버라이드가 허용된다.

```html
<apex:page standardController="Account"
    extensions="ExtOne,ExtTwo" showHeader="false">
    <apex:outputText value="{!foo}" />
</apex:page>
```

```apex
public class ExtOne {
    public ExtOne(ApexPages.StandardController acon) { }
    public String getFoo() {
        return 'foo-One';
    }
}
public class ExtTwo {
    public ExtTwo(ApexPages.StandardController acon) { }
    public String getFoo() {
        return 'foo-Two';
    }
}
```

`<apex:outputText>`는 **foo-One**으로 렌더된다. 오버라이드는 쉼표 리스트의 **가장 왼쪽(leftmost)** = 첫 번째 extension에 정의된 메서드가 결정한다. 따라서 ExtOne의 getFoo가 ExtTwo의 것을 오버라이드한다.

> **Note:** controller extension은 system mode로 실행되어 자격증명을 쓰지 않고 권한·FLS를 적용하지 않는다. 단 표준 컨트롤러를 확장하면 그 표준 컨트롤러 로직은 system mode가 아닌 **user mode**로 실행되어 권한·FLS·sharing rule이 적용된다. `with sharing`으로 OWD·역할 계층·sharing rule 존중 여부를 선택할 수 있다.

## 4. 커스텀 리스트 컨트롤러 (Building a Custom List Controller)

커스텀 리스트 컨트롤러는 표준 리스트 컨트롤러와 유사하나, 레코드 집합을 표시·처리하는 Apex 로직을 직접 정의한다.

### 예제 1 — SOQL 기반 `opportunityList2Con`

```apex
public class opportunityList2Con {
    // ApexPages.StandardSetController must be instantiated
    // for standard list controllers
    public ApexPages.StandardSetController setCon {
        get {
            if(setCon == null) {
                setCon = new ApexPages.StandardSetController(Database.getQueryLocator(
                    [SELECT Name, CloseDate FROM Opportunity]));
            }
            return setCon;
        }
        set;
    }
    // Initialize setCon and return a list of records
    public List<Opportunity> getOpportunities() {
        return (List<Opportunity>) setCon.getRecords();
    }
}
```

> **Note:** `getRecords()`가 반환하는 sObject 리스트는 **immutable**이다. 예를 들어 `clear()`를 호출할 수 없다. 리스트 내 sObject는 변경 가능하나 리스트 자체에 항목을 추가/제거할 수는 없다.

```html
<apex:page controller="opportunityList2Con">
    <apex:pageBlock>
        <apex:pageBlockTable value="{!opportunities}" var="o">
            <apex:column value="{!o.Name}"/>
            <apex:column value="{!o.CloseDate}"/>
        </apex:pageBlockTable>
    </apex:pageBlock>
</apex:page>
```

### 예제 2 — anti/semi-join SOQL + 표준 리스트 컨트롤러 확장 `AccountPagination`

```apex
public with sharing class AccountPagination {
    private final Account acct;
    // The constructor passes in the standard controller defined
    // in the markup below
    public AccountPagination(ApexPages.StandardSetController controller) {
        this.acct = (Account)controller.getRecord();
    }
    public ApexPages.StandardSetController accountRecords {
        get {
            if(accountRecords == null) {
                accountRecords = new ApexPages.StandardSetController(
                    Database.getQueryLocator([SELECT Name FROM Account WHERE Id NOT IN
                    (SELECT AccountId FROM Opportunity WHERE IsClosed = true)]));
            }
            return accountRecords;
        }
        private set;
    }
    public List<Account> getAccountPagination() {
        return (List<Account>) accountRecords.getRecords();
    }
}
```

```html
<apex:page standardController="Account" recordSetVar="accounts"
    extensions="AccountPagination">
    <apex:pageBlock title="Viewing Accounts">
        <apex:form id="theForm">
            <apex:pageBlockSection >
                <apex:dataList value="{!accountPagination}" var="acct" type="1">
                    {!acct.name}
                </apex:dataList>
            </apex:pageBlockSection>
            <apex:panelGrid columns="2">
                <apex:commandLink action="{!previous}">Previous</apex:commandlink>
                <apex:commandLink action="{!next}">Next</apex:commandlink>
            </apex:panelGrid>
        </apex:form>
    </apex:pageBlock>
</apex:page>
```

이 페이지는 표준 리스트 컨트롤러의 action(`previous`/`next`)을 섞어 쓰지만, 커스텀 리스트 컨트롤러가 반환하는 레코드 위를 반복(iterating)하는 데 의존한다.

## 5. 컨트롤러 메서드 (Action / Getter / Setter)

VF 마크업이 사용할 수 있는 컨트롤러 확장/커스텀 컨트롤러 메서드 유형은 **Action**, **Getter**, **Setter** 세 가지다.

### Action 메서드

페이지 이벤트(버튼 클릭, 영역 hover 등) 발생 시 로직·네비게이션을 수행한다. 다음 태그의 `action` 파라미터에서 `{! }` 표기로 호출한다.

| 태그 | 동작 |
|---|---|
| `<apex:commandButton>` | action을 호출하는 버튼 생성 |
| `<apex:commandLink>` | action을 호출하는 링크 생성 |
| `<apex:actionPoller>` | 주기적으로 action 호출 |
| `<apex:actionSupport>` | 다른 명명 컴포넌트의 이벤트("onclick","onmouseover" 등)가 action 호출 |
| `<apex:actionFunction>` | action을 호출하는 새 JavaScript 함수 정의 |
| `<apex:page>` | 페이지 로드 시 action 호출 |

### Getter 메서드

컨트롤러에서 값을 반환한다. 컨트롤러가 계산하여 페이지에 표시되는 모든 값(Boolean 변수 포함)은 대응 getter 메서드가 있어야 한다. getter는 항상 `getVariable` 형식으로 명명한다.

> **Important:** getter 메서드는 **idempotent**(부작용 없음)가 best practice다. 변수 증가, 로그 기록, 신규 레코드 추가 등을 하지 말 것. VF는 getter 호출 순서·횟수를 정의하지 않는다 — 한 번 호출되든 여러 번이든 동일 결과를 내도록 설계한다.

### Setter 메서드

페이지 마크업의 사용자 입력값을 컨트롤러로 전달한다. 컨트롤러의 setter는 **모든 action 메서드 전에 자동 실행**된다.

```html
<apex:page controller="theController">
    <apex:form>
        <apex:pageBlock mode="edit" id="block">
            <apex:pageBlockSection>
                <apex:pageBlockSectionItem>
                    <apex:outputLabel for="searchText">Search Text</apex:outputLabel>
                    <apex:panelGroup>
                        <apex:inputText id="searchText" value="{!searchText}"/>
                        <apex:commandButton value="Go!" action="{!doSearch}"
                            rerender="block" status="status"/>
                    </apex:panelGroup>
                </apex:pageBlockSectionItem>
            </apex:pageBlockSection>
            <apex:actionStatus id="status" startText="requesting..."/>
            <apex:pageBlockSection title="Results" id="results" columns="1">
                <apex:pageBlockTable value="{!results}" var="l"
                    rendered="{!NOT(ISNULL(results))}">
                    <apex:column value="{!l.name}"/>
                    <apex:column value="{!l.email}"/>
                    <apex:column value="{!l.phone}"/>
                </apex:pageBlockTable>
            </apex:pageBlockSection>
        </apex:pageBlock>
    </apex:form>
</apex:page>
```

```apex
public class theController {
    String searchText;
    List<Lead> results;
    public String getSearchText() {
        return searchText;
    }
    public void setSearchText(String s) {
        searchText = s;
    }
    public List<Lead> getResults() {
        return results;
    }
    public PageReference doSearch() {
        results = (List<Lead>)[FIND :searchText RETURNING Lead(Name, Email, Phone)][0];
        return null;
    }
}
```

getter는 컨트롤러 값 접근에 항상 필요하나, setter는 항상 필요하진 않다. VF 컴포넌트가 컨트롤러에 저장된 sObject에 바인딩되면, 대응 action 메서드가 저장/갱신하는 한 사용자 변경 시 sObject 필드가 자동 설정된다. setter는 항상 `setVariable` 형식으로 명명한다.

> **Important:** setter 메서드도 idempotent가 best practice다(부작용 없음). 변수 증가·로그·신규 레코드 추가 금지. 호출 순서·횟수가 미정의이므로 동일 결과를 내도록 설계한다.

### 메서드 실행 순서에 의존하지 말 것 (conVsBad / conVsGood)

Apex 메서드·변수는 보장된 순서로 인스턴스화되지 않는다. 따라서 컨트롤러/확장 클래스가 다른 메서드의 실행에 의존하지 말고 그 메서드를 직접 호출한다. 특히 변수 설정·DB 데이터 접근에 적용된다.

**나쁜 예 `conVsBad`** — `getContactMethod1`은 항상 정답을 반환(변수 `c` 존재를 가정 안 함)하나, `getContactMethod2`는 `c`가 아직 설정 안 됐으면 매번 정답이 아니다.

```apex
public class conVsBad {
    Contact c;
    public Contact getContactMethod1() {
        if (c == null) c = [SELECT Id, Name FROM Contact LIMIT 1];
        return c;
    }
    public Contact getContactMethod2() {
        return c;
    }
}
```

**좋은 예 `conVsGood`** — `getContactMethod2`가 `getContactMethod1`을 호출하므로 `c`가 항상 설정되어 반환 시 항상 정답이다.

```apex
public class conVsGood {
    Contact c;
    public Contact getContactMethod1() {
        if(c == null) c = [SELECT Id, Name FROM Contact LIMIT 1];
        return c;
    }
    public Contact getContactMethod2() {
        return getContactMethod1();
    }
}
```

두 컨트롤러를 호출하는 페이지(마크업은 동일, 컨트롤러명만 변경):

```html
<apex:page controller="conVsGood">
    getContactMethod2(): {!contactMethod2.name}<br/>
    getContactMethod1(): {!contactMethod1.name}
</apex:page>
```

```html
<apex:page controller="conVsBad">
    getContactMethod2(): {!contactMethod2.name}<br/>
    getContactMethod1(): {!contactMethod1.name}
</apex:page>
```

## 6. 컨트롤러 클래스 보안 (Controller Class Security)

다른 Apex 클래스처럼, 사용자 프로필 기반으로 custom controller/controller extension의 메서드 실행 가능 여부를 지정할 수 있다.

> **Note:** 관리형 패키지 설치 시, 패키지 내 Apex 클래스 중 `global`로 선언된 클래스 또는 `webService` 메서드를 포함한 클래스에 대해서만 보안 설정이 가능하다.

- **Author Apex** 권한 보유 사용자는 개별 클래스 보안 설정과 무관하게 조직 내 모든 Apex 클래스에 접근한다.
- 권한은 **top level에서만** 검사된다. 예: 클래스 A가 클래스 B를 호출하고, 사용자 X가 A 접근 가능·B 불가 프로필이면 → X는 A를 통해서만 B 코드를 실행할 수 있고 B를 직접 호출할 수 없다. 마찬가지로 VF 페이지가 연결 컨트롤러를 가진 custom component를 쓰면 보안은 페이지에 연결된 컨트롤러만 검사한다 — custom component의 컨트롤러는 권한과 무관하게 실행된다.
- 보안 설정 위치: 클래스 목록 페이지("Set Apex Class Access from the Class List Page") 또는 클래스 상세 페이지("Set Apex Class Access from the Class Detail Page").

## 7. 대용량 데이터 처리 — read-only mode (Working with Large Sets of Data)

VF custom controller·extension은 Apex governor limit이 적용된다(상세 한도는 [[Governor Limits]] 참조). VF iteration 컴포넌트(`<apex:pageBlockTable>`, `<apex:repeat>`)는 반복 컬렉션을 **최대 1,000 항목**으로 제한한다. 데이터 변경 없이 대용량을 표시(커스텀 리포팅·분석 등)하려면 VF의 **read-only mode**를 사용한다 — 1회 요청 쿼리 행 수 제한을 완화하고 반복 컬렉션 항목 수 제한을 증가시킨다.

read-only mode는 전체 페이지 또는 (제한 하에) 개별 컴포넌트/메서드에 지정할 수 있다.

> **Note:** 대용량 데이터 반복은 **전체 페이지에 read-only mode를 지정한 경우에만** 가능하다.

### 전체 페이지 read-only mode

`<apex:page>`의 `readOnly` 속성을 true로 설정한다.

```html
<apex:page controller="SummaryStatsController" readOnly="true">
    <p>Here is a statistic: {!veryLargeSummaryStat}</p>
</apex:page>
```

```apex
public class SummaryStatsController {
    public Integer getVeryLargeSummaryStat() {
        Integer closedOpportunityStats =
            [SELECT COUNT() FROM Opportunity WHERE Opportunity.IsClosed = true];
        return closedOpportunityStats;
    }
}
```

**한도 완화:**

| 항목 | 일반 | read-only mode |
|---|---|---|
| 단일 VF 페이지 요청 쿼리 행 | 최대 50,000행 | 최대 1,000,000행 |
| `<apex:dataTable>`·`<apex:dataList>`·`<apex:repeat>` 등 반복 컬렉션 항목 | 최대 1,000 | 최대 10,000 |

```apex
public class MerchandiseController {
    public List<Merchandise__c> getAllMerchandise() {
        List<Merchandise__c> theMerchandise =
            [SELECT Name, Price__c FROM Merchandise__c LIMIT 10000];
        return(theMerchandise);
    }
}
```

```html
<apex:page controller="MerchandiseController" readOnly="true">
    <p>Here is all the merchandise we have:</p>
    <apex:dataTable value="{!AllMerchandise}" var="product">
        <apex:column>
            <apex:facet name="header">Product</apex:facet>
            <apex:outputText value="{!product.Name}" />
        </apex:column>
        <apex:column>
            <apex:facet name="header">Price</apex:facet>
            <apex:outputText value="{!product.Price__c}" />
        </apex:column>
    </apex:dataTable>
</apex:page>
```

전체 페이지 read-only mode에서는 DML이 불가능하다. 단 form·UI 요소에 영향 주는 getter/setter/action 호출, 추가 read-only 쿼리 등은 가능하다.

### 컨트롤러 메서드 read-only mode (`@ReadOnly`)

페이지가 read-only가 아니어도 컨트롤러 메서드는 (제한 하에) Apex `@ReadOnly` annotation을 사용할 수 있다. `@ReadOnly` 적용 메서드는 자동으로 read-only mode를 활용한다. 단 제한상 VF 컨트롤러의 read-only 메서드는 **반드시 `@RemoteAction` annotation도** 가져야 한다. `@RemoteAction`은 메서드가 다음일 것을 요구한다.

- `global` 또는 `public`
- `static`

`@ReadOnly`로 read-only mode 활성화는 **top level 메서드 호출에 적용**해야 한다. top level 호출에 `@ReadOnly`가 없으면 보조 메서드에 `@ReadOnly`가 있어도 전체 요청에 일반 최대 쿼리 행 제한이 강제된다. 컨트롤러 메서드의 `@ReadOnly`는 VF 표현식 결과로 더 큰 레코드 컬렉션 조회를 허용하나, 반복 컴포넌트의 컬렉션 최대 항목 수는 증가시키지 않는다 — 더 큰 컬렉션을 반복하려면 전체 페이지 read-only mode가 필요하다.

## 8. 작성 시 고려사항 (Considerations)

- `webService` 메서드가 없는 한 custom extension·controller 클래스/메서드는 일반적으로 `public`으로 정의한다. web service 메서드를 포함하면 클래스는 `global`이어야 한다.
- DB에서 데이터 반환 시 set/map/list를 사용하면 DB 왕복이 줄어 효율적이다.
- VF controller extension·custom controller의 Apex governor limit은 anonymous block 또는 WSDL 메서드 한도와 동일하다.
- 민감 데이터를 의도치 않게 노출하지 않도록 주의한다. 권한 강제를 위해 클래스 정의에 `with sharing` 사용을 고려한다. Web service는 프로필에 의해 top-level 진입점으로 보안되지만, 시작된 후엔 system context로 실행되므로 주의한다.
- Apex 메서드·변수는 보장된 순서로 인스턴스화되지 않는다(§5 참조).
- 컨트롤러의 "getxxx" 메서드에서 DML을 사용할 수 없다. 예: getName 메서드에서 insert/update로 객체 생성 불가.
- 컨트롤러의 **생성자 메서드에서 DML을 사용할 수 없다.**
- 컨트롤러의 "getxxx"/"setxxx" 메서드나 생성자에서 [[Future 메서드|`@future` annotation]]을 사용할 수 없다.
- String·Integer 등 primitive Apex 타입은 컴포넌트 컨트롤러로 **값 전달(by value)**된다.
- list·sObject 등 non-primitive 타입은 컴포넌트 컨트롤러로 **참조 전달(by reference)**된다 → 컴포넌트 컨트롤러가 account 이름을 바꾸면 그 변경이 page 컨트롤러에서도 사용 가능하다.
- 동일 컨트롤러·확장을 쓰는 다른 VF 페이지의 출력을 가져오려고 `PageReference.getContent()` / `PageReference.getContentAsPDF()`를 쓰지 말 것 — 디버깅이 어려운 문제를 유발한다. 대신 대상 페이지의 base URL을 전달한다.
  ```apex
  new PageReference(Site.getBaseUrl() +
      '/apex/VisualforcePageName').getContentAsPdf();
  ```
- **person account 사용 조직:**
  - `<apex:inputField>`, `<apex:outputField>`, `<apex:column>`으로 account name 필드 참조 시 쿼리에 `isPersonAccount`를 명시해야 한다.
  - 신규 account 생성 시 name 설정 → business account; lastname 설정 → person account.
  - best practice: 두 유형 모두에 올바르게 렌더되는 커스텀 name formula 필드를 만들어 표준 필드 대신 사용한다.
  - VF 페이지를 AppExchange 패키지에 포함할 계획이면, 컨트롤러/확장에서 person account에만 존재하는 필드를 명시적으로 참조할 수 없다.

## 9. Visualforce 페이지의 실행 순서 (Order of Execution)

페이지 lifecycle을 먼저 이해해야 한다. 두 요청 유형이 있다.

- **get request**: 페이지 최초 요청 — URL 입력, 또는 새 페이지로 이동하는 링크/버튼 클릭 시.
- **postback request**: 사용자 상호작용으로 페이지 갱신이 필요할 때(예: Save 버튼 클릭 → save action 트리거).

> **Note:** VF 페이지 요청의 최대 응답 크기는 **15 MB 미만**이어야 한다.

### Get Request 실행 순서

> (PDF 다이어그램 — 텍스트만) PDF p.113에 get request 시 페이지↔컨트롤러 상호작용 다이어그램이 있으나 pdftotext로 잡히지 않아 본 노트에는 번호 단계 텍스트만 재현한다.

1. 연결된 custom controller/controller extension 클래스의 생성자 메서드를 호출해 컨트롤러 객체를 인스턴스화한다.
2. 페이지에 custom component가 있으면 생성되고, 연결된 컨트롤러/확장 생성자가 실행된다. 표현식으로 custom component 속성을 설정하면 생성자 평가 후 표현식이 평가된다.
3. 페이지가 custom component의 `assignTo` 속성을 실행한다. assignTo 실행 후 표현식 평가, `<apex:page>`의 `action` 속성 평가, getting/setting 등 기타 메서드 호출을 수행한다.
4. `<apex:form>` 컴포넌트가 있으면 페이지 요청 간 DB 상태 유지에 필요한 정보가 암호화된 **view state**로 저장된다. view state는 페이지 갱신 시마다 업데이트된다.
5. 결과 HTML이 브라우저로 전송된다. 클라이언트 측 기술(JavaScript 등)이 있으면 브라우저가 실행한다.

사용자가 페이지와 상호작용하면 action/getter/setter 실행을 위해 필요 시 컨트롤러 객체에 접촉한다. 새 get request가 발생하면 view state·컨트롤러 객체가 삭제된다.

> **Note:** 동일 컨트롤러 + 동일하거나 적절한 부분집합의 controller extension을 쓰는 페이지로 redirect되면 postback request가 발생한다. postback 시 view state는 유지된다.

### Postback Request 실행 순서

> (PDF 다이어그램 — 텍스트만) PDF p.115에 postback request 다이어그램이 있으나 pdftotext로 잡히지 않아 번호 단계 텍스트만 재현한다.

1. postback 요청 시 view state를 디코드하여 페이지 값 갱신 기준으로 사용한다.
   > **Note:** `immediate` 속성이 true인 컴포넌트는 이 단계를 우회한다. 즉 action은 실행되지만 입력 검증이 없고 페이지 데이터가 변경되지 않는다.
2. view state 디코드 후 표현식을 평가하고, 컨트롤러·확장의 set 메서드(custom component용 컨트롤러의 set 메서드 포함)를 실행한다. 이 메서드 호출들은 **모든 메서드가 성공 실행돼야** 데이터가 갱신된다. 예: 한 메서드가 속성을 갱신했으나 검증 규칙/잘못된 데이터 타입으로 무효면 데이터는 미갱신되고 오류 메시지와 함께 페이지가 재표시된다.
3. postback을 트리거한 action을 실행한다. 성공 완료 시 데이터가 갱신된다. 동일 페이지로 복귀하면 view state가 갱신된다.
   > **Note:** `<apex:page>`의 `action` 속성은 postback 시 평가되지 않는다. **get request 시에만** 평가된다.
4. 결과 HTML이 브라우저로 전송된다.

postback이 페이지 redirect를 지시하고 redirect 대상이 동일 컨트롤러 + 원본의 적절한 부분집합 확장을 쓰면 그 페이지에 postback이 실행된다. 아니면 get request가 실행된다. postback이 `<apex:form>`을 포함하면 postback에서 ID query parameter만 반환된다.

> **Tip:** PageReference의 `setRedirect` 속성으로 postback/get 실행을 제어한다. `setRedirect=true` → get request 실행. `false`로 설정해도 "대상이 동일 컨트롤러+적절한 확장 부분집합을 쓸 때만 postback 실행"이라는 제약을 무시하지 않는다. setRedirect=false인데 대상이 그 요건을 미충족하면 get request가 발생한다.

redirect 후 view state·컨트롤러 객체는 삭제된다.

### 실행 순서 예제 (Order of Execution Example)

예제 페이지는 account "Northern Trail Outfitters"의 이름·직원 수·industry를 표시한다. URL query parameter `key`가 true면 편집 가능하다. custom component 초기화 중 설정되는 `key` 원본값·갱신값도 표시한다.

**① custom component 컨트롤러 `PageValuesController`**

```apex
public with sharing class PageValuesController {
    public Boolean controllerKey {get; set;}
    public Boolean getNewKey() {
        // return the opposite of controllerKey
        return !controllerKey;
    }
}
```

**② custom component `PageValues`**

```html
<apex:component controller="PageValuesController">
    <apex:attribute name="originalKey" type="Boolean"
        description="The original key." assignTo="{!controllerKey}"/>
    <p>
    Original Key = {!originalKey}<br/>
    Controller Key = {!controllerKey}<br/>
    New Key = {!newKey}<br/>
    </p>
</apex:component>
```

**③ custom controller `AccountInfoController`**

```apex
public with sharing class AccountInfoController {
    private final Account account;
    public AccountInfoController() {
        account = [select id, name, site, NumberOfEmployees, Industry from Account
            where id = :ApexPages.currentPage().getParameters().get('id')];
    }
    public Account getAccount() {
        return account;
    }
    public PageReference save() {
        update account;
        return null;
    }
}
```

**④ controller extension `AccountInfoControllerExtension`**

```apex
public with sharing class AccountInfoControllerExtension {
    private final Account acct;
    Integer empAdd;
    public AccountInfoControllerExtension(AccountInfoController controller) {
        this.acct = (Account)controller.getAccount();
    }
    public String getGreeting() {
        return acct.name + ' Current Information';
    }
    public void resetNumberOfEmployees() {
        acct.NumberOfEmployees = 1;
        update acct;
    }
}
```

> PDF 본문은 `<apex:page>` action이 호출하는 메서드를 "resetEmp"로 칭하나, 실제 코드의 메서드명은 `resetNumberOfEmployees`다. 본 노트는 코드의 `resetNumberOfEmployees`를 정본으로 한다. [sic]

**⑤ 페이지 `AccountInfo`**

```html
<apex:page controller="AccountInfoController" tabStyle="Account"
    extensions="AccountInfoControllerExtension" action="{!resetNumberOfEmployees}">
    <apex:messages />
    <apex:pageBlock title="{!greeting}">
        <apex:outputLabel value="{!$ObjectType.account.fields.Name.label}: "
            for="acctName"/>
        <apex:outputField value="{!account.name}" id="acctName"/>
        <br/>
        <apex:outputLabel value="{!$ObjectType.account.fields.NumberOfEmployees.label}: "
            for="emps"/>
        <apex:outputField value="{!account.NumberOfEmployees}" id="emps"/>
        <br/>
        <apex:outputLabel value="{!$ObjectType.account.fields.Industry.label}: "
            for="industry"/>
        <apex:outputField value="{!account.Industry}" id="industry"/>
        <br/>
    </apex:pageBlock>
    <apex:pageBlock title="Page Values">
        <c:PageValues originalKey="{!IF($CurrentPage.parameters.key = 'true', true,
            false)}"/>
    </apex:pageBlock>
    <apex:form rendered="{!$CurrentPage.parameters.key = 'true'}">
        <apex:pageBlock title="Update the Account" id="updateBlock">
            <apex:pageBlockSection columns="1">
                <apex:inputField id="aName" value="{!account.name}"/>
                <apex:inputField value="{!account.NumberOfEmployees}"/>
                <apex:pageBlockSectionItem >
                    <apex:outputLabel value="{!$ObjectType.account.fields.Industry.label}"
                        for="acctIndustry"/>
                    <apex:actionRegion >
                        <apex:inputField value="{!account.Industry}" id="acctIndustry">
                            <apex:actionSupport event="onchange" rerender="updateBlock"/>
                        </apex:inputField>
                    </apex:actionRegion>
                </apex:pageBlockSectionItem>
            </apex:pageBlockSection>
            <apex:pageBlockButtons location="bottom">
                <apex:commandButton action="{!save}" value="Save"/>
            </apex:pageBlockButtons>
        </apex:pageBlock>
    </apex:form>
</apex:page>
```

**Get Request 추적** — URL `https://MyDomain_login_URL/apex/AccountInfo?id=recordId&key=false` 방문(key=false). URL 직접 입력이므로 get request다. (PDF p.119 스크린샷 "A page appears:")

1. custom controller `AccountInfoController`와 extension `AccountInfoControllerExtension`의 생성자가 실행된다. 컨트롤러는 SOQL 결과로 `account` 변수를 설정(URL의 account id 사용), extension은 컨트롤러의 getAccount 호출로 `acct` 변수를 생성한다.
2. custom component `PageValues`가 초기화된다. 자체 컨트롤러를 보유하고 명시적 생성자가 없으므로 암묵적 무인자 public 생성자로 객체가 생성된다. component 생성 일부로 `originalKey` 속성이 설정되는데, key=false이므로 originalKey는 false로 평가된다.
3. component 초기화 후 `assignTo` 속성이 실행된다. assignTo는 이 속성값을 연결 component 컨트롤러의 클래스 변수에 할당하는 setter다. PageValues의 assignTo는 `{!controllerKey}`이므로 PageValuesController의 controllerKey가 originalKey 값으로 설정된다. getNewKey는 newKey를 controllerKey의 반대로 설정 → controllerKey=false → newKey=true.
4. `<apex:page>`의 action 속성이 extension의 `resetNumberOfEmployees`(PDF 본문 명칭 "resetEmp" [sic])를 호출한다. 이 메서드는 account의 NumberOfEmployees를 1로 설정한다. 페이지에 여러 표현식이 평가되며 순서는 불확정(indeterminate, 로드마다 다를 수 있음)이다. 두 표현식에 주목한다.
   - `<apex:pageBlock title="{!greeting}">`: title이 extension의 getGreeting을 호출 → "Northern Trail Outfitters Current Information"을 표시.
   - `<apex:form rendered="{!$CurrentPage.parameters.key = 'false'}">`: rendered가 key 값 기반. key=false로 호출했으므로 form은 미렌더.
5. `<apex:form>`이 렌더되지 않으므로 view state가 유지되지 않는다.
6. HTML이 브라우저로 전송·렌더된다.

**Postback Request 추적** — URL `https://MyDomain_login_URL/apex/AccountInfo?id=recordId&key=true` 방문(key=true). (PDF p.120 스크린샷 "A page with a form appears:") Update the Account 섹션에서 Account Name→NTO, Employees→42, Industry→Other로 변경 후 Save 클릭 → postback request 시작.

1. view state를 디코드한다. view state는 페이지 값 갱신에 필요한 모든 정보를 포함한다.
2. 모든 표현식을 평가하고 컨트롤러·확장 메서드를 실행한다. 표현식 순서는 불확정. 두 표현식을 평가한다.
   - `<apex:pageBlock title="{!greeting}">`: getGreeting 호출. account name을 변경했으므로 greeting이 "NTO Current Information"으로 변경.
   - `<apex:form rendered="{!$CurrentPage.parameters.key = 'true'}">`: key 파라미터를 변경하지 않았으므로 view state 값 사용. view state 생성 시 true였으므로 form 렌더.
3. postback을 트리거한 save action을 평가한다. save action은 컨트롤러의 다음 메서드다.
   ```apex
   public PageReference save() {
       update account;
       return null;
   }
   ```
   오류가 없으면 새 데이터로 레코드가 갱신된다. postback 트리거 action에 page redirect가 없었으므로 view state가 갱신된다. 결과 HTML이 전송되어 갱신된 account 정보를 표시한다. save는 사용자 권한 부족 또는 변경이 트리거한 검증 규칙으로 실패할 수 있고 — 이 경우 오류 메시지와 함께 페이지가 표시된다. 사용자가 입력한 값은 입력 필드에 남아 편집·재제출할 수 있다.
4. postback 성공 실행 후 갱신된 페이지가 표시된다. (PDF p.121 스크린샷)

## 10. 커스텀 컨트롤러 테스트 (Test a Custom Controller)

오류 없는 코드를 위해 작성하는 모든 custom controller·controller extension에 대해 Apex unit test를 작성·실행한다. unit test 메서드는 인자가 없고 DB 커밋이 없으며 정의에 `@isTest` annotation 플래그를 단다. (테스트 메커니즘 일반론은 별도 Apex 테스트 노트 영역.)

예제 NewLead 페이지: 사용자가 모든 필드를 유효값으로 채우면 신규 lead 생성 후 Success 페이지로 이동, 아니면 lead 미생성·Failure 페이지로 이동한다.

```apex
public class NewLeadController {
    private String firstName;
    private String lastName;
    private String company;
    private String email;
    public NewLeadController() {
    }
    public String getFirstName() {
        return this.firstName;
    }
    public void setFirstName(String firstName) {
        this.firstName = firstName;
    }
    public String getLastName() {
        return this.lastName;
    }
    public void setLastName(String lastName) {
        this.lastName = lastName;
    }
    public String getCompany() {
        return this.company;
    }
    public void setCompany(String company) {
        this.company = company;
    }
    public String getEmail() {
        return this.email;
    }
    public void setEmail(String email) {
        this.email = email;
    }
    public PageReference save() {
        PageReference p = null;
        try {
            Lead newlead = new Lead(LastName=this.lastName,
                FirstName=this.firstName,
                Company=this.company,
                Email=this.email);
            insert newlead;
        } catch (Exception e) {
            p = Page.Failure;
            p.getParameters().put('error', 'noInsert');
        }
        if (p == null) {
            p = Page.Success;
        }
        p.setRedirect(true);
        return p;
    }
}
```

```html
<apex:page controller="NewLeadController" tabstyle="lead">
    <apex:pageBlock>
        <apex:form>
            <h1>Test page for adding leads</h1>
            <p>This is a test page for adding leads.</p>
            <p>First name: <apex:inputText value="{!FirstName}"></apex:inputText></p>
            <p>Last name: <apex:inputText value="{!LastName}"></apex:inputText></p>
            <p>Company: <apex:inputText value="{!Company}"></apex:inputText></p>
            <p>Email address: <apex:inputText value="{!Email}"></apex:inputText></p>
            <apex:commandButton action="{!save}" value="Save New Lead"/>
        </apex:form>
    </apex:pageBlock>
</apex:page>
```

```html
<apex:page>
    Success!
</apex:page>
```

```html
<apex:page>
    A failure has occurred.
</apex:page>
```

테스트 클래스 `NewLeadTests`(메서드 `testAddNewLead`)는 실패·성공 조건을 모두 검사한다. 컨트롤러의 현재 PageReference 설정은 `Test.setCurrentPage(PageReference page)`를 사용한다.

```apex
@isTest
private class NewLeadTests {
    @isTest
    static void testAddNewLead() {
        PageReference pageRef = Page.NewLead;
        Test.setCurrentPage(pageRef);
        //Instantiate a new controller with no field values
        NewLeadController myController = new NewLeadController();
        String nextPage = myController.save().getUrl();
        // Verify that the page fails to create the lead
        System.assertEquals('/apex/failure?error=noInsert', nextPage);
        // Instantiate a new controller with valid field values
        myController = new NewLeadController();
        myController.setLastName('lastname');
        myController.setFirstName('firstname');
        myController.setCompany('Ursa Major');
        myController.setEmail('firstlast@ursamajor.com');
        nextPage = myController.save().getUrl();
        // Verify that the Success page displays
        System.assertEquals('/apex/success', nextPage);
        Lead[] leads = [select id, email from lead where Company = 'Ursa Major'];
        System.assertEquals('firstlast@ursamajor.com', leads[0].email);
    }
}
```

Apex 테스트 메서드는 Developer Console, Setup, VS Code용 Salesforce 확장, 또는 API로 실행할 수 있다.

> **Tip:** 테스트 시 콘솔에 `Method does not exist or incorrect signature: Test.setCurrentPage(System.PageReference)` 메시지가 표시되면 `Test`라는 클래스를 직접 만들었는지 확인한다. 그렇다면 클래스명을 변경한다.

### VF 테스트 패턴 체크리스트

VF 컨트롤러 단위 테스트에 반복되는 관용구(idiom)를 한곳에 모은다. 각 항목의 상세는 링크된 노트를 참조한다 (새 사실이 아니라 여러 노트에 흩어진 조각의 색인).

| 관용구 | 목적 | 상세 노트 |
|---|---|---|
| `Test.setCurrentPage(Page.X)` | 테스트가 대상 VF 페이지를 현재 페이지 컨텍스트로 설정 (위 `NewLeadTests` 예제) | 본 §10 예제 |
| `ApexPages.currentPage().getParameters().put('id', rec.Id)` | 컨트롤러 생성자가 읽는 URL query parameter(예: `id`)를 테스트에서 주입 | [[ApexPages Namespace]] |
| `new ApexPages.StandardController(record)` | controller extension을 테스트할 때 생성자에 넘길 표준 컨트롤러 인스턴스 조립 | [[표준 컨트롤러·표준 리스트 컨트롤러]] |
| `new ApexPages.StandardSetController(queryLocator/list)` | 커스텀/표준 리스트 컨트롤러 확장을 테스트할 때 레코드 집합 컨트롤러 조립 | [[표준 컨트롤러·표준 리스트 컨트롤러]] |
| `standardSetController.setSelected(records)` | 리스트 컨트롤러에서 사용자가 선택한 레코드를 시뮬레이트 | [[표준 컨트롤러·표준 리스트 컨트롤러]] |
| `getContent()` / `getContentAsPDF()` **테스트 불가** | API v34.0 이상에서 callout으로 취급 → `@isTest` 메서드에서 호출하면 test 메서드가 실패한다. PDF 생성부를 분리해 우회하거나 assert 대상에서 제외 | [[Apex 버전별 동작 변경 레퍼런스]] · PDF 렌더 맥락은 [[페이지 출력 제어 — HTML·PDF·SLDS]] |

## 11. 검증 규칙과 커스텀 컨트롤러 (Validation Rules and Custom Controllers)

custom controller를 쓰는 VF 페이지에서 사용자 입력이 검증 규칙 오류를 유발하면 그 오류를 VF 페이지에 표시할 수 있다. 표준 컨트롤러 페이지처럼, 검증 규칙 오류 위치가 `<apex:inputField>`와 연결된 필드면 거기에 표시되고, 오류 위치가 페이지 상단이면 `<apex:page>` 내 `<apex:messages>`로 표시된다. 단 정보를 페이지로 전달하려면 custom controller가 예외를 catch해야 한다.

```html
<apex:page controller="MyController" tabStyle="Account">
    <apex:messages/>
    <apex:form>
        <apex:pageBlock title="Hello {!$User.FirstName}!">
            This is your new page for the {!name} controller. <br/>
            You are viewing the {!account.name} account.<br/><br/>
            Change Account Name: <p></p>
            <apex:inputField value="{!account.name}"/> <p></p>
            Change Number of Locations:
            <apex:inputField value="{!account.NumberofLocations__c}" id="Custom_validation"/>
            <p>(Try entering a non-numeric character here, then hit save.)</p><br/><br/>
            <apex:commandButton action="{!save}" value="Save New Account Name"/>
        </apex:pageBlock>
    </apex:form>
</apex:page>
```

> **Note:** 이 페이지를 렌더하려면 유효한 account 레코드 ID를 URL query parameter로 지정해야 한다. 예: `http://MyDomainName_login_URL/apex/myValidationPage?id=001x000xxx3Jsxb`.

```apex
public class MyController {
    Account account;
    public PageReference save() {
        try{
            update account;
        }
        catch(DmlException ex){
            ApexPages.addMessages(ex);
        }
        return null;
    }
    public String getName() {
        return 'MyController';
    }
    public Account getAccount() {
        if(account == null)
            account = [select id, name, numberoflocations__c from Account
                where id = :ApexPages.currentPage().getParameters().get('id')];
        return account;
    }
}
```

사용자가 페이지 저장 시 검증 오류가 트리거되면 예외가 catch되어 표준 컨트롤러처럼 페이지에 표시된다.

## 12. `transient` 키워드 사용 (Using the transient Keyword)

`transient` 키워드로 저장될 수 없고 VF 페이지 view state의 일부로 전송되어선 안 되는 인스턴스 변수를 선언한다.

```apex
Transient Integer currentTotal;
```

`transient`는 직렬화 가능한 Apex 클래스 — 컨트롤러, 컨트롤러 확장, `Batchable`/`Schedulable` 인터페이스 구현 클래스 — 에서 사용 가능하다. 또한 직렬화 가능 클래스에 선언된 필드 타입을 정의하는 클래스에서도 사용 가능하다. (`transient` 키워드 일반론은 [[Apex 언어 기초 — 제어 흐름과 클래스]] 참조.)

transient 선언은 view state 크기를 감소시킨다. 일반 사용 사례: 페이지 요청 동안만 필요하지만 view state의 일부가 되어선 안 되고, 요청 중 여러 번 재계산하기엔 시스템 리소스를 너무 많이 쓰는 VF 페이지 필드.

일부 Apex 객체는 **자동으로 transient**로 간주되어 값이 view state의 일부로 저장되지 않는다.

- PageReferences
- XmlStream 클래스
- 보유 객체 타입이 자동 transient인 경우에만 자동 transient로 표시되는 Collection (예: Savepoint의 컬렉션)
- 대부분의 system 메서드 생성 객체 (예: Schema.getGlobalDescribe)
- JSONParser 클래스 인스턴스

Static 변수도 view state로 전송되지 않는다.

```html
<apex:page controller="ExampleController">
    T1: {!t1} <br/>
    T2: {!t2} <br/>
    <apex:form>
        <apex:commandLink value="refresh"/>
    </apex:form>
</apex:page>
```

```apex
public class ExampleController {
    DateTime t1;
    transient DateTime t2;
    public String getT1() {
        if (t1 == null) t1 = System.now();
        return '' + t1;
    }
    public String getT2() {
        if (t2 == null) t2 = System.now();
        return '' + t2;
    }
}
```

refresh 버튼 클릭 시 transient date(`t2`)는 페이지 새로고침마다 재생성되어 갱신되고, non-transient date(`t1`)는 view state에서 역직렬화된 원본 값을 유지한다.

## 13. 종합 예제 (Advanced Examples)

quick start 튜토리얼 예제는 초급(주로 VF 마크업만)이지만, advanced 예제는 VF 마크업 + Lightning Platform Apex 코드를 함께 사용한다.

> **Note:** Salesforce UI로 Apex 추가/편집/삭제는 Developer Edition, Salesforce Enterprise Edition 평가판 조직, sandbox 조직에서만 가능하다. production 조직에서는 Ant Migration Tool 또는 Lightning Platform API `compileAndTest` 호출로만 Apex를 변경할 수 있다.

### 13.1 페이지에 커스텀 컨트롤러 추가하는 두 방법

custom controller는 단순히 Apex 클래스다(유효하나 무의미한 예: `public class MyController { }`). 페이지에 추가하는 방법은 두 가지다.

- `<apex:page>` 태그에 `controller` 속성을 추가한 뒤 "quick fix"로 즉석 생성:
  ```html
  <apex:page controller="MyController">
      <apex:pageBlock title="Hello {!$User.FirstName}!">
          This is your new page.
      </apex:pageBlock>
  </apex:page>
  ```
  → quick fix 옵션으로 MyController라는 Apex 클래스를 자동 생성.
- Apex 에디터에서 컨트롤러 클래스를 생성·저장한 뒤(Setup → Quick Find "Apex Classes" → New) 페이지의 `<apex:page>`에 controller 속성으로 참조.

> **Note:** 페이지는 한 번에 컨트롤러 하나만 참조할 수 있다. `<apex:page>`에서 `standardController`와 `controller` 속성을 함께 쓸 수 없다.

유효한 custom controller 참조 페이지를 저장하는 즉시 Page Editor 옆에 두 번째 Controller editor 탭이 사용 가능해진다. (PDF p.128 스크린샷 "The Custom Controller Editor")

### 13.2 Getter 메서드 정의 (점진적 구축)

getter는 보통 `getIdentifier`로 명명한다(Identifier는 반환 레코드/primitive 값 이름). 페이지에서는 get 접두어를 뺀 이름을 표현식으로 쓴다(예: getName → `{!name}`). 표준 Account 컨트롤러의 getAccount를 모방하면 다음과 같다.

```apex
public class MyController {
    public String getName() {
        return 'MyController';
    }
    public Account getAccount() {
        return [select id, name from Account
            where id = :ApexPages.currentPage().getParameters().get('id')];
    }
}
```

getAccount는 embedded SOQL로 URL의 id 파라미터가 지정한 account를 반환한다. id 접근에 [[ApexPages Namespace]]를 사용한다.

- `currentPage` 메서드가 현재 페이지의 PageReference 인스턴스를 반환한다(query string parameter 포함 VF 페이지 참조).
- `getParameters` 메서드로 지정 query string parameter 이름·값의 map을 반환한다.
- `get`에 id를 지정 호출하면 id 파라미터 값이 반환된다.

SOQL이 반환한 필드만 페이지에서 사용 가능하다. 표준 Account 컨트롤러를 더 가깝게 모방하려면 `<apex:page>`에 `tabStyle="Account"`를 추가한다. (PDF p.130 스크린샷 "Using a Custom Controller to Display Values on a Page")

### 13.3 Action 메서드 정의 (save 점진적 구축)

VF 에디터가 save 메서드 추가 quick fix를 제공한다. quick fix가 생성한 save는 표준 action 메서드 시그니처(public, PageReference 반환, 인자 없음)다. save가 DB를 갱신하려면 먼저 account 정보를 저장할 member 변수가 필요하다(없으면 렌더 후 레코드가 유지되지 않아 사용자 갱신이 저장되지 않음). member 변수 추가 + getAccount 초기 쿼리 시 설정 후, save가 DB 갱신만 하면 되는 최종 형태는 다음과 같다.

```apex
public class MyController {
    Account account;
    public PageReference save() {
        update account;
        return null;
    }
    public String getName() {
        return 'MyController';
    }
    public Account getAccount() {
        if(account == null)
            account = [select id, name, site from Account
                where id = :ApexPages.currentPage().getParameters().get('id')];
        return account;
    }
}
```

더 견고한 save는 예외 catch·중복 검사 등을 하겠으나 단순 예제라 생략한다.

### 13.4 Navigation 메서드 정의

custom controller action 메서드는 PageReference 객체 반환으로 다른 페이지로 네비게이트할 수 있다. PageReference는 페이지 인스턴스화의 참조로, URL + query parameter 이름·값 집합으로 구성된다. PageReference 참조·인스턴스화 방법은 세 가지다.

| 구문 | 용도 / 특징 |
|---|---|
| `Page.existingPageName` | 조직에 이미 저장된 VF 페이지의 PageReference 참조. 플랫폼이 컨트롤러/확장의 페이지 의존성을 인식하여, 컨트롤러/확장 존재 동안 페이지 삭제를 방지한다. |
| `new PageReference('partialURL')` | Lightning Platform에 호스팅된 페이지의 PageReference 생성(예: `/apex/HelloWorld`, 또는 `/`+recordID로 레코드 상세). 런타임 구성이라 `Page.existingPageName`보다 **덜 선호**됨 — 참조 무결성 시스템에 미제공되어 의존성 미인식·삭제 방지 오류가 발생하지 않는다. |
| `new PageReference('fullURL')` | 외부 URL용. 예: `new PageReference('http://www.google.com')`. |

Save 후 다른 페이지로 redirect하는 예제:

```html
<apex:page standardController="Account">
    Hello {!$User.FirstName}!
    <p>You are viewing the {!account.name} account.</p>
</apex:page>
```

```apex
public class MyController {
    Account account;
    public PageReference save() {
        update account;
        PageReference secondPage = Page.mySecondPage;
        secondPage.setRedirect(true);
        return secondPage;
    }
    public String getName() {
        return 'MyController';
    }
    public Account getAccount() {
        if(account == null)
            account = [select id, name, site from Account
                where id = :ApexPages.currentPage().getParameters().get('id')];
        return account;
    }
}
```

PageReference의 redirect 속성이 true로 설정되어 있다. 미설정 시 PageReference가 브라우저에 반환되나 네비게이션이 발생하지 않는다(원본 URL 유지). 또한 redirect 시 컨트롤러가 context state를 비우므로 data context가 손실되어 `{!account.name}` 값이 없어진다 — 따라서 PageReference의 parameter map에 id query string parameter를 재설정해야 한다.

```apex
public class MyUpdatedController {
    Account account;
    public PageReference save() {
        update account;
        PageReference secondPage = Page.mySecondPage;
        secondPage.setRedirect(true);
        secondPage.getParameters().put('id',account.id);
        return secondPage;
    }
    public String getName() {
        return 'MyController';
    }
    public Account getAccount() {
        if(account == null)
            account = [select id, name, site from Account
                where id = :ApexPages.currentPage().getParameters().get('id')];
        return account;
    }
}
```

### 13.5 Wizard 만들기 (3단계)

VF 마크업으로 3단계 wizard를 만들어 opportunity를 관련 contact·account·contact role과 동시에 생성한다.

- 1단계: account·contact 정보 캡처
- 2단계: opportunity 정보 캡처
- 최종 단계: 생성될 레코드 표시·저장/취소

구현은 3단계 각각의 페이지 + 페이지 간 네비게이션·입력 데이터를 추적하는 단일 custom controller로 한다.

> **Important:** 여러 VF 페이지에 걸쳐 쓰는 데이터는 (해당 페이지가 미사용이어도) 첫 페이지에 정의해야 한다. 예: 2·3페이지에 필요한 필드는 1페이지에도 있어야 한다. 필드의 rendered 속성을 false로 설정해 숨길 수 있다.

> **Note:** 빈 페이지는 만들 수 있으나 역은 불가하다 — 페이지가 컨트롤러를 참조하려면 컨트롤러가 모든 메서드·프로퍼티와 함께 존재해야 한다. (먼저 빈 페이지 정의 → 컨트롤러 생성 → 페이지에 마크업 추가 순으로 conundrum을 해결한다.)

**컨트롤러 `newOpportunityController`:**

```apex
public class newOpportunityController {
    // These four member variables maintain the state of the wizard.
    // When users enter data into the wizard, their input is stored
    // in these variables.
    Account account;
    Contact contact;
    Opportunity opportunity;
    OpportunityContactRole role;

    // The next four methods return one of each of the four member
    // variables. If this is the first time the method is called,
    // it creates an empty record for the variable.
    public Account getAccount() {
        if(account == null) account = new Account();
        return account;
    }
    public Contact getContact() {
        if(contact == null) contact = new Contact();
        return contact;
    }
    public Opportunity getOpportunity() {
        if(opportunity == null) opportunity = new Opportunity();
        return opportunity;
    }
    public OpportunityContactRole getRole() {
        if(role == null) role = new OpportunityContactRole();
        return role;
    }

    // The next three methods control navigation through
    // the wizard. Each returns a PageReference for one of the three pages
    // in the wizard. Note that the redirect attribute does not need to
    // be set on the PageReference because the URL does not need to change
    // when users move from page to page.
    public PageReference step1() {
        return Page.opptyStep1;
    }
    public PageReference step2() {
        return Page.opptyStep2;
    }
    public PageReference step3() {
        return Page.opptyStep3;
    }

    // This method cancels the wizard, and returns the user to the
    // Opportunities tab
    public PageReference cancel() {
        PageReference opportunityPage = new PageReference('/006');
        opportunityPage.setRedirect(true);
        return opportunityPage;
    }
    // This method performs the final save for all four objects, and
    // then navigates the user to the detail page for the new
    // opportunity.
    public PageReference save() {
        // Create the account. Before inserting, copy the contact's
        // phone number into the account phone number field.
        account.phone = contact.phone;
        insert account;
        // Create the contact. Before inserting, use the id field
        // that's created once the account is inserted to create
        // the relationship between the contact and the account.
        contact.accountId = account.id;
        insert contact;
        // Create the opportunity. Before inserting, create
        // another relationship with the account.
        opportunity.accountId = account.id;
        insert opportunity;
        // Create the junction contact role between the opportunity
        // and the contact.
        role.opportunityId = opportunity.id;
        role.contactId = contact.id;
        insert role;
        // Finally, send the user to the detail page for
        // the new opportunity.
        PageReference opptyPage = new ApexPages.StandardController(opportunity).view();
        opptyPage.setRedirect(true);
        return opptyPage;
    }
}
```

**Step 1 — `opptyStep1`:**

```html
<apex:page controller="newOpportunityController" tabStyle="Opportunity">
    <script>
    function confirmCancel() {
        var isCancel = confirm("Are you sure you wish to cancel?");
        if (isCancel) return true;
        return false;
    }
    </script>
    <apex:sectionHeader title="New Customer Opportunity" subtitle="Step 1 of 3"/>
    <apex:form>
        <apex:pageBlock title="Customer Information" mode="edit">
            <!-- The pageBlockButtons tag defines the buttons that appear at the top
            and bottom of the pageBlock. Like a facet, it can appear anywhere in
            a pageBlock, but always defines the button areas.-->
            <!-- The Next button contained in this pageBlockButtons area
            calls the step2 controller method, which returns a pageReference to
            the next step of the wizard. -->
            <apex:pageBlockButtons>
                <apex:commandButton action="{!step2}" value="Next"/>
                <apex:commandButton action="{!cancel}" value="Cancel"
                    onclick="return confirmCancel()" immediate="true"/>
            </apex:pageBlockButtons>
            <apex:pageBlockSection title="Account Information">
                <!-- Within a pageBlockSection, inputFields always display with their
                corresponding output label. -->
                <apex:inputField id="accountName" value="{!account.name}"/>
                <apex:inputField id="accountSite" value="{!account.site}"/>
            </apex:pageBlockSection>
            <apex:pageBlockSection title="Contact Information">
                <apex:inputField id="contactFirstName" value="{!contact.firstName}"/>
                <apex:inputField id="contactLastName" value="{!contact.lastName}"/>
                <apex:inputField id="contactPhone" value="{!contact.phone}"/>
            </apex:pageBlockSection>
        </apex:pageBlock>
    </apex:form>
</apex:page>
```

설명 요점:

- `<apex:pageBlock>`은 선택적 `<apex:pageBlockButtons>` 자식으로 헤더·푸터 버튼을 제어한다. `<apex:pageBlockButtons>`가 본문에 나타나는 순서는 무관하다. 이 단계는 푸터에 Next 버튼을 포함한다.
- Cancel 버튼 클릭 시 이탈 확인 대화상자 표시에 JavaScript를 사용한다. 단순화를 위해 마크업에 직접 포함했으나 static resource에 두고 참조하는 것이 best practice다.
- Next 버튼이 step2를 호출 → 다음 단계 PageReference 반환. command 버튼은 form 안에 있어야 한다(form 컴포넌트가 새 PageReference 기반 페이지 갱신을 담당).
- `<apex:pageBlockSection>`은 표시할 데이터 집합을 구성한다. 1+ 컬럼, 각 컬럼은 2셀(필드 라벨·값)에 걸친다. 본문 컴포넌트는 컬럼 수에 도달할 때까지 행의 다음 셀에 배치되고, 도달 시 다음 행 첫 셀로 wrap된다. `<apex:inputField>` 등 일부 컴포넌트는 자동으로 컬럼 2셀 모두(라벨+값)를 차지한다. 예: Contact Information에서 First Name은 1번 컬럼, Last Name은 2번 컬럼, Phone은 다음 행 1번 컬럼으로 wrap.
- 첫 `<apex:inputField>`의 value 속성은 사용자 입력을 getContact가 반환하는 contact 레코드의 firstName 필드에 할당한다.

(PDF p.139 스크린샷 "Step 1 of the New Customer Opportunity Wizard")

### 13.6 Visualforce 대시보드 컴포넌트

custom list controller를 쓰는 VF 페이지를 만들어 대시보드 컴포넌트로 사용한다.

> **Note:** VF 페이지를 대시보드 컴포넌트로 쓰는 것은 **Salesforce Classic에서만** 가능하다. Lightning Experience에서는 custom tab을 만들어 커스텀 lightning 컴포넌트용 대시보드로 사용한다.

**EDITIONS:**
- Available in: Salesforce Classic (not available in all orgs)
- Available in: all editions

대시보드 포함 요건: VF 페이지는 custom controller 사용, 표준/커스텀 list controller 사용, 또는 컨트롤러 없음 중 하나여야 한다. 표준 컨트롤러를 쓰는 VF 페이지는 대시보드에 추가할 수 없다. 이 요건을 충족하는 VF 페이지만 Data Sources 탭에 옵션으로 표시된다.

VF 대시보드 컴포넌트는 third-party cookie가 비활성화되면 미지원이다. 다음 예제는 contact "Barbara Levy"와 연관된 모든 open case를 표시한다. (PDF p.142 스크린샷)

```apex
public class retrieveCase {
    public String getContactName() {
        return 'Barbara Levy';
    }
    public List<Case> getCases() {
        return [SELECT status, subject FROM Case
            WHERE Contact.name = 'Barbara Levy' AND status != 'Closed' limit 5];
    }
}
```

```html
<apex:page controller="retrieveCase" tabStyle="Case">
    <apex:pageBlock>
        {!contactName}'s Cases
        <apex:pageBlockTable value="{!cases}" var="c">
            <apex:column value="{!c.status}"/>
            <apex:column value="{!c.subject}"/>
        </apex:pageBlockTable>
    </apex:pageBlock>
</apex:page>
```

이후 이 VF 페이지를 Salesforce Classic의 대시보드에 추가한다.

### 13.7 커스텀 리스트 컨트롤러로 레코드 일괄 갱신 (Mass Update)

mass update 페이지 생성에 `StandardSetController` 클래스의 **prototype object**를 사용한다. list controller는 두 레코드 집합을 추적한다 — 필터된 레코드의 primary list + 그 선택분의 secondary list. secondary list는 사용자가 체크박스로 레코드를 선택하는 표준 list view 페이지에서 확립된다. 사용자가 custom list button을 클릭하면 custom mass update 페이지로 이동하고, prototype object로 선택 레코드에 새 필드값을 적용한다. prototype object는 사용자가 선택한 모든 레코드에 작동하며, 조회는 StandardSetController의 `getRecord` 메서드로 한다.

**컨트롤러 `selectedSizeWorkaround`:**

```apex
public class selectedSizeWorkaround {
    ApexPages.StandardSetController setCon;
    public selectedSizeWorkaround(ApexPages.StandardSetController controller) {
        setCon = controller;
    }
    public integer getMySelectedSize() {
        return setCon.getSelected().size();
    }
    public integer getMyRecordsSize() {
        return setCon.getRecords().size();
    }
}
```

**마크업 `massupdatestages`:**

```html
<apex:page
    standardController="Opportunity"
    recordSetVar="opportunities"
    extensions="selectedSizeWorkaround"
    showHeader="false"
    id="muopp"
>
    <apex:form id="muform">
        <apex:pageMessage
            summary="Selected Collection Size: {!mySelectedSize}"
            severity="info"
            id="mupms"
        />
        <apex:pageMessage
            summary="Record Set Size: {!myRecordsSize}"
            severity="info"
            id="mupmr"
        />
        <apex:pageBlock title="Opportunity Mass-Update" mode="edit" id="mub1">
            <apex:pageMessages />
            <apex:pageBlockSection id="mus1">
                <apex:inputField value="{!opportunity.stagename}" id="stagename">
                    <apex:actionSupport event="onchange" rerender="muselectedlist"/>
                </apex:inputField>
            </apex:pageBlockSection>
            <apex:pageBlockButtons location="bottom" id="mubut">
                <apex:commandButton value="Save" action="{!save}" id="butsav"/>
                <apex:commandButton value="Cancel" action="{!cancel}" id="butcan"/>
            </apex:pageBlockButtons>
        </apex:pageBlock>
        <apex:pageBlock title="Selected Opportunities" id="muselectedlist">
            <apex:pageBlockTable value="{!selected}" var="opp" id="mutab">
                <apex:column value="{!opp.name}" id="oppname"/>
                <apex:column value="{!opp.stagename}" id="oppstage"/>
            </apex:pageBlockTable>
        </apex:pageBlock>
    </apex:form>
</apex:page>
```

**버튼 연결 절차:**

1. opportunity의 object management settings → Buttons, Links, and Actions.
2. New Button or Link 클릭.
3. Button Label = `Mass Update Stages`, Name = `MassUpdateStages` 설정.
4. Display Type = List Button, "Display Checkboxes (for Multi-Record Selection)" 체크 확인. Behavior = Display in existing window with sidebar, Content Source = Visualforce Page. 생성한 페이지명을 클릭해 버튼에 연결 후 저장.
5. opportunity object management settings → List View Button Layout. List View 옆 dropdown에서 Edit.
6. Custom Buttons 아래 Mass Update Stages 버튼을 Selected Buttons 리스트로 이동 후 저장.
7. Opportunities 탭 클릭. 변경할 기존 opportunity를 표시하는 필터를 선택/생성.
8. 리스트 뷰 각 레코드 옆 체크박스로 여러 opportunity를 선택 후 Mass Update Stages 클릭 → 저장.

이 예는 1개 필드 갱신만 보여주나 prototype object의 임의 개수 필드를 참조·적용할 수 있다. 사용자가 설정하지 않은 prototype object 필드는 선택 레코드에 영향이 없다. 필드 속성(필수 여부 등)은 prototype object에 유지된다 — 예: Opportunity.StageName 같은 필수 필드의 input field를 페이지에 포함하면 사용자는 값 입력이 필수다.

> **Note:** `selectedSizeWorkaround`는 페이지가 사용자 선택 또는 필터 집합의 크기를 표시/참조하려는 경우에만 필요하다. 그런 표시는 mass update가 수정하는 집합 정보를 사용자에게 주므로 유용하다.
