# 표준 컨트롤러 · 표준 리스트 컨트롤러

> Visualforce 페이지에 코드 없이 표준 Salesforce 동작(save·edit·delete·pagination·list view)을 부여하는 두 가지 내장 컨트롤러 — 단일 레코드용 `standardController`와 레코드 집합용 `recordSetVar` 기반 표준 리스트 컨트롤러.

> ℹ️ 레거시 안내 — Visualforce 표준/리스트 컨트롤러는 Salesforce Classic 시대 패턴이다. 신규 UI는 LWC/Aura가 권장되나, 기존 VF 페이지 유지보수와 Classic 호환 화면에는 여전히 유효하다.

---

## 표준 컨트롤러 (Standard Controller)

Visualforce 컨트롤러는 사용자가 마크업의 컴포넌트와 상호작용할 때(버튼·링크 클릭 등) 무슨 일이 일어날지 지정하는 명령 집합이다. 컨트롤러는 페이지에 표시할 데이터에 대한 접근을 제공하고 컴포넌트 동작을 수정할 수 있다.

Lightning 플랫폼은 표준 Salesforce 페이지에서 사용되는 것과 동일한 기능·로직을 담은 다수의 **표준 컨트롤러**를 제공한다. 예를 들어 표준 Accounts 컨트롤러를 사용하면, Visualforce 페이지에서 Save 버튼을 클릭한 결과는 표준 Account 편집 페이지에서 Save를 클릭한 것과 동일하게 동작한다.

> **표준 컨트롤러는 Lightning Platform API로 쿼리할 수 있는 모든 Salesforce 객체에 대해 존재한다.**

### 표준 컨트롤러를 Visualforce 페이지에 연결하기

표준 컨트롤러를 Visualforce 페이지에 연결하려면 `<apex:page>` 태그의 `standardController` 속성에 Lightning Platform API로 쿼리할 수 있는 임의의 Salesforce 객체 이름을 지정한다.

예를 들어 `MyCustomObject`라는 커스텀 객체의 표준 컨트롤러를 페이지에 연결하려면 다음 마크업을 사용한다.

```xml
<apex:page standardController="MyCustomObject__c">
</apex:page>
```

> **Note:** `<apex:page>` 태그에서 `standardController` 속성을 사용할 때는 `controller` 속성을 동시에 사용할 수 없다.

### 표준 컨트롤러로 데이터 접근하기

모든 표준 컨트롤러에는 페이지 URL의 `id` 쿼리 문자열 파라미터로 지정된 레코드를 반환하는 getter 메서드가 포함되어 있다. 이 메서드 덕분에 연결된 페이지 마크업은 `{!object}` 구문으로 컨텍스트 레코드의 필드를 참조할 수 있다. 여기서 `object`는 컨트롤러에 연결된 객체의 소문자 이름이다.

예를 들어 Account 표준 컨트롤러를 사용하는 페이지는 `{!account.name}`으로 현재 컨텍스트의 account의 name 필드 값을 반환할 수 있다.

> **Note:** getter 메서드가 성공하려면 URL의 `id` 쿼리 문자열 파라미터로 지정된 레코드가 표준 컨트롤러와 동일한 타입이어야 한다. 예를 들어 Account 표준 컨트롤러를 사용하는 페이지는 account 레코드만 반환할 수 있다. `id` 쿼리 문자열 파라미터에 contact 레코드 ID가 지정되면 `{!account}` 표현식은 아무 데이터도 반환하지 않는다.

#### 관계 traversal (관련 레코드 데이터)

Lightning Platform API의 쿼리와 마찬가지로, merge field 구문으로 관련 레코드의 데이터를 가져올 수 있다.

- **자식→부모(child-to-parent) 관계는 최대 5레벨까지 traversal 가능.** 예를 들어 Contact 표준 컨트롤러를 사용한다면 `{!contact.Account.Owner.FirstName}`(3레벨 자식→부모 관계)로 contact에 연결된 account 레코드의 소유자 이름을 반환할 수 있다.
- **부모→자식(parent-to-child) 관계는 1레벨까지 traversal 가능.** 예를 들어 Account 표준 컨트롤러를 사용한다면 `{!account.Contacts}`로 현재 컨텍스트의 account에 연결된 모든 contact의 배열을 반환할 수 있다.

### 표준 컨트롤러 액션 사용하기

액션 메서드는 페이지 이벤트가 발생할 때(사용자가 버튼을 클릭하거나 페이지 영역 위로 마우스를 올릴 때 등) 로직이나 내비게이션을 수행한다. 액션 메서드는 다음 태그 중 하나의 `action` 파라미터에서 `{! }` 표기법으로 페이지 마크업에서 호출할 수 있다.

- `<apex:commandButton>` — 액션을 호출하는 버튼 생성
- `<apex:commandLink>` — 액션을 호출하는 링크 생성
- `<apex:actionPoller>` — 주기적으로 액션 호출
- `<apex:actionSupport>` — 다른 명명된 컴포넌트의 이벤트(“onclick”, “onmouseover” 등)가 액션을 호출하게 함
- `<apex:actionFunction>` — 액션을 호출하는 새 JavaScript 함수 정의
- `<apex:page>` — 페이지 로드 시 액션 호출

다음 표는 **모든 표준 컨트롤러가 지원하는 액션 메서드**를 설명한다. 이 액션들은 `action` 속성을 포함하는 임의의 Visualforce 컴포넌트에 연결할 수 있다.

| Action | Description |
|---|---|
| `save` | 새 레코드를 삽입하거나, 현재 컨텍스트에 있는 기존 레코드를 갱신한다. 작업 완료 후 save 액션은 사용자를 원래 페이지(알 수 있는 경우)로 되돌리거나, 저장된 레코드의 detail 페이지로 이동시킨다. |
| `quicksave` | 새 레코드를 삽입하거나, 현재 컨텍스트에 있는 기존 레코드를 갱신한다. save 액션과 달리 이 페이지는 사용자를 다른 페이지로 리다이렉트하지 않는다. |
| `edit` | 현재 컨텍스트에 있는 레코드의 편집 페이지로 사용자를 이동시킨다. 작업 완료 후 edit 액션은 사용자가 원래 액션을 호출한 페이지로 되돌린다. |
| `delete` | 컨텍스트에 있는 레코드를 삭제한다. 작업 완료 후 delete 액션은 페이지를 새로고침하거나 사용자를 연결된 객체의 tab으로 보낸다. |
| `cancel` | 편집 작업을 중단한다. 작업 완료 후 cancel 액션은 사용자가 원래 편집을 호출한 페이지로 되돌린다. |
| `list` | 해당 객체에 대해 가장 최근에 사용된 list filter 기준으로 표준 list 페이지의 PageReference 객체를 반환한다. 예를 들어 표준 컨트롤러가 contact이고 사용자가 마지막으로 본 필터된 목록이 New Last Week라면, 지난 주에 생성된 contact들이 표시된다. |

예를 들어 다음 페이지는 account를 갱신할 수 있게 해준다. Save를 클릭하면 표준 컨트롤러에서 save 액션이 트리거되고 account가 갱신된다.

```xml
<apex:page standardController="Account">
<apex:form>
<apex:pageBlock title="My Content" mode="edit">
<apex:pageBlockButtons>
<apex:commandButton action="{!save}" value="Save"/>
</apex:pageBlockButtons>
<apex:pageBlockSection title="My Content Section" columns="2">
<apex:inputField value="{!account.name}"/>
<apex:inputField value="{!account.site}"/>
<apex:inputField value="{!account.type}"/>
<apex:inputField value="{!account.accountNumber}"/>
</apex:pageBlockSection>
</apex:pageBlock>
</apex:form>
</apex:page>
```

> **Note:** 이 페이지가 account 데이터를 표시하려면 유효한 account 레코드의 ID가 페이지 URL의 쿼리 파라미터로 지정되어야 한다. 예:
> `https://MyDomain_login_URL/apex/myPage?id=001x000xxx3Jsxb`

> **Note:** 표준 컨트롤러에서 `save`, `quicksave`, `edit`, `delete` 액션에 연결된 명령 버튼과 링크는 **사용자가 적절한 권한을 가진 경우에만** 렌더링된다. 마찬가지로 특정 레코드가 페이지에 연결되어 있지 않으면 `edit`·`delete` 액션에 연결된 명령 버튼과 링크는 렌더링되지 않는다.

### Validation Rules와 표준 컨트롤러

사용자가 표준 컨트롤러를 사용하는 Visualforce 페이지에서 데이터를 입력했는데 그 데이터가 validation rule 오류를 일으키면, 그 오류를 Visualforce 페이지에 표시할 수 있다.

- validation rule 오류 위치가 `<apex:inputField>` 컴포넌트에 연결된 필드라면, 오류는 거기에 표시된다.
- validation rule 오류 위치가 페이지 상단으로 설정되어 있다면, `<apex:page>` 안에 `<apex:pageMessages>` 또는 `<apex:messages>` 컴포넌트를 사용해 오류를 표시한다.

### 표준 컨트롤러를 사용하는 페이지 스타일링

표준 컨트롤러에 연결된 페이지는 지정된 객체에 연결된 표준 Salesforce 페이지의 스타일을 자동으로 상속한다. 즉, 지정된 객체의 tab이 선택된 것으로 표시되고, 그 tab에 연결된 색상이 모든 페이지 요소를 스타일링하는 데 사용된다.

`<apex:page>` 태그의 `tabStyle` 속성으로 표준 컨트롤러를 사용하는 페이지의 스타일링을 재정의할 수 있다. 예를 들어 다음 페이지는 Account 표준 컨트롤러를 사용하지만 Opportunities tab을 강조하고 Opportunity tab의 노란색 색상으로 페이지를 렌더링한다.

```xml
<apex:page standardController="Account" tabStyle="Opportunity">
</apex:page>
```

`MyCustomObject`에 연결된 스타일링을 사용하려면:

```xml
<apex:page standardController="Account" tabStyle="MyCustomObject__c">
</apex:page>
```

커스텀 Visualforce tab에 연결된 스타일링을 사용하려면, 속성을 (label이 아닌) tab의 name에 더블 언더스코어와 `tab`이라는 단어를 붙인 값으로 설정한다. 예를 들어 name이 `Source`이고 label이 `Sources`인 Visualforce tab의 스타일링을 사용하려면:

```xml
<apex:page standardController="Account" tabStyle="Source__tab">
</apex:page>
```

또는 자체 커스텀 스타일시트와 인라인 스타일로 표준 컨트롤러 페이지 스타일을 재정의할 수도 있다.

### 객체 접근성 확인 (Checking for Object Accessibility)

사용자에게 객체를 볼 권한이 부족하면, 그 객체를 렌더링하기 위해 컨트롤러를 사용하는 모든 Visualforce 페이지는 접근 불가능해진다. 이 오류를 피하려면, Visualforce 컴포넌트가 컨트롤러에 연결된 객체에 사용자가 접근 권한을 가진 경우에만 렌더링되도록 한다.

객체의 접근성은 다음과 같이 확인할 수 있다.

```text
{!$ObjectType.objectname.accessible}
```

이 표현식은 `true` 또는 `false` 값을 반환한다. 예를 들어 표준 Lead 객체에 접근 가능한지 확인하려면:

```text
{!$ObjectType.Lead.accessible}
```

커스텀 객체의 경우 코드는 유사하다.

```text
{!$ObjectType.MyCustomObject__c.accessible}
```

페이지의 특정 부분이 사용자가 객체에 접근 가능한 경우에만 표시되도록 하려면 컴포넌트에 `rendered` 속성을 사용한다. 사용자가 객체에 접근할 수 없을 때는 대체 메시지를 제공한다.

```xml
<apex:page standardController="Lead">
<apex:pageBlock rendered="{!$ObjectType.Lead.accessible}">
<p>This text will display if you can see the Lead object.</p>
</apex:pageBlock>
<apex:pageBlock rendered="{! NOT($ObjectType.Lead.accessible) }">
<p>Sorry, but you cannot see the data because you do not have access to the Lead
object.</p>
</apex:pageBlock>
</apex:page>
```

## 표준 리스트 컨트롤러 (Standard List Controller)

표준 리스트 컨트롤러를 사용하면 **레코드 집합(set of records)**을 표시하거나 그에 대해 동작하는 Visualforce 페이지를 만들 수 있다. 레코드 집합으로 동작하는 기존 Salesforce 페이지의 예로는 list 페이지, related list, mass action 페이지가 있다.

### 지원 객체 (14종)

표준 리스트 컨트롤러는 다음 객체와 함께 사용할 수 있다.

- Account
- Asset
- Campaign
- Case
- Contact
- Contract
- Idea
- Lead
- Opportunity
- Order
- Product2
- Solution
- User
- Custom objects (커스텀 객체)

### 표준 리스트 컨트롤러를 Visualforce 페이지에 연결하기

표준 리스트 컨트롤러를 사용하는 방법은 표준 컨트롤러와 매우 유사하다. 먼저 `<apex:page>` 컴포넌트에 `standardController` 속성을 설정한 다음, 같은 컴포넌트에 `recordSetVar` 속성을 설정한다.

예를 들어 account의 표준 리스트 컨트롤러를 페이지에 연결하려면 다음 마크업을 사용한다.

```xml
<apex:page standardController="Account" recordSetVar="accounts">
```

> **Note:** `<apex:page>` 태그에서 `standardController` 속성을 사용할 때는 `controller` 속성을 동시에 사용할 수 없다.

`recordSetVar` 속성은 페이지가 리스트 컨트롤러를 사용함을 나타낼 뿐 아니라, 레코드 컬렉션의 변수 이름을 설정한다. 이 변수는 레코드 컬렉션의 데이터에 접근하는 데 사용된다.

### 리스트 컨트롤러로 데이터 접근하기

#### 표현식 구문으로 레코드 접근 (Access Records with Expression Syntax)

페이지를 리스트 컨트롤러에 연결한 후에는 expression language 구문으로 레코드 집합에 대해 동작할 수 있다. 예를 들어 account 테이블을 만들려면 다음 마크업을 사용한다.

```xml
<apex:page standardController="Account" recordSetVar="accounts" tabstyle="account"
sidebar="false">
<apex:pageBlock>
<apex:pageBlockTable value="{!accounts}" var="acc">
<apex:column value="{!acc.name}"/>
</apex:pageBlockTable>
</apex:pageBlock>
</apex:page>
```

이 예제는 `<apex:pageBlockTable>` 컴포넌트로 데이터 테이블을 생성한다. `value` 속성은 표준 리스트 컨트롤러가 로드한 변수 `{!accounts}`(=`<apex:pageBlockTable>`이 루프를 도는 레코드 목록)로 설정된다. 목록의 각 레코드에 대해 `<apex:pageBlockTable>`은 레코드를 `acc` 변수에 할당하고, `<apex:column>` 컴포넌트가 정의한 행으로 테이블의 새 행을 구성한다.

> **표준 리스트 컨트롤러를 사용하면 반환된 레코드는 현재 view가 정의한 첫 번째 데이터 열을 기준으로 자동 정렬된다.** extension이나 custom 리스트 컨트롤러를 사용하면 정렬 방법을 제어할 수 있다.

> **Note:** 이 페이지는 요청에 filter를 지정하지 않으므로 마지막으로 사용된 filter로 표시된다. filter 사용에 대해서는 아래 [List View 섹션](#list-view-standard-list-controllers)을 참조.

표준 컨트롤러와 마찬가지로, Lightning Platform API의 쿼리처럼 expression language 구문으로 관련 레코드의 데이터를 가져올 수 있다 — **자식→부모 관계 최대 5레벨, 부모→자식 관계 1레벨** traversal 가능.

#### ID로 레코드 접근 (Access Records with IDs)

일반적인 페이지 상호작용에서 사용자는 페이지로 이동하기 전에 list view에서 레코드를 선택하고, Visualforce가 이를 컨트롤러로 보낸다. 컨트롤러에 직접 선택 레코드를 설정하여 레코드를 수동으로 지정할 수도 있다.

> 표준 리스트 컨트롤러는 `StandardSetController` Apex 클래스 기반이다. Apex 컨트롤러에서 레코드 목록을 설정하려면 `ApexPages.StandardSetController.setSelected()` 메서드를 사용한다. (메서드 시그니처·반환 타입은 [[ApexPages Namespace]] 참조)

```xml
<apex:page standardController="Account" recordSetVar="accounts"
extensions="MyControllerExtension">
<apex:pageBlock >
<apex:pageBlockTable value="{!accounts}" var="acc">
<apex:column value="{!acc.name}"/>
</apex:pageBlockTable>
</apex:pageBlock>
</apex:page>
```

```apex
public with sharing class MyControllerExtension {
private ApexPages.StandardSetController setController;
public MyControllerExtension(ApexPages.StandardSetController setController) {
this.setController = setController;
Account [] records = [SELECT Id, Name FROM Account LIMIT 30];
setController.setSelected(records);
}
}
```

`MyControllerExtension`의 생성자에서 Account 객체의 ID와 Name을 선택하는 SOQL 요청을 만들고 처음 30개 결과로 제한한다. 그런 다음 `setController.setSelected(records)`를 정의하여 페이지 로드 시 레코드가 선택되도록 한다.

> **Note:** **표준 리스트 컨트롤러는 최대 10,000개 레코드를 반환할 수 있다.** custom 컨트롤러는 더 큰 결과 집합으로 작업할 수 있다.

레코드 ID 목록을 multiple query 파라미터로 포함하여 URL로 전달하는 것도 가능하다. 예를 들어 3개 Account ID를 가진 URL은 다음과 같다.
`/apex/pageName?ids=001xx00account1&ids=001xx00account2&ids=001xx00account3`

> **주의:** 일부 브라우저는 URL 길이에 하드 제한이 있다. URL에 ID가 너무 많으면 그 제한에 도달하여 페이지가 오작동할 가능성이 커진다. URL 문자열에 ID를 수동으로 포함하는 대신, 컨트롤러에 선택 레코드를 설정하는 것이 더 좋다.

### 표준 리스트 컨트롤러 액션

표준 리스트 컨트롤러는 액션 메서드를 지원한다. 액션 메서드는 페이지 이벤트가 발생할 때(사용자가 버튼을 클릭하거나 페이지 영역 위로 마우스를 올릴 때 등) 로직이나 내비게이션을 수행한다. 액션 메서드는 다음 태그 중 하나의 `action` 속성에서 `{! }` 표기법으로 호출한다(표준 컨트롤러와 동일한 태그 목록 — `<apex:commandButton>`, `<apex:commandLink>`, `<apex:actionPoller>`, `<apex:actionSupport>`, `<apex:actionFunction>`, `<apex:page>`).

다음 표는 **모든 표준 리스트 컨트롤러가 지원하는 액션 메서드**를 설명한다.

| Action | Description |
|---|---|
| `save` | 새 레코드를 삽입하거나 변경된 기존 레코드를 갱신한다. 작업 완료 후 save 액션은 사용자를 원래 페이지(알 수 있는 경우)로 되돌리거나 home 페이지로 보낸다. |
| `quicksave` | 새 레코드를 삽입하거나 변경된 기존 레코드를 갱신한다. save 액션과 달리 quicksave는 사용자를 다른 페이지로 리다이렉트하지 않는다. |
| `list` | 해당 객체에 대해 가장 최근에 사용된 list filter 기준으로(사용자가 `filterId`를 지정하지 않은 경우) 표준 list 페이지의 PageReference 객체를 반환한다. |
| `cancel` | 편집 작업을 중단한다. 작업 완료 후 cancel 액션은 사용자가 원래 편집을 호출한 페이지로 되돌린다. |
| `first` | 집합의 첫 번째 페이지 레코드를 표시한다. |
| `last` | 집합의 마지막 페이지 레코드를 표시한다. |
| `next` | 집합의 다음 페이지 레코드를 표시한다. |
| `previous` | 집합의 이전 페이지 레코드를 표시한다. |

다음 예제에서 사용자는 account 레코드를 볼 filter를 지정한다.

```xml
<apex:page standardController="Account" recordSetVar="accounts">
<apex:form>
<apex:selectList value="{!filterid}" size="1">
<apex:selectOptions value="{!listviewoptions}"/>
</apex:selectList>
<apex:commandButton value="Go" action="{!list}"/>
</apex:form>
</apex:page>
```

이 페이지는 `StandardSetController` Apex 클래스 기반의 표준 Account 리스트 컨트롤러에 연결된다. `{!listviewoptions}` 표현식은 `StandardSetController`의 `getListViewOptions()` 메서드를 호출하여 사용 가능한 list view로 평가된다. 사용자가 선택한 list view는 컨트롤러의 `filterId` 속성에 바인딩된다. `filterId`가 변경되면 페이지에서 사용할 수 있는 레코드가 filter에 따라 변경된다. 따라서 사용자가 Go를 클릭하면 표준 list 페이지에 선택된 필터 레코드가 표시된다.

> `getListViewOptions()`·`filterId`의 Apex 메서드 시그니처는 [[ApexPages Namespace]] 참조.

### 리스트 컨트롤러로 Pagination

리스트 컨트롤러가 있는 Visualforce 페이지에 pagination을 추가하려면 `next`·`previous` 액션을 사용한다.

다음 예제에서 Visualforce 페이지는 표준 Account 리스트 컨트롤러에 연결된다. 페이지에는 `action` 속성이 각각 `{!previous}`·`{!next}`로 설정된 두 개의 `<apex:commandLink>` 컴포넌트가 있다. 사용자가 링크 중 하나를 클릭하면 연결된 액션이 호출되고 account 레코드의 subset이 페이지에 표시된다.

> **Note:** 이 예제에서 페이지는 요청에 filter를 지정하지 않으므로 마지막으로 사용된 filter로 표시된다.

```xml
<apex:page standardController="Account" recordSetvar="accounts">
<apex:pageBlock title="Viewing Accounts">
<apex:form id="theForm">
<apex:pageBlockSection >
<apex:dataList var="a" value="{!accounts}" type="1">
{!a.name}
</apex:dataList>
</apex:pageBlockSection>
<apex:panelGrid columns="2">
<apex:commandLink action="{!previous}">Previous</apex:commandlink>
<apex:commandLink action="{!next}">Next</apex:commandlink>
</apex:panelGrid>
</apex:form>
</apex:pageBlock>
</apex:page>
```

> **기본적으로 리스트 컨트롤러는 페이지당 20개 레코드를 반환한다.** 각 페이지에 표시되는 레코드 수를 제어하려면 controller extension을 사용해 `pageSize`를 설정한다. (`setPageSize()`/`getPageSize()` 시그니처는 [[ApexPages Namespace]] 참조)

> **Note:** pagination을 사용할 때, 행이 수정된 컬렉션(extension 액션으로 추가된 행 포함)에서는 예외가 발생한다. 이 경우 오류 메시지는 표준 동작을 따르며 `<apex:pageMessages>` 또는 `<apex:messages>` 컴포넌트로 페이지에 표시할 수 있다.

> ℹ️ 위 마크업의 `recordSetvar`(소문자 v)와 닫는 태그 `</apex:commandlink>`(소문자)는 PDF 원문 표기를 [sic] 그대로 보존한 것이다. 실제 대소문자 정규형은 `recordSetVar`·`</apex:commandLink>`이다.

### List View와 표준 리스트 컨트롤러
<a id="list-view-standard-list-controllers"></a>

Visualforce 페이지에 필터된 레코드 목록을 표시하려면 페이지를 표준 리스트 컨트롤러에 연결한다.

많은 Salesforce 페이지는 페이지에 표시되는 레코드를 필터링할 수 있는 list view를 포함한다. 예를 들어 opportunities home 페이지에서 list view 드롭다운에서 My Opportunities를 선택하면 본인 소유 opportunity만 볼 수 있다. 리스트 컨트롤러에 연결된 모든 페이지에서 list view를 만들 수 있다.

> **Note:** Visualforce에서 date filter는 Lightning Experience·Salesforce Classic의 filter와 다르게 계산된다. Visualforce 페이지용 list view에 date filter를 만들 때는 정확한 날짜가 아니라 항상 **날짜 범위(date range) 내**로 필터링한다.
>
> 예를 들어 `Date/Time Closed equals 1/25/2023` filter의 case list view는 Visualforce 페이지에서 2023년 1월 25일 특정 시각(예: 오후 4시)에 닫힌 case만 표시한다. Lightning Experience나 Classic에서는 같은 filter가 2023년 1월 25일 24시간 동안 닫힌 모든 case를 표시한다. Visualforce에서 이 case 집합을 표시하려면 filter를 `Date/Time Closed greater or equal 1/25/2023 AND Date/Time Closed less than 1/26/2023`으로 조정한다.

예를 들어 list view가 있는 간단한 account 목록을 만들려면 다음 마크업으로 페이지를 만든다.

```xml
<apex:page standardController="Account" recordSetvar="accounts">
<apex:pageBlock title="Viewing Accounts">
<apex:form id="theForm">
<apex:panelGrid columns="2">
<apex:outputLabel value="View:"/>
<apex:selectList value="{!filterId}" size="1">
<apex:actionSupport event="onchange" rerender="list"/>
<apex:selectOptions value="{!listviewoptions}"/>
</apex:selectList>
</apex:panelGrid>
<apex:pageBlockSection >
<apex:dataList var="a" value="{!accounts}" id="list">
{!a.name}
</apex:dataList>
</apex:pageBlockSection>
</apex:form>
</apex:pageBlock>
</apex:page>
```

페이지는 `StandardSetController` Apex 클래스 기반의 표준 Account 리스트 컨트롤러에 연결된다. `{!listviewoptions}` 표현식은 `StandardSetController`의 `getListViewOptions()` 메서드를 호출하여 사용 가능한 list view로 평가된다. 사용자가 드롭다운에서 선택한 값은 컨트롤러의 `filterId` 속성에 바인딩된다. `filterId`가 변경되면 페이지에서 사용할 수 있는 레코드가 filter에 따라 변경되고, `<apex:datalist>`가 갱신된 list view로 렌더링된다.

> **Note:** 기본적으로 리스트 컨트롤러는 페이지당 20개 레코드를 반환한다. 각 페이지에 표시되는 레코드 수를 제어하려면 controller extension을 사용해 `StandardSetController`의 `pageSize`를 설정한다.

edit 페이지에서도 list view를 사용할 수 있다.

```xml
<apex:page standardController="Opportunity" recordSetVar="opportunities"
tabStyle="Opportunity"
sidebar="false">
<apex:form>
<apex:pageBlock>
<apex:pageMessages/>
<apex:pageBlock>
<apex:panelGrid columns="2">
<apex:outputLabel value="View:"/>
<apex:selectList value="{!filterId}" size="1">
<apex:actionSupport event="onchange" rerender="opp_table"/>
<apex:selectOptions value="{!listviewoptions}"/>
</apex:selectList>
</apex:panelGrid>
</apex:pageBlock>
<apex:pageBlockButtons>
<apex:commandButton value="Save" action="{!save}"/>
</apex:pageBlockButtons>
<apex:pageBlockTable value="{!opportunities}" var="opp" id="opp_table">
<apex:column value="{!opp.name}"/>
<apex:column headerValue="Stage">
<apex:inputField value="{!opp.stageName}"/>
</apex:column>
<apex:column headerValue="Close Date">
<apex:inputField value="{!opp.closeDate}"/>
</apex:column>
</apex:pageBlockTable>
</apex:pageBlock>
</apex:form>
</apex:page>
```

> **Note:** 사용자가 list view를 변경하면 컬렉션에 수정된 행이 있을 경우 예외가 발생한다. 이 경우 오류 메시지 처리는 표준 동작을 따르며 `<apex:pageMessages>` 또는 `<apex:messages>` 컴포넌트로 페이지에 표시할 수 있다.

### 리스트 컨트롤러로 레코드 편집

리스트 컨트롤러로 레코드 집합을 편집할 수도 있다. 예를 들어 다음 마크업으로 페이지를 만들면 opportunity의 Stage와 Close Date를 갱신·저장할 수 있는 페이지가 나타난다.

```xml
<apex:page standardController="Opportunity" recordSetVar="opportunities"
tabStyle="Opportunity" sidebar="false">
<apex:form >
<apex:pageBlock >
<apex:pageMessages />
<apex:pageBlockButtons >
<apex:commandButton value="Save" action="{!save}"/>
</apex:pageBlockButtons>
<apex:pageBlockTable value="{!opportunities}" var="opp">
<apex:column value="{!opp.name}"/>
<apex:column headerValue="Stage">
<apex:inputField value="{!opp.stageName}"/>
</apex:column>
<apex:column headerValue="Close Date">
<apex:inputField value="{!opp.closeDate}"/>
</apex:column>
</apex:pageBlockTable>
</apex:pageBlock>
</apex:form>
</apex:page>
```

> ℹ️ PDF 원문은 이 예제 직후 결과 화면을 가리키며 *“like the following:For more information…”*(콜론 뒤 공백 누락)으로 이어진다 — 자세한 내용은 PDF의 *Mass Updating Records with a Custom List Controller*(p.143) 참조. **PDF에는 이 지점에 결과 화면 스크린샷이 있으나 본 wiki에는 텍스트 설명만 포함한다.**

> **Note:** 리스트 컨트롤러에서 `save`, `quicksave`, `edit` 액션에 연결된 명령 버튼과 링크는 **사용자가 적절한 권한을 가지지 않으면** 렌더링되지 않는다. 마찬가지로 특정 레코드가 페이지에 연결되어 있지 않으면 `edit` 액션에 연결된 명령 버튼과 링크는 렌더링되지 않는다.

## 표준 컨트롤러 vs 표준 리스트 컨트롤러 — 언제 무엇을

| 구분 | 표준 컨트롤러 | 표준 리스트 컨트롤러 |
|---|---|---|
| 대상 | 단일 레코드 | 레코드 집합(최대 10,000개) |
| 연결 속성 | `standardController` | `standardController` + `recordSetVar` |
| 지원 객체 | API로 쿼리 가능한 모든 객체 | 14종 (Account~User + Custom) |
| 데이터 참조 | `{!account.name}` | `{!accounts}`(컬렉션) |
| 액션 (개수) | save·quicksave·edit·delete·cancel·list (6) | save·quicksave·list·cancel·first·last·next·previous (8) |
| Pagination | 없음 | `next`·`previous` (기본 20레코드/page, `pageSize`로 조정) |
| List view | 해당 없음 | `filterId`·`listviewoptions`로 지원 |
| 기반 Apex 클래스 | `StandardController` | `StandardSetController` |

> 두 컨트롤러의 기반 Apex 클래스(`StandardController`·`StandardSetController`)의 생성자·메서드 전체 시그니처는 [[ApexPages Namespace]]에서 다룬다.
