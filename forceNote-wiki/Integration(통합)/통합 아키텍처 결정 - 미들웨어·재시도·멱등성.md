# 통합 아키텍처 결정 — 미들웨어·재시도·멱등성

> 외부 시스템 연동을 설계할 때 두 개의 큰 결정: **(1) 직결(point-to-point) vs 미들웨어(ESB/MuleSoft)** 로 연결 위상을 정하고, **(2) 재시도·멱등성**으로 신뢰성(중복 없는 at-least-once)을 확보한다. 개별 API의 사용법이 아니라 "어떤 위상·어떤 신뢰성 계약을 고를지" 판단 프레임.

> [!note] 근거: Salesforce **Integration Patterns and Practices**(공식 아키텍트 가이드)와 **Data Integration Decision Guide**. 📖 [Integration Patterns and Practices](https://developer.salesforce.com/docs/atlas.en-us.integration_patterns_and_practices.meta/integration_patterns_and_practices/)

## 1. 위상 결정 — Point-to-Point vs 미들웨어(ESB)

### Point-to-Point (직결)

각 시스템이 상대 시스템과 **직접** 연결한다. Salesforce가 ERP를 직접 호출하고, 프로토콜 변환·데이터 변환·재시도 로직을 **각 연결마다 자체 구현**한다.

- 장점: 인프라 추가 없음, 지연(latency)이 낮음, 소규모에서 단순·저비용.
- 단점: 시스템이 늘면 연결이 **N×M로 폭발**(스파게티). 한 시스템의 스키마가 바뀌면 그와 연결된 모든 상대를 수정. 모니터링·에러 처리가 연결마다 흩어진다.

### 미들웨어 / ESB (MuleSoft 등 허브-스포크)

Salesforce와 외부 시스템 **사이에 계층**을 둔다. Salesforce는 ERP가 아니라 미들웨어와 대화하고, 미들웨어가 변환·라우팅·에러 처리·모니터링을 담당한다.

- 장점: 연결이 **N+M**로 수렴(각 시스템은 허브 1곳만 봄), 변환/오케스트레이션 중앙화, 통합 재사용, 거버넌스·중앙 모니터링·재시도(dead-letter queue).
- 단점: 미들웨어 자체가 비용·운영·단일 장애점(HA 필요), 홉(hop) 하나가 더 생겨 지연 증가.

```text
// 구조 예시 — 실제 원본 다이어그램 아님
Point-to-Point (N×M)              Hub-Spoke / ESB (N+M)
SF ─── ERP                        SF ──┐
SF ─── Billing                    ERP ─┤
SF ─── DWH            vs          Bill ┼── [ MuleSoft / ESB ] ── (변환·라우팅·재시도·모니터링)
ERP ── Billing                    DWH ─┘
ERP ── DWH                        각 시스템은 허브 1곳만 연결
(연결 6개, 3시스템)               (연결 4개, 새 시스템=허브에 1개만 추가)
```

### 결정 표

| 신호 | Point-to-Point | 미들웨어(ESB/MuleSoft) |
|---|---|---|
| 연결할 시스템 수 | 소수(2~3), 안정적 | 다수·계속 증가 |
| 데이터 변환 필요 | 거의 없음(포맷 일치) | 복잡한 매핑·정규화 필요 |
| 프로토콜 차이 | 양쪽 다 REST/JSON | REST↔SOAP↔FTP↔레거시 혼재 |
| 오케스트레이션 | 단일 호출로 끝 | 여러 시스템 조율·순차/보상 트랜잭션 |
| 재사용 | 재사용 불필요 | 여러 팀·앱이 같은 통합 재사용 |
| 모니터링/거버넌스 | 각자 로그로 충분 | 중앙 관측·감사·SLA 필요 |
| 비용·팀 역량 | 미들웨어 도입 부담 큼 | 이미 MuleSoft/ESB 보유·전담 팀 |

> **언제 point-to-point가 정답인가:** 연결 대상이 소수이고 안정적이며, 변환·오케스트레이션이 거의 없고, 조직에 미들웨어가 없을 때. 이럴 때 ESB 도입은 과잉설계다. Salesforce Decision Guide도 "**MuleSoft 등 ETL/ESB가 이미 있으면 활용**하라"고 조건부로 권한다 — 없는데 억지로 도입하라는 게 아니다.

> **Salesforce의 6대 통합 패턴**(직결이든 미들웨어든 그 위에서 고르는 상호작용 패턴): Remote Process Invocation—Request and Reply(동기 요청·응답), Remote Process Invocation—Fire and Forget(발신 후 진행), Batch Data Synchronization(주기적 대량 동기화), Remote Call-In(외부가 SF를 호출), UI Update Based on Data Changes(데이터 변경으로 UI 갱신), Data Virtualization(복제 없이 외부 데이터 조회). 위상 결정 후 상호작용은 이 표에서 고른다.

## 2. 아웃바운드 통지 방식 비교 — Platform Event vs Outbound Message vs REST 콜아웃

Salesforce에서 "레코드가 바뀌면 외부에 알린다"를 구현하는 세 가지 대표 방식. 코드량·전달 보장·순서 특성이 서로 달라, 위상(1절)을 정한 뒤 **이 표에서 통지 메커니즘**을 고른다.

| 축 | **Platform Event** | **Outbound Message** | **REST 콜아웃(Apex)** |
|---|---|---|---|
| 트리거 계기 | Apex `EventBus.publish` · Flow · API · Pub/Sub | **선언적** — Workflow Rule 또는 레코드 트리거 Flow(Winter '22부터 Flow 지원) | Apex 코드에서 `Http.send`(트리거/큐어블/스케줄에서 발동) |
| 코드 필요 | 발행 최소 · 구독 코드 필요 | **무코드**(엔드포인트 WSDL만 구현) | 콜아웃·재시도 전부 직접 코드 |
| 프로토콜/전송 | 이벤트 버스(Pub/Sub API gRPC · CometD) | **SOAP** 메시지를 외부 엔드포인트로 push | 임의(REST/JSON 등 원하는 대로) |
| 전달 보장 | 버스에 **1회 발행** — SF측 재시도 없음, 구독자가 replay로 복구 | **보장 전달** — ACK 못 받으면 재시도 | 없음 — 실패 처리는 직접 구현 |
| 재시도 | 없음(구독자 책임). 트리거 소비 실패 시 `EventBus.RetryableException` | **최대 24시간** 지수 백오프 자동 재시도 후 큐에서 제거 | 직접(Queueable 자기 재큐·백오프) |
| 순서 | 발행 순서 보장(파티션 내), replayId 순차 | **순서 미보장** — 메시지가 큐 순서와 무관하게 독립 재시도돼 뒤바뀔 수 있음 | 호출자가 제어 |
| 중복 | at-least-once(구독자 멱등 필요) | **동일 notification ID**가 재시도에도 유지 → 수신자가 ID로 중복 판별 | 타임아웃 후 재시도 시 중복 가능 |
| 페이로드 | 이벤트 정의 필드(커스텀 `__e`) | sObject 필드 셋, **한 SOAP 메시지에 최대 100 notification** 묶음 | 임의 페이로드 자유 설계 |
| 유지 기간 | 표준 24h / 고용량 72h 저장(replay 창) | 큐에서 24h 재시도 창 | 해당 없음 |
| 언제 | 다수 구독자·느슨한 결합·이벤트 스트림, ESB/외부가 replay 관리 | **간단한 point-to-point 실시간 push를 무코드로**, SOAP 수신 가능한 단일 엔드포인트 | 동기 요청·응답, 응답값을 즉시 써야 하거나 완전한 제어가 필요할 때 |

> **Outbound Message의 정체:** 코드 없이 Workflow/Flow에서 **SOAP 메시지를 외부 URL로 밀어내는 선언적 통지**다. 강점은 무코드 + 24h 보장 재시도, 약점은 SOAP 종속·순서 미보장·중복 가능. 그래서 수신자는 **notification ID 기반 멱등 처리**(→ 4절)가 사실상 필수다. 반대로 다수 구독·스트리밍은 Platform Event, 응답을 바로 소비해야 하면 REST 콜아웃이 맞다. 이벤트 상세는 [[Platform Event 통합 패턴]], 콜아웃 재시도는 [[Queueable + Callout 패턴]] 참조.

## 3. 실시간 vs 배치 결정 프레임

같은 데이터를 옮기더라도 **언제·얼마나 자주** 옮기느냐가 아키텍처를 가른다. 이벤트/동기 콜아웃(실시간) 대 Bulk/스케줄(배치)의 트레이드오프.

| 축 | **실시간**(Platform Event · 동기 콜아웃 · CDC) | **배치**(Bulk API · 스케줄 Apex · ETL) |
|---|---|---|
| 지연(latency) | 초 이하 ~ 수초(near-real-time 1~30초) | 분~시간(스케줄 주기) |
| 데이터 신선도 | 변경 즉시 반영 — 라이브 대시보드·알림·상담원 화면 | 마지막 배치 시점 기준(지연 허용) |
| API/자원 소모 | 건별 처리라 트랜잭션당 호출 多 — 고임팩트 건에 한정 | **대량을 소수 호출로** 흡수(델타 동기화 시 변경량에 비례) |
| 복잡도 | 이벤트 버스·재시도·멱등·순서 처리 필요 | 잡 스케줄·오류 재처리 위주로 단순 |
| 비용 | 인프라·모니터링 부담 큼 | 상대적으로 저렴, 야간 창 활용 |
| 적합 | 결제·재고·SLA처럼 **즉시성이 비즈니스 가치** | 야간 마스터 동기화·리포팅·대량 마이그레이션 |

> **실무 결론:** 흔히 **혼합**이 정답이다 — 크리티컬한 소량 변경은 실시간 push, 대량 마스터 데이터는 스케줄 배치. "이 데이터가 몇 초 늦으면 실제로 손해인가?"가 아니라면 배치가 API·비용·복잡도에서 유리하다. Salesforce 6대 패턴에서 실시간=Remote Process Invocation, 배치=Batch Data Synchronization에 대응한다.

## 4. 재시도(Retry)와 멱등성(Idempotency)

### 왜 필요한가 — at-least-once의 함정

Salesforce의 비동기 이벤팅(**Platform Events·Change Data Capture·Outbound Message**)과 대부분의 재시도 아키텍처는 **at-least-once(최소 한 번)** 전달을 채택한다. 즉 **같은 메시지가 두 번 이상 도착**하거나, 순서가 뒤바뀔 수 있다. 이건 버그가 아니라 계약이다.

- Outbound Message·이벤트 재시도는 **긍정 ACK를 못 받으면 다시 보낸다.** 실제로는 처리에 성공했는데 ACK만 유실돼도 재전송된다 → 수신자가 대비 안 하면 **중복 처리**.
- 사용자가 버튼을 여러 번 누르거나 미들웨어가 타임아웃 후 재시도하면 같은 요청이 반복된다.

> 공식 지침(Integration Patterns): "Salesforce가 메시지를 몇 번 보낼지, 사용자가 버튼을 몇 번 누를지 제어할 수 없으므로 **수신자(receiver)를 멱등하게 설계**해야 한다." 재시도는 **항상 멱등 연산과 짝**을 이뤄야 한다.

### 멱등성 설계 — External Id + upsert

멱등(idempotent) = **같은 요청을 몇 번 처리해도 결과가 같다**. Salesforce에서 가장 효과적인 도구는 **External ID 필드 + upsert**다.

```apex
// Account에 external system의 고유 키를 담는 Unique External Id 필드(Legacy_Id__c) 사용
// 같은 Legacy_Id__c로 여러 번 upsert해도 레코드는 1개 — 있으면 update, 없으면 insert
public static void ingest(String extKey, String name) {
    Account a = new Account(Name = name, Legacy_Id__c = extKey);
    // upsert의 키를 External Id 필드로 지정 → Salesforce가 매칭 후 생성/갱신
    Database.upsert(a, Account.Legacy_Id__c, /*allOrNone*/ false);
}
```

REST로도 동일하다 — `PATCH /services/data/v67.0/sobjects/Account/Legacy_Id__c/{extKey}` (external id upsert). 같은 키로 재전송돼도 중복 레코드가 생기지 않는다. 자세한 REST upsert 규약은 [[REST API]] 참조.

- **필수 조건:** External Id 필드에 **Unique** 체크. 미체크면 여러 매칭 시 에러 또는 중복.
- 표준 External Id 대신 **idempotency-key**(요청 단위 UUID)를 이벤트/요청에 실어 보내고, 그 값을 Unique 필드에 저장해 upsert하면 "동일 요청 재전송"을 레코드 수준에서 차단한다.

### 이벤트 소비자 멱등 처리

Platform Event 수신 트리거는 같은 이벤트가 두 번 와도 안전해야 한다.

```apex
// 구조 예시 — 이벤트에 실린 idempotency 키(Message_Id__c)를 처리 로그에 upsert해 중복 차단
trigger OrderEventTrigger on Order_Event__e (after insert) {
    List<Processed_Message__c> logs = new List<Processed_Message__c>();
    for (Order_Event__e e : Trigger.new) {
        // 이미 처리한 Message_Id__c면 upsert가 기존 로그를 갱신(no-op) → 부수효과 재실행 안 함
        logs.add(new Processed_Message__c(External_Message_Id__c = e.Message_Id__c));
    }
    // Unique External_Message_Id__c 로 upsert; DUPLICATE_VALUE를 잡아 중복은 skip
    Database.upsert(logs, Processed_Message__c.External_Message_Id__c, false);
    // 신규로 삽입된 것만 실제 비즈니스 처리 (부수효과 1회 보장)
}
```

durable **replay(재생)** 전략(replayId 저장 후 복구)과 짝지으면 다운타임 후에도 누락 없이 복구된다. Platform Event 발행·구독·replay는 [[Platform Event 통합 패턴]]·[[Pub-Sub API (gRPC) — Platform Event·CDC 구독]] 참조.

### 아웃바운드 콜아웃 재시도

Salesforce → 외부 콜아웃이 실패(타임아웃·5xx)했을 때의 재시도 설계.

| 방식 | 재시도 메커니즘 | 비고 |
|---|---|---|
| **Queueable + Callout** | catch에서 지수 백오프 후 `System.enqueueJob(this)`로 자기 재큐 | 시도 횟수 카운터를 멤버 변수로 들고 상한 도달 시 중단. [[Queueable + Callout 패턴]] |
| **Platform Event 재구독** | 트리거에서 실패 시 `EventBus.RetryableException` throw → 플랫폼이 재전달 | 최대 재시도 횟수·지연 플랫폼 관리 |
| **Scheduled/Batch 재처리** | 실패 레코드를 상태 필드로 마킹 후 스케줄러가 재시도 | 대량·주기적 재동기화(Batch Data Sync 패턴) |
| **미들웨어 재시도** | ESB의 retry + dead-letter queue | 재시도 로직을 SF 밖으로 위임 |

> [!warning] 재시도는 **반드시 멱등 연산 위에서만** 안전하다. 멱등하지 않은 연산(단순 insert, 잔액 +N 같은 누적 부수효과)을 재시도하면 중복·이중 반영이 발생한다. 재시도를 넣기 전에 "이 연산을 두 번 실행해도 결과가 같은가?"를 먼저 보장하라.

## 5. 미들웨어에서 Salesforce API 일일 한도 관리 전략

외부/미들웨어가 Salesforce를 자주 호출하면 **일일 API 요청 한도**를 소진해 조직 전체 통합이 막힌다(`REQUEST_LIMIT_EXCEEDED`). 미들웨어 계층에서 호출 자체를 줄이고 관측하는 것이 핵심.

| 전략 | 방법 |
|---|---|
| **왕복 최소화(Composite)** | Composite API로 최대 25개 서브요청을 **1 API 호출**로 묶는다. 부모-자식 생성, 조회+갱신을 한 번에. 건별 개별 호출을 배치로 접어 호출 수를 대폭 절감. |
| **대량은 Bulk** | 2,000건 초과 데이터 로드는 Bulk API 2.0로. 대량을 소수 잡으로 처리하고, 표준 일일 REST/SOAP 한도와 **별도 할당**을 쓴다(레코드 기준 한도). |
| **캐싱** | 피클리스트·제품 카탈로그 등 잘 안 바뀌는 참조 데이터는 미들웨어가 **캐시**하고 변경 시에만 갱신 → 반복 쿼리를 로컬 조회로 대체. |
| **백오프·서킷브레이커** | 5xx·타임아웃엔 **지터 포함 지수 백오프 + 재시도 상한 + 서킷브레이커**. 단 `REQUEST_LIMIT_EXCEEDED`는 롤링 창이라 짧은 주기 재시도가 자멸적 — 작업을 보류하고 한도 회복 후 재개. |
| **한도 모니터링** | `GET /services/data/vXX.0/limits`로 `DailyApiRequests` 잔량을 주기 확인. 안전 임계치(예: 잔여 30%) 아래면 비필수 호출을 지연·스킵하는 게이트를 미들웨어에 둔다. |

> 구체적 수치(일일 API 호출 한도·Bulk 레코드 한도·Composite 서브요청 상한 등)는 [[Salesforce 한도·할당량 레퍼런스 (API·Bulk·Metadata·SOQL·VF)]]에 위임한다. 실시간 건별 호출이 한도를 빨리 태우므로, 3절의 실시간 vs 배치 판단과 함께 본다.
