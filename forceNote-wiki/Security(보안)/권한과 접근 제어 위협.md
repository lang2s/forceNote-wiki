# 권한과 접근 제어 위협

> 권한이 있는 리소스만 접근하도록 보장하는 위협 영역 — Apex의 CRUD/FLS bypass, sharing violation, privilege escalation을 USER_MODE·sharing 키워드·describe 메서드·stripInaccessible로 방어한다.

---

## 위협 개요

권한이 있는 리소스만 접근하도록 보장한다. 흔한 취약점: **directory traversal, insecure direct object reference, authorization bypass, privilege escalation.**

### User Roles

- **Unauthenticated** — login page만 접근.
- **Regular** — maintenance·setup을 제외한 접근.
- **Administrator** — full 접근.

privilege escalation = limited 사용자가 admin 권한을 획득하는 것. (CWE/SANS Top 25 참조)

### Test Your Application for Vulnerabilities (질문 전수)

인증 page는 무엇인가, role/group은 무엇인가, 각 role의 capability·resource는 무엇인가, 접근은 어떻게 부여되는가, 인증된 member를 검증하는가, 잘못된 role data를 어떻게 처리하는가, 외부 role data를 어떻게 처리하는가, proxy로 자신의 role을 수정하면 어떻게 되는가, 가정 사항은 무엇인가. Salesforce 앱은 CRUD/FLS/Sharing을 강제한다. (Trailhead Secure Server-Side Development, Salesforce Code Analyzer)

## Protect from CRUD/FLS Vulnerabilities

기본적으로 Apex의 data 작업(SOQL/DML/SOSL)은 **system mode, full CRUD access**로 실행된다. **AccessLevel class**가 두 모드를 표현한다: `AccessLevel.SYSTEM_MODE`, `AccessLevel.USER_MODE`. optional accessLevel 파라미터로 전달한다.

### accessLevel 파라미터 지원 메서드 (전수)

- `Database.query`
- `Database.getQueryLocator`
- `Database.countQuery`
- `Search.query`
- Database DML methods (insert, update, upsert, merge, delete)

> **Note:** Database DML을 USER_MODE로 실행하면 `SaveResult.getErrors()`로 record별 error에 접근할 수 있다. 각 `Database.Error`가 `getFields()`로 원인 field를 제공한다. insert in user mode는 `DmlException`의 `getFieldNames()`로 FLS 위반 field를 획득한다.

### accessLevel 파라미터 필수 메서드 (전수)

- `Database.queryWithBinds`
- `Database.getQueryLocatorWithBinds`
- `Database.countQueryWithBinds`

### WITH USER_MODE / WITH SYSTEM_MODE

SOQL/SOSL에서 모드를 표시한다. USER_MODE는 sharing rule, CRUD, FLS를 강제한다.

> **Note:** `WITH SECURITY_ENFORCED`보다 `WITH USER_MODE`를 권장한다. `WITH SECURITY_ENFORCED`는 AppExchange package에서 불허된다. **WITH USER_MODE 장점(전수):**
> - polymorphic field(Owner, Task.whatId) 처리
> - SOQL SELECT의 모든 절(WHERE 포함) 처리
> - 모든 FLS error 발견(`SECURITY_ENFORCED`는 첫 error만). USER_MODE에서는 `QueryException`의 `getInaccessibleFields()`로 전체 access error를 확인.

> `WITH USER_MODE`의 키워드 시그니처·문법 상세는 [[WITH USER_MODE]] 참조. 여기서는 권한 위협 관점의 장점·필수 메서드 목록만 다룬다.

### User Mode Operations 예제 (전수, 원문)

```apex
// Access
List<Account> a = [SELECT Id FROM Account WITH USER_MODE];

// Insert
insert as user o;
// 또는
database.insert(o, AccessLevel.USER_MODE);

// Update
update as user a;
// 또는
database.update(a, AccessLevel.USER_MODE);

// SOSL
List<List<SObject>> r = search.query(queryString, AccessLevel.USER_MODE);
```

> **Note:** USER_MODE는 CRUD/FLS/Sharing을 강제하므로 Sharing/CRUD/FLS 위반을 회피한다.

## Use CRUD/FLS Check Methods

`Schema.DescribeSObjectResult`, `Schema.DescribeFieldResult` 메서드로 현재 access를 확인한다.

### DescribeSObjectResult helper 함수 (전수, 원문 예제)

- **isCreateable()** — object Create + field Edit 권한 확인.
  ```apex
  Schema.sObjectType.Opportunity.isCreateable();
  Schema.sObjectType.Opportunity.fields.Amount.isCreateable();
  ```
- **isAccessible()** — field read 권한.
  ```apex
  Schema.sObjectType.Opportunity.isAccessible();
  Schema.sObjectType.Opportunity.fields.ExpectedRevenue.isAccessible();
  ```
- **isUpdateable()** — field·object Edit 권한.
  ```apex
  Schema.sObjectType.Opportunity.isUpdateable();
  Schema.sObjectType.Opportunity.fields.StageName.isUpdateable();
  ```
- **isDeletable()** — record delete 권한. update/create/access와 달리 **CRUD check만**(field 아닌 object).
  ```apex
  Lead.sObjectType.getDescribe().isDeleteable();
  ```

> CRUD/FLS describe 메서드의 wrapper 패턴(`CanTheUser`)은 [[CanTheUser]] 참조.

## Enforce Field and Object-level Data Protection — stripInaccessible()

`stripInaccessible()`는 query/subquery 결과에서 inaccessible field·relationship field를 strip한다. DML 전에 inaccessible sObject field를 제거하고, untrusted source의 sObject를 sanitize한다(exception 방지). source records와 동일 순서로 반환되는 list를 생성한다. query되지 않은 field는 null(exception 없음). **AggregateResult SObject type은 미지원**(사용 시 exception).

> **Note:** DML 이슈 방지를 위해 **ID field는 제거하지 않는다.**

`isSet` 메서드로 제거된 inaccessible field를 식별한다. 예제(원문):

```apex
SObjectAccessDecision securityDecision = Security.stripInaccessible(sourceRecords);
// ...
System.debug(c.isSet('social_security_number__c')); // prints "false"
```

> `Security.stripInaccessible`/`SObjectAccessDecision`의 메서드 상세는 [[StripInaccessible]]·[[Safely]] 참조.

> **Note (CRUD/FLS bypass 허용 케이스 — 전수):**
> - Roll-Up summary/aggregate(직접 노출 안 함)
> - custom object·field를 CRUD·FLS로 직접 접근 불가하게 수정
> - 고권한 메서드에서 custom object 접근(non-admin 불가)
> - 자기 namespace의 custom object를 bespoke security policy로 접근
>
> → AppExchange Security Review에 문서화 필수.

## Protect from Sharing Violations — Sharing Keywords (전수, 원문 예제)

Apex는 보통 system context에서 실행된다(object permission/FLS/sharing rule 미적용). 특정 class가 sharing rule을 강제할 수 있다.

- **With sharing** — 현재 사용자 sharing rule 강제.
  ```apex
  public with sharing class ProjectService {
    // [SELECT Id, Name, Status__c FROM Project__c]
  }
  ```
- **Without sharing** — sharing rule 미강제.
  ```apex
  public without sharing class ProjectServiceWithoutSharing { }
  ```
- **Inherited sharing** — 호출 class와 동일 sharing mode로 실행. 의도를 명확히 하고 누락 선언 모호성을 회피.
  ```apex
  public inherited sharing class ProjectServiceInheritedSharing { }
  ```

영향: SOQL/SOSL이 fewer rows를 반환할 수 있고, DML이 권한 부족 시 fail할 수 있다.

> **Note:** sharing 설정은 메서드가 **정의된** class의 설정을 기준으로 한다(호출 class 아님). with sharing 메서드를 without sharing class가 호출해도 with sharing이 강제된다. class-level security는 항상 필요하다.

### General Considerations (전수)

- DB 작업 class에 sharing 선언을 항상 포함.
- 일반적으로 "with sharing"(least privilege) — guest user 접근 controller class는 예외일 수 있다.
- "inherited sharing"/"without sharing"은 의식적 결정으로 사용.
- **Apex trigger는 명시적 sharing 선언이 불가하며 without sharing으로 실행** → Handler class로 분리.

> **Note (sharing bypass 허용 케이스 — 전수):**
> - site/community에서 guest user 접근을 의도적으로 차단
> - 자기 namespace의 custom object를 bespoke policy로 접근(AppExchange 문서화 필수, standard object는 admin 소유라 해당 안 됨).

(Trailhead Secure Server-Side Development, Use the with sharing... Keywords 참조)
