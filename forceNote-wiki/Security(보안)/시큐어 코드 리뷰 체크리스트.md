# 시큐어 코드 리뷰 체크리스트

> 배포·PR 전에 위협 영역별로 훑는 크로스커팅 점검표 — 각 항목은 "확인할 것 + 방어 한 줄 + 상세 노트 링크"로만 구성하고, 방어 메커니즘 자체는 링크된 위협 노트에서 다룬다.

---

## 이 노트의 위치

이 노트는 개별 방어법을 **다시 설명하지 않는다.** Secure Coding Guide의 위협 영역들(XSS·CSRF·SOQL Injection·Redirect·CRUD/FLS·민감 데이터·세션·TLS)을 리뷰어가 한 화면에서 훑을 수 있도록 **체크박스 + 라우팅**만 모은 절차 노트다. 각 항목의 "왜/어떻게"는 링크된 노트로 들어가서 확인한다.

> **근거 (Secure Coding Guide, Ch10 — Test Your Application for Vulnerabilities):**
> *"For Salesforce applications, ensure that the data operations enforce CRUD, FLS, and Sharing checks for the objects and fields. ... To detect CRUD and FLS violations in your code, consider using a code scanner such as Salesforce Code Analyzer."*

> **리뷰 주기 (Secure Coding 개요 Ch2 — Implement Regular Reviews):** 변경·신규 배포 후 정기 검토를 수행한다. 체크리스트는 1회성 관문이 아니라 배포마다 반복하는 절차다.

---

## 배포/PR 전 위협별 체크리스트

각 행: **확인 항목(체크박스) · 방어 요약 1줄 · 상세 노트**. `🔍`은 [[dx-code-analyzer-run]](Salesforce Code Analyzer)로 정적 탐지가 유력한 항목(수동 리뷰를 대체하지 않고 보조).

| ✔ | 위협 | 확인 항목 | 방어 요약 (1줄) | 상세 | 🔍 |
|---|---|---|---|---|---|
| ☐ | XSS | 모든 사용자 입력 출력에 **컨텍스트별 인코딩** 적용(HTML/JS/URL/CSS). `escape="false"`·`<script>`/`<style>` 내 merge-field 감사 | 브라우저 파싱 단계 시퀀스에 맞춰 인코딩 함수 시퀀스 적용 | [[XSS 방어]] | 🔍 |
| ☐ | SOQL/SOSL Injection | 정적 SOQL `:bind` / 동적은 `queryWithBinds` · 식별자(필드·오브젝트·정렬)는 **화이트리스트** | 값은 바인딩으로, 식별자는 allowlist로 문법에서 분리 | [[SOQL Injection 위협]] | 🔍 |
| ☐ | CSRF | **page-load DML 금지** — `<apex:page action>`·생성자·`init`/`connectedCallback`/`renderedCallback`에서 state-change 없음 | state-changing은 오직 user-triggered 이벤트에서만 | [[CSRF 방어]] | |
| ☐ | Arbitrary Redirect | 리다이렉트 대상 URL을 **known-safe allowlist**로만 매칭. `retURL`이 sanitize된다고 가정 금지 | `PageReference`·`window.location`·hash fragment redirect를 allowlist 검증 | [[Arbitrary Redirect 방어]] | |
| ☐ | CRUD/FLS 강제 | SOQL/DML이 **USER_MODE**(또는 `as user`)로 실행, 사전 분기 필요 시 `CanTheUser`, 신뢰 못 할 JSON은 `stripInaccessible` | 데이터 작업이 현재 사용자의 오브젝트·필드 권한을 강제 | [[권한과 접근 제어 위협]] · [[CRUD·FLS·공유 강제 결정 가이드]] | 🔍 |
| ☐ | 민감 데이터 저장 | **시크릿 하드코딩 금지** · `System.debug()`/로그/이메일에 secret 노출 금지 · GET query string에 credential 금지 | 시크릿은 Protected Custom Metadata/Setting·Named Credential·Crypto로 | [[민감 데이터 저장]] | 🔍(부분) |
| ☐ | Sharing 선언 | DB 작업 클래스에 **명시적 sharing 선언**(with/without/inherited). 트리거 로직은 핸들러로 위임 | 레코드 가시성(행)을 의식적으로 결정. v67.0 기본값은 `with sharing` | [[Sharing 키워드 (with·without·inherited sharing)]] · [[CRUD·FLS·공유 강제 결정 가이드]] | 🔍 |
| ☐ | 세션 ID·브라우저 통신 | managed package의 session ID 오용 없음 · `postMessage` targetOrigin/origin allowlist · WebSocket은 `wss://` + Origin 검증 | cross-origin bridge와 session ID를 defensive하게 처리 | [[세션 ID와 브라우저 통신 위협]] | |
| ☐ | TLS/통신 | 모든 리소스 HTTPS 로드 · 인증·PII cookie에 **Secure flag** · 아웃바운드 콜아웃 TLS 확인 | Salesforce는 TLS 1.2+ 독점. HTTP 다운그레이드 차단 | [[Secure Communications (TLS)]] | |
| ☐ | Flow 실행 컨텍스트 | UI/Screen flow는 User Mode · 권한 필요 부분만 System Mode 서브플로우로 분리 · "available for input" 변수 검증 | 최소 권한 원칙으로 플로우 실행 모드 설계 | [[Secure Coding 개요]] | |

> 위 표의 방어 요약은 **한 줄 라우팅**이다. 실제 구현(인코딩 함수 시퀀스·bind 문법·AccessLevel 시그니처 등)은 반드시 상세 노트로 들어가 확인한다 — 이 체크리스트에서 기억으로 코드를 쓰지 않는다.

## 정적 분석 연동 — Salesforce Code Analyzer

Secure Coding Guide는 CRUD/FLS 위반 탐지에 **Salesforce Code Analyzer** 같은 코드 스캐너 사용을 권장한다. 위 표의 `🔍` 항목은 정적 분석이 유력하게 잡아내는 범주다(CRUD/FLS 위반, SOQL Injection, `escape="false"` 기반 XSS, sharing 위반 등).

- 실행 절차·명령 변환·위반 필터링은 실행형 스킬 [[dx-code-analyzer-run]]에 위임한다(지식=이 위키 · 실행=스킬).
- 어떤 질문에 어떤 스킬·위키 패턴이 매핑되는지는 디스패처 [[스킬 ↔ 위키 토픽 맵]]을 참조한다.

```text
// 구조 예시 — 실제 동작 코드 아님 (리뷰 게이트에서의 스캔 호출 개념)
sf code-analyzer run --rule-selector security
  └─ CRUD/FLS violation      → 체크리스트 "CRUD/FLS 강제" 행 확인
  └─ SOQL injection          → 체크리스트 "SOQL/SOSL Injection" 행 확인
  └─ ApexSharingViolations   → 체크리스트 "Sharing 선언" 행 확인
```

> **한계:** 정적 분석은 수동 코드 리뷰를 **대체하지 않는다.** CSRF(page-load DML), redirect allowlist, 세션 ID 오용, postMessage origin 검증 등은 대부분 **사람이 직접 로직을 읽어야** 판단된다(`🔍` 없는 행). 시크릿 하드코딩·약한 암호는 Code Analyzer 룰(`ApexBadCrypto`·하드코딩 크리덴셜 탐지)이 **부분적으로만** 잡으므로(`🔍(부분)`) 수동 확인이 여전히 필요하다. 자동 탐지는 게이트의 1차 필터, 체크리스트는 전수 관문이다.
