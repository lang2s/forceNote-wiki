# 배포 방법 결정 가이드

> Salesforce 메타데이터·코드를 org 사이로 옮기는 6가지 경로(Change Sets · Metadata API/`sf project deploy` · DX source · Unlocked Package · Tooling API · DevOps Center)를 **결정 축**(에디션·UI/CLI·Git·CI·granularity·아티팩트 재사용·역할·validation/quick deploy)으로 비교해 "이 상황엔 이것"을 고른다. 각 경로의 절차·API·필드 상세는 해당 노트로 위임한다 — 여기서는 **무엇을 언제 고르는가**만 다룬다.

---

## 이 노트의 범위 (scope)

이 노트는 **선택(decision)** 만 다룬다. 각 경로가 *어떻게* 동작하는지(단계별 절차, CLI 플래그, sObject 필드, 파이프라인 객체 모델)는 아래 위임 링크의 정본 노트가 소관한다. 메커니즘 재서술을 피하고, 축별 사실만 원본 노트에서 대조해 표로 압축한다.

| 경로 | 정본(메커니즘) 노트 |
|---|---|
| Change Sets | [[Change Sets 배포]] |
| Metadata API / `sf project deploy` (Org Dev Model) | [[Metadata API 빌드·릴리스 워크플로]] · [[Metadata API File-Based 호출]] |
| DX source (Scratch Org · Source Tracking) | [[DX 개발 워크플로]] · [[Salesforce DX 개요]] |
| Unlocked Package | [[Unlocked Package 릴리스와 설치]] · [[Unlocked Package 개념과 준비]] |
| Tooling API | [[Tooling API 배포]] |
| DevOps Center | [[DevOps Center]] |

> Apex 관점(개발 org → production)만의 5경로 카탈로그는 [[Apex 배포 방법]] 참조. 이 노트는 거기에 DX source·Unlocked Package를 동급 결정옵션으로 올린 **크로스커팅 매트릭스**다.

## 결정 매트릭스 (6경로 × 8축)

기호 압축 전 원본 값 매핑을 먼저 고정한다(추측 금지):
`✅` = 지원/가능 · `❌` = 불가/미지원 · `△` = 조건부/부분 · `—` = 소스에 명시 없음(빈칸으로 두고 추측하지 않음).

| 축 | Change Sets | Metadata API / `sf project deploy` | DX source | Unlocked Package | Tooling API | DevOps Center |
|---|---|---|---|---|---|---|
| **인터페이스** | UI (Salesforce Classic) | CLI + API | CLI + VS Code | CLI + URL 설치 | API (REST/SOAP) | UI (파이프라인·클릭) |
| **에디션·환경 제약** | Enterprise·Performance·Unlimited·Database.com **만** · Developer Edition ❌ · connected org 간(sandbox↔prod) | 소스 미명시 · sandbox/production | Scratch Org엔 Dev Hub 필요 · 배포 대상은 any org | 패키지 생성·버전엔 Dev Hub 필요 · 설치는 any org | Special Access(View All Data + Author Apex/Customize App) · **production에서 Apex 클래스·트리거 생성/편집/삭제 불가** | 매니지드 패키지 설치 필요(에디션 소스 미명시) |
| **Git/VCS 통합** | ❌ | ✅ | ✅ (VCS = source of truth) | ✅ | ✅ (source control integration) | ✅ (저장소 브랜치 병합 — Heroku 위임) |
| **CI 자동화** | ❌ | ✅ | ✅ | ✅ | ✅ | △ 파이프라인 기반 promote(선언적 변경관리) — 범용 CI 도구는 아님 |
| **Granularity (배포 단위)** | 컴포넌트 수동 선택 (diff/추적 없음) | manifest(`package.xml`)/변경분/전체 — deployment `.zip` | source format + source tracking 자동 변경감지 (`--metadata`/`--source-dir`/`--manifest`) | 패키지 전체(버전 단위·불변) | **복합 타입 내 단일 요소**(클래스·트리거 하나) — 최소 단위 | work item = 메타데이터 변경 묶음(변경 추적) |
| **아티팩트 재사용** | ❌ (target org로 1회성 업로드) | △ deployment `.zip`(버전 불변 아님) | △ source 파일(패키지 아님) | ✅ **버전 불변 아티팩트(04t)** — 다수 org 설치·Push Upgrade | △ `MetadataContainer` 재사용 가능·멤버는 배포 후 재사용 불가 | ❌ (아티팩트가 아니라 파이프라인 promote) |
| **validation-only / quick deploy** | — (PDF Salesforce Help 영역, 미수록) | ✅ `sf project deploy validate`→job ID→`sf project deploy quick` (검증 후 **10일 이내**) | ✅ 동일 `validate`/`quick` 사용 | — (validate/quick 모델 아님; 설치 시 `--apex-compile`, Upgrade Type Delete/DeprecateOnly/Mixed) | ✅ `IsCheckOnly=true`(저장 없이 컴파일 = check-only) — 단 `MetadataContainerMember` 지정 시만 | — (소스 미수록) |
| **주 역할** | 어드민·개발자 (동일 org 패밀리) | 고객·비-ISV 파트너 | 개발자 (source-driven) | 개발자·다중 org 배포·조직 간 재사용 (ISV는 managed 2GP) | 개발 도구/IDE·대화형 앱 | 선언적 + 코드 개발자 |

> **에디션 제약 요약:** 6경로 중 **하드 에디션 제약이 명시된 것은 Change Sets 뿐**이다(Enterprise·Performance·Unlimited·Database.com에서만 제공, Developer Edition 불가). Tooling API·DX·Metadata API는 에디션이 아니라 **권한/환경**(Dev Hub·Special Access·production Apex 편집 금지)이 제약이다.
>
> **아티팩트 재사용 = Unlocked Package 고유:** 한 번 만든 버전(04t)을 여러 구독 org에 설치·업그레이드·Push Upgrade할 수 있는 **재사용 가능한 불변 아티팩트**는 Unlocked Package(및 ISV용 managed 2GP)만 제공한다. 나머지는 target을 향한 1회성 전송(Change Sets)이거나 소스/`.zip` 배포다.

## 이 상황엔 이것 (빠른 선택)

- **클릭만으로 sandbox → production, Git·CI 불필요** → **Change Sets** (단 Enterprise+ 에디션, connected org 필요). Developer Edition이면 사용 불가 → CLI 계열로.
- **VCS를 source of truth로 팀 협업 + CI/CD 파이프라인** → **DX source**(`sf project deploy`) — source tracking으로 변경분 자동 감지, `validate`→`quick`로 안전 배포.
- **sandbox 기반 Org Development Model에서 스테이징을 거쳐 릴리스** → **Metadata API / `sf project deploy` 워크플로** — deployment `.zip`을 Developer→Pro→Full Sandbox로 승격 후 production quick deploy.
- **여러 org에 같은 앱을 버전으로 배포·업그레이드(핫픽스 Push Upgrade)** → **Unlocked Package** — 재사용 가능한 불변 아티팩트가 핵심. (AppExchange 유통이면 ISV용 managed 2GP)
- **IDE·도구에서 클래스/트리거 하나만 컴파일·저장(최소 granularity)** → **Tooling API** — 복합 타입 내 단일 요소 변경. production Apex 편집은 불가.
- **선언적·코드 혼합 팀의 변경 관리를 UI 파이프라인으로 통합(코드 없이 promote)** → **DevOps Center** — work item 단위 변경 추적 + dev→prod promote.

### 결정 트리 (요약)

```text
// 구조 예시 — 실제 원본 다이어그램 아님 (위 결정 축을 트리로 재구성)
배포해야 한다
├─ 여러 org에 버전으로 재배포/업그레이드? ── 예 → Unlocked Package (ISV 유통이면 managed 2GP)
├─ 요소 하나(클래스/트리거)만 도구에서? ──── 예 → Tooling API (IsCheckOnly로 check-only)
├─ UI 파이프라인·선언적 변경관리 원함? ───── 예 → DevOps Center
├─ Git/VCS + CI/CD 자동화? ──────────────── 예 → DX source · Metadata API (validate→quick, 10일 내)
└─ 클릭만·Git 없이 sandbox→prod? ──────────
      ├─ 에디션 Enterprise+ & connected org → Change Sets
      └─ 아니면(예: Developer Edition)      → CLI 계열(DX source / Metadata API)
```

## 축별 주의점 (결정에 영향)

- **validation-only 후 quick deploy 유효기간:** `sf project deploy validate`로 얻은 job ID의 quick deploy는 **검증 후 10일 이내**에 production에 실행해야 한다(만료 시 재검증). 상세 워크플로는 [[Metadata API 빌드·릴리스 워크플로]].
- **production Apex 개발 금지:** 어떤 경로든 production org에서 Apex를 직접 개발/편집할 수 없다. Tooling API 컨테이너 배포도 production Apex 편집은 불가다. 배포 전 코드 커버리지 **75% 이상**이 필요하다(상세: [[DX 개발 워크플로]] · [[Apex 배포 방법]]).
- **대량 배포 시 커버리지 객체 주의:** 단일 Metadata API 배포에 Apex 클래스가 매우 많으면 코드 커버리지 객체가 영향을 받는 케이스가 있다 — 정확한 임계값·동작은 [[Apex 배포 방법]]의 Metadata API 섹션 참조(여기서는 재서술하지 않음).
- **Change Sets의 validation/모드 옵션:** 이 매트릭스의 Change Sets validation-only 칸은 원본 PDF가 Salesforce Help 영역으로 넘긴 부분이라 `—`로 둔다(추측하지 않음). 근거·경계는 [[Change Sets 배포]]의 scope 섹션.
