# 실행 컨텍스트와 트랜잭션

> "실행 컨텍스트(execution context)"는 Apex Developer Guide가 **Apex 트랜잭션**이라 부르는 것과 같은 개념 — 진입점 하나에서 시작해 하나의 단위로 실행·커밋·롤백되는 작업 묶음. 이 노트는 그 개념을 한데 모으고, 각 세부(한도·컨텍스트 식별·저장 순서·익명 실행)는 전용 노트로 위임하는 **개념 허브**다.

---

## 실행 컨텍스트 = Apex 트랜잭션

> **원문:** "An Apex transaction is sometimes referred to as an execution context. This guide uses the term Apex transaction."

두 용어는 같은 것을 가리킨다. 하나의 **진입점(entry point)** 에서 시작된 코드가 그와 함께 실행되는 모든 것(호출하는 클래스·트리거·플로우 등)을 아울러 **하나의 단위**로 취급하는 실행 범위다.

> **원문:** "An Apex transaction represents a set of operations that are executed as a single unit. All DML operations in a transaction must complete successfully. If an error occurs in one operation, the entire transaction is rolled back and no data is committed to the database."

경계 안에서 일어나는 모든 작업 — 외부 코드(클래스·트리거) 호출 포함 — 은 단일 작업 단위다. 모든 작업이 오류 없이 끝난 **후에만** DB에 커밋되고, 중간 단계에서 오류가 나면 모든 DB 변경이 롤백되고 트랜잭션은 커밋되지 않는다.

---

## 트랜잭션 경계 — 무엇이 "한 트랜잭션"인가

트랜잭션 경계(진입점)가 될 수 있는 것:

| 진입점 | 예 |
|---|---|
| Trigger | `before/after insert·update·delete` 등 |
| 클래스 메서드 | `MyService.doWork()` |
| Anonymous block | Developer Console / `executeAnonymous()` |
| Visualforce page | 컨트롤러 액션 |
| Custom Web service 메서드 | `webservice`/Apex REST |
| 그 외 진입점 | Aura 컨트롤러, LWC에서 호출한 `@AuraEnabled`, 비동기 Apex 클래스 등 ("Any other entry point to an Apex transaction") |

한 진입점에서 시작해 그 안에서 호출하는 모든 것이 **한 트랜잭션**이다.

> **원문 예:** "a custom Apex Web service method causes a trigger to fire, which in turn calls a method in a class. In this case, all changes are committed to the database only after all operations in the transaction finish executing and don't cause any errors."

### 비동기는 새 실행 컨텍스트다

`@future`·Queueable·Batch·Scheduled로 비동기 작업을 enqueue하면, 그 작업은 **현재 트랜잭션의 일부가 아니라 별도의 새 실행 컨텍스트**에서 나중에 실행된다. 그래서 새 거버너 한도 세트(대개 비동기 한도)를 받는다.

- **Batch:** "Each execution of a batch Apex job is considered a discrete transaction." — 1,000건을 scope 200으로 돌리면 5개의 개별 트랜잭션. 각 트랜잭션마다 거버너 한도가 초기화되고, 첫 트랜잭션이 성공하면 이후 트랜잭션이 실패해도 **첫 트랜잭션 결과는 롤백되지 않는다.**
- **Queueable와 롤백 관계:** "If an Apex transaction rolls back, any queueable jobs queued for execution by the transaction aren't processed." — 부모 트랜잭션이 롤백되면 그 트랜잭션이 enqueue한 Queueable은 아예 실행되지 않는다.
- 어느 비동기 방식을 언제 쓰는지는 → [[비동기 컨텍스트 선택]].

## static 변수의 트랜잭션 수명

> **원문:** "A static variable is static only within the scope of the Apex transaction. It's not static across the server or the entire organization. The value of a static variable persists within the context of a single transaction and is reset across transaction boundaries."

핵심 함정 정리:

- static 변수는 **서버 전역·조직 전역 상태가 아니다.** 요청(트랜잭션)이 끝나면 리셋된다 — 요청 간에 값이 유지되지 않는다.
- **한 트랜잭션 안에서는** 유지된다. "if an Apex DML request causes a trigger to fire multiple times, the static variables persist across these trigger invocations." → 한 DML이 트리거를 여러 번 발화시켜도 static 값은 그 발화들 사이에 살아있다.
- 따라서 static의 정당한 용도는 **한 트랜잭션 내 상태 공유**: "all triggers that a single transaction spawns can communicate with each other by viewing and updating static variables in a related class."

### 재귀 가드 (recursion guard) 패턴

> **원문:** "A recursive trigger can use the value of a class variable to determine when to exit the recursion."

```apex
// Apex Developer Guide 원문 발췌
public class P {
    public static boolean firstRun = true;
}

trigger T1 on Account (before delete, after delete, after undelete) {
    if(Trigger.isBefore){
        if(Trigger.isDelete){
            if(p.firstRun){
                Trigger.old[0].addError('Before Account Delete Error');
                p.firstRun=false;   // 이후 재귀 발화에서는 스킵
            }
        }
    }
}
```

static이 트랜잭션 수명을 갖기 때문에 이 플래그는 같은 트랜잭션의 후속 트리거 재발화에는 살아있고, 다음 요청에는 깨끗하게 초기화된다. 트리거 아키텍처에서의 활용은 → [[TriggerHandler 패턴]].

## 거버너 한도가 컨텍스트 단위인 이유

> **원문:** "These limits count for each Apex transaction. For Batch Apex, these limits are reset for each execution of a batch of records..."

거버너 한도는 **트랜잭션(=실행 컨텍스트) 단위로 카운트·초기화**된다. 멀티테넌트 환경에서 한 트랜잭션이 공유 자원을 독점하지 못하게 막는 장치이므로, 한도의 회계 단위가 자연히 트랜잭션이다. 그래서:

- 새 트랜잭션(비동기 job, Batch의 각 execute)에 진입하면 SOQL·DML·CPU·Heap 카운터가 초기화된다.
- 동기(6MB Heap·100 SOQL·10,000ms CPU) vs 비동기(12MB·200 SOQL·60,000ms)로 한도가 갈리는 것도 "어떤 컨텍스트인가"에 달렸다.
- 테스트의 `startTest`/`stopTest`: 그 사이 코드는 **새 거버너 한도 세트**를 받는다("assigned a new set of governor limits") — 컨텍스트를 새로 추가하는 개념.

수치 표·`Limits` 클래스·방어 패턴 전체 → [[Governor Limits]].

## 부분/전체 롤백과 예외

트랜잭션은 원자적(atomic)이다. 예외가 처리되지 않으면 그 전에 처리된 DML까지 **전부 롤백**된다.

> **원문 예:** validation rule 실패로 예외 발생 → "all DML operations processed before this exception are rolled back."

| 상황 | 결과 |
|---|---|
| 진입점 안에서 uncaught 예외 | 전체 트랜잭션 롤백, 커밋 없음 |
| `Database.insert(records, false)` 등 부분 성공 허용 | 실패 레코드만 제외, 성공분은 커밋 |
| `Database.setSavepoint()` + `Database.rollback()` | Savepoint 이후 변경만 롤백(부분 롤백) |
| `System.LimitException` (거버너 초과) | catch 불가 — 강제 롤백 |
| **Payments 트랜잭션** | 예외 — 오류가 나도 커밋됨(결제 게이트웨이에서 이미 발생) |
| 비동기(Batch) — 한 트랜잭션 실패 | 이미 커밋된 **다른** 트랜잭션은 롤백 안 됨 |

allOrNothing·Savepoint 등 DML 레벨 롤백 제어 상세 → [[DML 패턴]].
