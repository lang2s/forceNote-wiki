# 테스트 전략

> Apex 테스트의 구조화 원칙. 단위 테스트 격리, 외부 의존성 모킹, 체계적인 검증.

---

## 개념

### 왜 Apex 테스트 전략이 중요한가

Salesforce는 배포 시 **코드 커버리지 75% 이상**을 강제한다. 그러나 커버리지 달성만을 목표로 한 테스트는 실제 버그를 잡지 못한다. 잘 설계된 테스트 전략은 다음을 보장한다.

- **회귀 방지**: 새 기능 추가나 리팩터링 시 기존 동작이 깨지지 않음을 빠르게 확인
- **배포 안전성**: Sandbox → Production 배포 시 릴리즈 유효성 검증
- **설계 피드백**: 테스트하기 어려운 코드는 대부분 설계 문제(강결합, 정적 의존성)가 있다는 신호

### Apex 테스트의 핵심 제약

Apex 테스트 환경에는 일반 코드와 다른 제약이 있다.

- **외부 Callout 불가**: 테스트에서 실제 HTTP 요청을 보내면 예외 발생 → `HttpCalloutMock` 필수
- **SOSL 결과 없음**: Full-Text Search 인덱스가 갱신되지 않으므로 항상 빈 결과 → `Test.setFixedSearchResults()` 필수
- **Governor Limit 별도 집계**: 테스트 데이터 생성(`@TestSetup`, `insert`) 과정이 Limit을 소모하므로, 실제 테스트 대상 코드의 Limit과 분리하기 위해 `Test.startTest()` / `Test.stopTest()`로 경계를 명확히 해야 한다
- **비동기 실행 동기화**: `@future`, `Queueable`, `Batch` 작업은 `Test.stopTest()` 호출 시점에 동기적으로 실행된다

### 테스트 격리 원칙

좋은 Apex 테스트는 **외부 상태에 의존하지 않는다.** 테스트 데이터는 테스트 내부에서 생성하고, 외부 시스템(HTTP, 다른 Apex 클래스의 부수 효과)은 모킹한다. 하나의 테스트 메서드가 다른 테스트의 성공에 영향을 주어서는 안 된다.

## 테스트 클래스 기본 구조

```apex
@isTest
private class BookApiServiceTest {

    // 공통 데이터 초기화
    @TestSetup
    static void makeData() {
        Account acct = new Account(Name = 'Test Account');
        insert acct;
    }

    // 정상 케이스
    @isTest
    static void searchBooks_returnsResults_withValidKeyword() {
        Test.setMock(HttpCalloutMock.class, new SuccessCalloutMock());

        Test.startTest();
        List<BookModel> result = new BookApiService().searchBooks('salesforce');
        Test.stopTest();

        Assert.isFalse(result.isEmpty(), '결과가 있어야 함');
        Assert.areEqual('Salesforce Book', result[0].title);
    }

    // 실패 케이스
    @isTest
    static void searchBooks_throwsException_on404() {
        Test.setMock(HttpCalloutMock.class, new ErrorCalloutMock(404, '{}'));

        Test.startTest();
        try {
            new BookApiService().searchBooks('unknown');
            Assert.fail('예외가 발생해야 함');
        } catch (BookApiService.BookNotFoundException e) {
            Assert.isNotNull(e.getMessage());
        }
        Test.stopTest();
    }
}
```

## Assert 모범 사례

```apex
// ✅ 명시적 메시지 포함
Assert.areEqual(expected, actual, '설명 메시지');
Assert.isTrue(condition, '이 조건이 true여야 하는 이유');

// ✅ 예외 테스트는 fail() 포함
try {
    methodThatShouldThrow();
    Assert.fail('예외가 발생해야 함'); // 예외 없으면 테스트 실패
} catch (ExpectedException e) {
    Assert.isNotNull(e.getMessage());
}

// ❌ 피해야 할 패턴
System.assertEquals(expected, actual); // 구형 API
Assert.isTrue(list.size() > 0);        // isEmpty() 사용 권장
Assert.areEqual(1, list.size());       // 더 명확
```

## Test.startTest / Test.stopTest 사용

```apex
// Governor limit 초기화 — 외부 callout 포함 시 필수
Test.startTest();
    List<BookModel> result = service.searchBooks('sf'); // callout 실행
Test.stopTest();
// stopTest()에서 @future, Queueable, Batch가 동기 실행됨
```

> [!tip] startTest/stopTest 역할
> - Governor limit을 초기화하여 테스트 자체의 DML/쿼리를 테스트 대상에서 분리
> - `stopTest()` 호출 시 비동기 작업(@future, Queueable, Batch)이 강제 실행됨

## Assert·Test 메서드 레퍼런스

> `source: salesforce_apex_reference_guide.pdf` — Assert Class / Test Class (System 네임스페이스). 시그니처 전수.

### System.Assert 메서드 (전수)

`System.Assert`는 테스트에서 조건을 단언하는 정적 메서드 모음이다. **모든 메서드는 `public static void`** 이며, 각 단언은 `msg`(맨 뒤 `String` 파라미터, 실패 시 에러 메시지에 붙는 커스텀 문구)를 받는 오버로드와 받지 않는 오버로드 **두 벌**을 제공한다. 단언이 실패하면 fatal error가 던져져 코드 실행이 즉시 멈추며, **로그에는 예외로 기록되지만 `try/catch`로는 잡을 수 없다.**

| 메서드 | 시그니처 (msg 포함형) | 단언 내용 |
|---|---|---|
| `areEqual` | `areEqual(Object expected, Object actual, String msg)` | 두 인자가 **같다** |
| `areNotEqual` | `areNotEqual(Object notExpected, Object actual, String msg)` | 두 인자가 **다르다** |
| `isTrue` | `isTrue(Boolean condition, String msg)` | 조건이 **true** |
| `isFalse` | `isFalse(Boolean condition, String msg)` | 조건이 **false** |
| `isNull` | `isNull(Object value, String msg)` | 값이 **null** |
| `isNotNull` | `isNotNull(Object value, String msg)` | 값이 **null 아님** |
| `isInstanceOfType` | `isInstanceOfType(Object instance, System.Type expectedType, String msg)` | 인스턴스가 지정 타입 **임** |
| `isNotInstanceOfType` | `isNotInstanceOfType(Object instance, System.Type notExpectedType, String msg)` | 인스턴스가 지정 타입 **아님** |
| `fail` | `fail(String msg)` | 무조건 fatal error로 실행 중단 (예외 미발생 시 강제 실패용) |

- `areEqual`/`areNotEqual`의 첫 인자는 각각 `expected`/`notExpected`, 둘째가 `actual` — **순서가 (기대값, 실제값)** 이다.
- `fail`은 인자 없는 `fail()` 오버로드도 있어, 예외를 기대하는 `try` 블록 끝에 놓아 "여기 도달하면 안 됨"을 표현한다.
- `msg`는 항상 마지막 파라미터이며 **선택적**(없는 오버로드 존재)이지만, 실무에선 실패 원인 추적을 위해 넣는 것이 모범 사례다(위 [Assert 모범 사례](#assert-모범-사례) 참조).

```apex
// PDF 발췌 — 대표 사용
String sub = 'abcde'.substring(2);
Assert.areEqual('cde', sub, 'Expected characters after first two'); // 성공
Assert.areNotEqual('xyz', sub);                                     // 성공

Account o = new Account();
Assert.isInstanceOfType(o, Account.class);        // 성공
Assert.isNotInstanceOfType(new Contact(), Account.class); // 성공

// 예외 기대 케이스
try {
    SomeClass.methodUnderTest();
    Assert.fail('DmlException Expected'); // 예외 없으면 여기서 강제 실패
} catch (DmlException ex) {
    // 예상 예외에 대한 단언
}
```

#### 구식 System.assertEquals / assert 와의 관계

`System.Assert` 클래스 이전에는 `System` 클래스의 아래 3개 메서드를 썼다. **여전히 동작하지만 공식 권고는 `System.Assert` 클래스로 교체하는 것**이다("The System.Assert class provides methods that handle all types of logical assertions and comparisons, which improve the clarity of your Apex code").

| 구식 (System 클래스) | 시그니처 | 대체 (System.Assert) |
|---|---|---|
| `System.assert` | `assert(Boolean condition, Object msg)` | `Assert.isTrue(condition, msg)` |
| `System.assertEquals` | `assertEquals(Object expected, Object actual, Object msg)` | `Assert.areEqual(expected, actual, msg)` |
| `System.assertNotEquals` | `assertNotEquals(Object expected, Object actual, Object msg)` | `Assert.areNotEqual(expected, actual, msg)` |

> 구식 메서드는 `msg`가 `Object` 타입(신형은 `String`)이라는 차이가 있으나, 동작·롤백·`try/catch` 불가 특성은 동일하다.

### System.Test 메서드 (전수)

`System.Test`(모든 메서드 **정적**)는 테스트 컨텍스트 제어·모킹·비동기 경계·시딩을 담당한다. 요청받은 핵심 메서드의 시그니처·용도는 다음과 같다.

| 메서드 | 시그니처 | 반환 | 용도 |
|---|---|---|---|
| `startTest` | `startTest()` | `void` | 테스트 본체 시작 지점 표시. 이 호출 이후 코드에 **새 governor limit 세트** 부여. 메서드당 1회만 호출 가능 |
| `stopTest` | `stopTest()` | `void` | 테스트 종료 지점. 이 시점에 `startTest` 이후 큐잉된 **모든 비동기 처리(@future·executeBatch·Queueable)가 동기 실행**됨. 이후 코드는 원래 limit로 복귀 |
| `isRunningTest` | `isRunningTest()` | `Boolean` | 현재 코드가 테스트 메서드에서 호출됐으면 `true`. 테스트 여부에 따라 분기할 때 |
| `setMock` | `setMock(Type interfaceType, Object instance)` | `void` | HTTP 클래스·WSDL 자동생성 코드의 callout에 대해 mock 응답 모드로 전환 (`HttpCalloutMock`/`WebServiceMock`) |
| `setFixedSearchResults` | `setFixedSearchResults(ID[] fixedSearchResults)` | `void` | 이후 모든 SOSL이 반환할 고정 결과 지정. 미지정 시 테스트의 SOSL은 항상 빈 결과. WHERE·LIMIT는 이 고정 목록에 적용됨 |
| `loadData` | `loadData(Schema.SObjectType sObjectToken, String resourceName)` | `List<sObject>` | 지정 sObject 타입에 대해 static resource `.csv`에서 테스트 레코드를 insert하고 삽입된 목록 반환 |
| `getStandardPricebookId` | `getStandardPricebookId()` | `Id` | 조직 표준 가격표 ID 반환 (SeeAllData 여부와 무관). 테스트에서 PricebookEntry 생성 시 필요 |
| `createStub` | `createStub(System.Type parentType, System.StubProvider stubProvider)` | `Object` | Apex stub API — `System.StubProvider` 구현과 함께 클래스의 스텁(모킹) 인스턴스 생성 |
| `newSendEmailQuickActionDefaults` | `newSendEmailQuickActionDefaults(ID contextId, ID replyToId)` | `QuickAction.SendEmailQuickActionDefaults` | `QuickAction.QuickActionDefaultsHandler` 구현 테스트용 인스턴스 생성 |
| `enableChangeDataCapture` | `enableChangeDataCapture()` | `void` | 지원되는 CDC 엔티티 전체에 대해 change event 알림을 생성. **DML 수행·`getEventBus().deliver()` 호출 전, 테스트 시작 시점에 호출** |
| `getEventBus` | `getEventBus()` | `EventBus.TestBroker` | 테스트 이벤트 버스 브로커 반환. `Test.getEventBus().deliver()`로 platform event·change event 메시지 전달 |

```apex
// PDF 발췌 — getEventBus 전달 패턴 (startTest/stopTest 블록 안에서)
Test.startTest();
    // 테스트 이벤트 생성 → EventBus.publish()로 발행
    Test.getEventBus().deliver(); // 이벤트 전달
    // 검증
Test.stopTest();
```

> `getEventBus().deliver()`는 `Test.startTest()`~`Test.stopTest()` 블록 안에 넣어야 한다. `enableChangeDataCapture()`는 DML보다 **먼저** 호출해야 change event가 캡처된다.

## SeeAllData — 조직 데이터 접근

### 기본 격리 (API 24.0+ = SeeAllData=false)

**API 버전 24.0 이상**으로 저장된 Apex 테스트는 기본적으로 **조직의 기존 데이터(표준 객체·커스텀 객체·커스텀 세팅 데이터)에 접근할 수 없다.** 테스트가 직접 생성한 데이터만 볼 수 있다(data silo). 단, 조직 관리·메타데이터 객체는 예외로 항상 접근 가능하다.

- 예외 객체 예: `User`, `Profile`, `Organization`, `CronTrigger`, `RecordType`, `ApexClass`, `ApexTrigger`, `ApexComponent`, `ApexPage`
- API 23.0 이하로 저장된 코드는 여전히 조직 전체 데이터에 접근하며, 이 버전에서는 `SeeAllData` 어노테이션 자체가 무효다.

`@isTest(SeeAllData=true)`를 클래스나 메서드에 붙이면 이 격리를 해제하고 조직 전체 데이터를 볼 수 있다. 단 **쿼리(읽기)에만 적용**되며, 테스트가 생성·수정·삭제한 레코드는 어노테이션과 무관하게 테스트 종료 시 전부 롤백된다.

### 왜 피해야 하는가 (공식 권고: data silo)

> 공식 문서 경고: *"By annotating your class with @isTest(SeeAllData=true), you allow test methods to access all org records. The best practice, however, is to run Apex tests with data silo using @isTest(SeeAllData=false)."*

| 위험 | 설명 |
|---|---|
| org 데이터 의존 | 테스트가 특정 레코드(예: `Name='Acme'`) 존재를 가정 → 그 데이터가 없는 조직에서 실패 |
| 배포 취약 | Sandbox↔Production 간 데이터가 다르므로 배포 시 테스트가 깨짐 (환경 이식성 상실) |
| `@TestSetup` 사용 불가 | 클래스/메서드가 SeeAllData=true면 test setup 메서드가 지원되지 않음 |
| 병렬 실행 불가 | `@isTest(SeeAllData=true)`와 `@isTest(IsParallel=true)`는 같은 메서드에 병용 불가 |
| 격리 붕괴 | 다른 테스트·실사용자가 만든 데이터가 쿼리 결과에 섞여 assert가 비결정적으로 변함 |

`@TestSetup`으로 테스트 데이터를 직접 만드는 방식이 나은 이유가 정확히 이것이다 — 어떤 조직에서든 동일한 기준 데이터로 결정적(deterministic)으로 실행되고, 클래스당 1회 생성으로 성능도 좋다.

### 클래스/메서드 레벨 오버라이드 규칙

| 클래스 어노테이션 | 메서드 어노테이션 | 그 메서드의 데이터 접근 |
|---|---|---|
| `SeeAllData=true` | (미지정) | 조직 전체 접근 |
| `SeeAllData=true` | `SeeAllData=false` | **false는 무시됨 — 여전히 전체 접근** (좁히기 불가) |
| (미지정 / `false`) | `SeeAllData=true` | 그 메서드만 전체 접근 (넓히기는 가능) |

```apex
// 공식 문서 발췌 — 메서드 레벨 SeeAllData
@IsTest
private class ClassWithDifferentDataAccess {
    // Test method that has access to all data.
    @IsTest(SeeAllData=true)
    static void testWithAllDataAccess() {
        // Can query all data in the organization.
    }
    // Test method that has access to only the data it creates
    // and organization setup and metadata objects.
    @IsTest
    static void testWithOwnDataAccess() {
        // This method can still access the User object.
        User u = [SELECT UserName,Email FROM User LIMIT 1];
        // Can access the test account that is created here.
        Account a = new Account(Name='Test Account');
        insert a;
    }
}
```

### 불가피한 케이스 — 언제 SeeAllData=true를 쓰나

가능하면 항상 테스트 데이터를 직접 생성하되, 아래처럼 테스트 컨텍스트에서 데이터를 만들 수 없는 경우에만 제한적으로 사용한다.

- **ConnectApi**: 다수 메서드가 SeeAllData=true 없이는 테스트에서 직접 호출 불가 → 어노테이션 대신 **래퍼 클래스 + [[StubProvider]]로 우회**하는 것이 권장 패턴
- **기존 커스텀 세팅 데이터**: 커스텀 세팅 데이터는 테스트 격리에서 '데이터'로 취급되어 SeeAllData=true 없이는 기존 값이 안 보임 — 단, 베스트 프랙티스는 필요한 커스텀 세팅을 테스트 셋업에서 직접 생성하는 것
- **테스트에서 생성 불가한 레코드**: 일부 표준 객체는 생성 자체가 불가, 커밋 후에만 생기는 레코드(Chatter `FeedTrackedChange`, 필드 히스토리 등)는 테스트에서 만들 수 없음
- 참고: **리포트 실행**은 SeeAllData 값과 무관하게 항상 조직의 기존 데이터를 포함한다 (어노테이션이 무시됨)
