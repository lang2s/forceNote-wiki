# 테스트 전략

> Apex 테스트의 구조화 원칙. 단위 테스트 격리, 외부 의존성 모킹, 체계적인 검증.

---

## 개념

### 왜 Apex 테스트 전략이 중요한가

Salesforce는 배포 시 **코드 커버리지 75% 이상**을 강제한다. 그러나 커버리지 달성만을 목표로 한 테스트는 실제 버그를 잡지 못한다. 잘 설계된 테스트 전략은 다음을 보장한다.

- **회귀 방지**: 새 기능 추가나 리팩터링 시 기존 동작이 깨지지 않음을 빠르게 확인
- **배포 안전성**: Sandbox → Production 배포 시 릴리즈 유효성 검증
- **설계 피드백**: 테스트하기 어려운 코드는 대부분 설계 문제(강결합, 정적 의존성)가 있다는 신호

### Apex 테스트의 핵심 제약

Apex 테스트 환경에는 일반 코드와 다른 제약이 있다.

- **외부 Callout 불가**: 테스트에서 실제 HTTP 요청을 보내면 예외 발생 → `HttpCalloutMock` 필수
- **SOSL 결과 없음**: Full-Text Search 인덱스가 갱신되지 않으므로 항상 빈 결과 → `Test.setFixedSearchResults()` 필수
- **Governor Limit 별도 집계**: 테스트 데이터 생성(`@TestSetup`, `insert`) 과정이 Limit을 소모하므로, 실제 테스트 대상 코드의 Limit과 분리하기 위해 `Test.startTest()` / `Test.stopTest()`로 경계를 명확히 해야 한다
- **비동기 실행 동기화**: `@future`, `Queueable`, `Batch` 작업은 `Test.stopTest()` 호출 시점에 동기적으로 실행된다

### 테스트 격리 원칙

좋은 Apex 테스트는 **외부 상태에 의존하지 않는다.** 테스트 데이터는 테스트 내부에서 생성하고, 외부 시스템(HTTP, 다른 Apex 클래스의 부수 효과)은 모킹한다. 하나의 테스트 메서드가 다른 테스트의 성공에 영향을 주어서는 안 된다.

## 테스트 클래스 기본 구조

```apex
@isTest
private class BookApiServiceTest {

    // 공통 데이터 초기화
    @TestSetup
    static void makeData() {
        Account acct = new Account(Name = 'Test Account');
        insert acct;
    }

    // 정상 케이스
    @isTest
    static void searchBooks_returnsResults_withValidKeyword() {
        Test.setMock(HttpCalloutMock.class, new SuccessCalloutMock());

        Test.startTest();
        List<BookModel> result = new BookApiService().searchBooks('salesforce');
        Test.stopTest();

        Assert.isFalse(result.isEmpty(), '결과가 있어야 함');
        Assert.areEqual('Salesforce Book', result[0].title);
    }

    // 실패 케이스
    @isTest
    static void searchBooks_throwsException_on404() {
        Test.setMock(HttpCalloutMock.class, new ErrorCalloutMock(404, '{}'));

        Test.startTest();
        try {
            new BookApiService().searchBooks('unknown');
            Assert.fail('예외가 발생해야 함');
        } catch (BookApiService.BookNotFoundException e) {
            Assert.isNotNull(e.getMessage());
        }
        Test.stopTest();
    }
}
```

## 의존성별 모킹 전략

| 의존성 유형 | 모킹 방법 |
|---|---|
| HTTP 외부 호출 | `HttpCalloutMock` + `Test.setMock()` |
| Apex 클래스 메서드 | `StubProvider` + `Test.createStub()` |
| static 메서드 | `@testVisible` Boolean/Exception 회로차단기 |
| Salesforce 시스템 클래스 | 래퍼 클래스 → StubProvider |
| ConnectApi | 래퍼 클래스 → StubProvider |
| Quiddity | `QuiddityGuard.testQuiddityOverride` |

## Assert 모범 사례

```apex
// ✅ 명시적 메시지 포함
Assert.areEqual(expected, actual, '설명 메시지');
Assert.isTrue(condition, '이 조건이 true여야 하는 이유');

// ✅ 예외 테스트는 fail() 포함
try {
    methodThatShouldThrow();
    Assert.fail('예외가 발생해야 함'); // 예외 없으면 테스트 실패
} catch (ExpectedException e) {
    Assert.isNotNull(e.getMessage());
}

// ❌ 피해야 할 패턴
System.assertEquals(expected, actual); // 구형 API
Assert.isTrue(list.size() > 0);        // isEmpty() 사용 권장
Assert.areEqual(1, list.size());       // 더 명확
```

## Test.startTest / Test.stopTest 사용

```apex
// Governor limit 초기화 — 외부 callout 포함 시 필수
Test.startTest();
    List<BookModel> result = service.searchBooks('sf'); // callout 실행
Test.stopTest();
// stopTest()에서 @future, Queueable, Batch가 동기 실행됨
```

> [!tip] startTest/stopTest 역할
> - Governor limit을 초기화하여 테스트 자체의 DML/쿼리를 테스트 대상에서 분리
> - `stopTest()` 호출 시 비동기 작업(@future, Queueable, Batch)이 강제 실행됨

## @TestSetup vs 각 테스트 내 데이터 생성

| | @TestSetup | 각 테스트 내 생성 |
|---|---|---|
| 실행 시점 | 테스트 클래스 실행 전 1회 | 각 테스트 메서드마다 |
| 격리 | 각 테스트는 독립된 사본 | 완전 격리 |
| 성능 | 빠름 (공유 데이터) | 느림 |
| 권장 | 공통 기준 데이터 | 테스트 고유 데이터 |

## SeeAllData — 조직 데이터 접근

### 기본 격리 (API 24.0+ = SeeAllData=false)

**API 버전 24.0 이상**으로 저장된 Apex 테스트는 기본적으로 **조직의 기존 데이터(표준 객체·커스텀 객체·커스텀 세팅 데이터)에 접근할 수 없다.** 테스트가 직접 생성한 데이터만 볼 수 있다(data silo). 단, 조직 관리·메타데이터 객체는 예외로 항상 접근 가능하다.

- 예외 객체 예: `User`, `Profile`, `Organization`, `CronTrigger`, `RecordType`, `ApexClass`, `ApexTrigger`, `ApexComponent`, `ApexPage`
- API 23.0 이하로 저장된 코드는 여전히 조직 전체 데이터에 접근하며, 이 버전에서는 `SeeAllData` 어노테이션 자체가 무효다.

`@isTest(SeeAllData=true)`를 클래스나 메서드에 붙이면 이 격리를 해제하고 조직 전체 데이터를 볼 수 있다. 단 **쿼리(읽기)에만 적용**되며, 테스트가 생성·수정·삭제한 레코드는 어노테이션과 무관하게 테스트 종료 시 전부 롤백된다.

### 왜 피해야 하는가 (공식 권고: data silo)

> 공식 문서 경고: *"By annotating your class with @isTest(SeeAllData=true), you allow test methods to access all org records. The best practice, however, is to run Apex tests with data silo using @isTest(SeeAllData=false)."*

| 위험 | 설명 |
|---|---|
| org 데이터 의존 | 테스트가 특정 레코드(예: `Name='Acme'`) 존재를 가정 → 그 데이터가 없는 조직에서 실패 |
| 배포 취약 | Sandbox↔Production 간 데이터가 다르므로 배포 시 테스트가 깨짐 (환경 이식성 상실) |
| `@TestSetup` 사용 불가 | 클래스/메서드가 SeeAllData=true면 test setup 메서드가 지원되지 않음 |
| 병렬 실행 불가 | `@isTest(SeeAllData=true)`와 `@isTest(IsParallel=true)`는 같은 메서드에 병용 불가 |
| 격리 붕괴 | 다른 테스트·실사용자가 만든 데이터가 쿼리 결과에 섞여 assert가 비결정적으로 변함 |

`@TestSetup`으로 테스트 데이터를 직접 만드는 방식이 나은 이유가 정확히 이것이다 — 어떤 조직에서든 동일한 기준 데이터로 결정적(deterministic)으로 실행되고, 클래스당 1회 생성으로 성능도 좋다.

### 클래스/메서드 레벨 오버라이드 규칙

| 클래스 어노테이션 | 메서드 어노테이션 | 그 메서드의 데이터 접근 |
|---|---|---|
| `SeeAllData=true` | (미지정) | 조직 전체 접근 |
| `SeeAllData=true` | `SeeAllData=false` | **false는 무시됨 — 여전히 전체 접근** (좁히기 불가) |
| (미지정 / `false`) | `SeeAllData=true` | 그 메서드만 전체 접근 (넓히기는 가능) |

```apex
// 공식 문서 발췌 — 메서드 레벨 SeeAllData
@IsTest
private class ClassWithDifferentDataAccess {
    // Test method that has access to all data.
    @IsTest(SeeAllData=true)
    static void testWithAllDataAccess() {
        // Can query all data in the organization.
    }
    // Test method that has access to only the data it creates
    // and organization setup and metadata objects.
    @IsTest
    static void testWithOwnDataAccess() {
        // This method can still access the User object.
        User u = [SELECT UserName,Email FROM User LIMIT 1];
        // Can access the test account that is created here.
        Account a = new Account(Name='Test Account');
        insert a;
    }
}
```

### 불가피한 케이스 — 언제 SeeAllData=true를 쓰나

가능하면 항상 테스트 데이터를 직접 생성하되, 아래처럼 테스트 컨텍스트에서 데이터를 만들 수 없는 경우에만 제한적으로 사용한다.

- **ConnectApi**: 다수 메서드가 SeeAllData=true 없이는 테스트에서 직접 호출 불가 → 어노테이션 대신 **래퍼 클래스 + [[StubProvider]]로 우회**하는 것이 권장 패턴
- **기존 커스텀 세팅 데이터**: 커스텀 세팅 데이터는 테스트 격리에서 '데이터'로 취급되어 SeeAllData=true 없이는 기존 값이 안 보임 — 단, 베스트 프랙티스는 필요한 커스텀 세팅을 테스트 셋업에서 직접 생성하는 것
- **테스트에서 생성 불가한 레코드**: 일부 표준 객체는 생성 자체가 불가, 커밋 후에만 생기는 레코드(Chatter `FeedTrackedChange`, 필드 히스토리 등)는 테스트에서 만들 수 없음
- 참고: **리포트 실행**은 SeeAllData 값과 무관하게 항상 조직의 기존 데이터를 포함한다 (어노테이션이 무시됨)
