# 코드 커버리지 규칙

> Apex를 프로덕션에 배포하거나 패키지로 업로드하려면 조직 전체 75% 커버리지 + 각 트리거 최소 커버리지가 필요하다. 커버리지 계산·확인 방법·"커버리지 ≠ 품질" 원칙을 정리한다.

---

## 개념 — 배포·패키지 게이트

Apex 테스트 프레임워크는 테스트를 실행할 때마다 클래스·트리거의 **코드 커버리지**(테스트로 실행된 executable line 수)를 계산한다. 코드를 배포하거나 AppExchange 패키지로 만들기 전 아래 조건이 모두 참이어야 한다.

- **단위 테스트가 Apex 코드의 최소 75%를 커버**해야 하며, 그 테스트가 전부 성공해야 한다.
- **모든 트리거는 어느 정도의 테스트 커버리지가 있어야 한다** (트리거는 "some test coverage" 필수 — 0%면 배포 불가).
- **모든 클래스·트리거가 정상 컴파일**되어야 한다.

| 대상 | 커버리지 요구 | 근거 |
|---|---|---|
| 프로덕션 배포 | 조직 전체(overall) ≥ 75% + 모든 테스트 통과 | Testing Apex → Why Test Apex? |
| 패키지(1GP/2GP) 업로드 | 누적(cumulative) ≥ 75%, 각 트리거 some coverage | Adding Apex Code to a AppExchange App |
| 개별 클래스 | 조직 요구는 아님(전체 평균으로 판정)이나, 배포 실패 시 <75% 클래스를 찾아 보강 | Recommended Process |

> [!note] 프로덕션 배포 시 조직 네임스페이스의 모든 단위 테스트가 기본 실행된다. 배포 중 테스트는 항상 **동기·직렬(synchronous·serially)** 로 실행된다(UI에서 시작한 테스트는 비동기·병렬).

패키지 관련 참고:
- `@isTest(OnInstall=true)` 주석이 붙은 테스트는 패키지가 설치자 조직에 설치될 때 실행된다. 이 subset이 통과해야 설치가 성공한다.
- 관리형 패키지에서 설치된 Apex는 **조직 레벨 커버리지 요구에서 제외**된다. 패키지 설치는 커버리지 요구로 차단되지 않는다.

## 커버리지 계산 — 무엇이 포함/제외되는가

커버리지 = **조직 전체의 총 코드 라인 수** 기준으로 계산된다. 라인을 추가/삭제하면 퍼센트가 변한다.

> 예: 조직에 테스트로 커버된 50라인이 있어 100%였는데, 테스트 없는 50라인짜리 트리거를 추가하면 총 라인이 100으로 늘고 커버된 건 50뿐이라 **100% → 50%로 하락**한다.

**커버리지 계산에서 제외되는 것:**

| 제외 대상 | 설명 |
|---|---|
| `System.debug` 호출 | 커버리지에 카운트되지 않음 |
| 테스트 메서드·테스트 클래스 | `@isTest` 코드 자체는 커버리지 대상 아님 |
| 컴파일러가 최적화한 라인 | 여러 줄로 쓴 상수 표현식이 하나로 접히면 접힌 라인은 무시됨 (예: `'Hello' + ' World!'` 두 번째 줄) |
| test setup 메서드가 호출한 타 클래스의 non-test 메서드 | 해당 non-test 메서드에 대한 커버리지가 계산되지 않음 |

```apex
// 구조 예시 — 실제 동작 코드 아님. 컴파일러 최적화로 두 번째 줄이 커버리지에서 무시되는 사례
String s = 'Hello'
         + ' World!';   // 내부적으로 'Hello World!' 한 상수로 최적화 → 이 줄은 무시
```

### 전체(overall) vs 클래스별(aggregate)

- **전체 커버리지** = 조직 전체 총 라인 대비 커버된 라인. 배포·패키지 게이트가 판정하는 값.
- **클래스별 커버리지**(`ApexCodeCoverageAggregate`) = 특정 클래스를 테스트한 **모든** 테스트 메서드의 합산 커버리지.
- **테스트 메서드별 커버리지**(`ApexCodeCoverage`) = 개별 테스트 메서드가 커버/미커버한 라인. 한 클래스에 여러 행(테스트 메서드마다 1개)이 생김.

> `ApexCodeCoverage`의 `NumLinesUncovered`는 aggregate 값과 다르다. 각각 **하나의 테스트 메서드** 기준이기 때문. 예: `testTaskPriority()`가 10라인 중 7라인 커버 → 미커버 3라인. aggregate는 모든 메서드 합산이라 미커버가 2라인으로 줄 수 있다.

## 확인 방법 (절차)

### 1. Setup / Apex Classes · Application Test Execution
- Setup → **Application Test Execution** 에서 테스트를 선택·실행하면 실행 후 커버리지 상세를 볼 수 있다.
- 관리형 패키지 클래스는 Apex Classes 페이지에서 **Compile all classes**를 먼저 눌러야 목록에 나온다.
- 실행 옵션에서 **Skip Code Coverage**를 선택하면 테스트 실행 중 커버리지 수집을 생략한다(속도 목적).

### 2. Developer Console
- **Tests 탭**의 code coverage pane에서 각 Apex 클래스별 + 조직 전체(Overall Code Coverage) 커버리지를 본다.
- 커버리지 라인을 더블클릭하면 트리거/클래스에서 커버된 라인 비율(예: 100%)을 확인할 수 있다.

### 3. Tooling API (SOQL) — `ApexCodeCoverageAggregate` / `ApexCodeCoverage`
커버리지는 두 Tooling API 오브젝트에 저장된다. Developer Console Query Editor에서 **Use Tooling API**를 체크하고 조회하거나 Tooling API로 쿼리한다.

```sql
-- 클래스 합산 커버리지 (모든 테스트 클래스가 기여한 결과)
SELECT ApexClassOrTrigger.Name, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverageAggregate
WHERE ApexClassOrTrigger.Name = 'TaskUtil'

-- 어떤 테스트 메서드가 커버했는지 (테스트 클래스·메서드별)
SELECT ApexTestClass.Name, TestMethodName, NumLinesCovered, NumLinesUncovered
FROM ApexCodeCoverage
WHERE ApexClassOrTrigger.Name = 'TaskUtil'
```

> [!warning] 단일 배포에 Apex 클래스가 **2,000개 초과**면, 배포가 실패·롤백되어도 해당 클래스의 `ApexCodeCoverage` 오브젝트는 삭제된다. `ApexCodeCoverageAggregate`는 영향받지 않는다.

오브젝트 필드 상세·쿼리 예는 [[Tooling API 객체 — Apex 코드·테스트·커버리지]] 참조.

## 커버리지 새로고침 · 샌드박스↔프로덕션 차이

- **커버리지 숫자는 자동 갱신되지 않는다.** Apex 코드를 수정해도 테스트를 다시 돌리기 전까지 커버리지가 refresh되지 않는다 → 조직이 갱신됐다면 재실행해야 추정치가 정확하다.
- 조직 전체 커버리지 %에는 **패키지 관련 테스트 커버리지가 포함되지 않는다**(예외: 패키지 테스트가 내 트리거를 발동시킬 때).
- **샌드박스와 프로덕션 커버리지가 다른 이유**: 두 환경의 데이터·메타데이터가 달라서. 흔한 원인 —
  - Test Failures — 비교 전 배포 대상 코드의 테스트가 전부 통과하는지 먼저 확인
  - Data Dependencies — `@IsTest(SeeAllData=true)` 의존 시 조직 데이터에 따라 결과가 달라짐 → 테스트가 직접 데이터를 만들도록 수정
  - Metadata Dependencies — 프로파일 등 메타데이터 차이가 다른 코드 경로를 타게 함
  - Managed/Unlocked Package Tests — UI 실행 vs `RunAllTestsInOrg` 배포 실행에서 패키지 코드 포함 여부가 다름
- **100% 커버리지 신규 컴포넌트라도** 신·구 코드 평균이 75% 미만이면 배포가 실패한다. 기존 테스트를 보강해 전체를 75% 위로 올려야 한다.
- 권장 프로세스: **Full Sandbox**를 스테이징으로 사용(데이터·메타데이터 근접) → 테스트 데이터 사용 → 실패 시 <75% 클래스를 찾아 테스트 추가.

## 베스트프랙티스 — 커버리지 ≠ 품질

> 75%만 커버하면 되지만, **커버된 코드의 퍼센트에 집착하지 말라.** 대신 애플리케이션의 모든 use case(positive·negative, bulk·single record)를 커버하라. 그러면 자연히 75% 이상이 커버된다.

- **의미 있는 assert가 핵심이다.** 라인만 실행하고 검증(`Assert.areEqual` 등)이 없으면 커버리지는 올라가도 회귀를 잡지 못한다. 커버리지는 "실행됐다"만 말할 뿐 "올바르다"는 보장하지 않는다.
- 단일 레코드뿐 아니라 **1~200 레코드 bulk** 케이스를 테스트한다.
- 조직 데이터 의존 대신 **테스트 데이터를 생성**한다 ([[Test Data Factory 패턴]]).
- 배포 실패 시 목표는 "겨우 75%"가 아니라 가능한 한 높게(이상적으로 100%) 올리고 재시도하는 것.

```apex
// 구조 예시 — 실제 동작 코드 아님. 커버리지는 오르지만 검증이 없어 품질을 보장하지 못하는 안티패턴
@isTest
static void badTest() {
    Account a = new Account(Name = 'Test');
    insert a;
    MyService.process(a.Id);   // 라인은 실행 → 커버리지 ↑
    // ❌ assert 없음 → 결과가 틀려도 통과. 커버리지 ≠ 정확성
}
```
