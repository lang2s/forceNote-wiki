# WebServiceMock — SOAP(wsdl2apex) 콜아웃 모킹

> WSDL에서 자동 생성된 Apex 스텁 클래스가 호출하는 `WebServiceCallout.invoke`를 테스트에서 가짜 응답으로 대체하는 인터페이스. `Test.setMock(WebServiceMock.class, new MyMock())`으로 등록한다.

---

## 언제/왜 쓰나 — "do not support Web service callouts" 에러

WSDL2Apex로 생성한 스텁 클래스의 메서드는 내부적으로 `WebServiceCallout.invoke`를 호출해 외부 서비스로 콜아웃한다. **기본적으로 테스트 메서드는 web service 콜아웃을 지원하지 않으며, 콜아웃을 수행하는 테스트는 실패한다.** 런타임에서는 다음과 같은 예외를 만난다.

```
System.TypeException: Methods defined as testMethod do not support Web service callouts
```

- 스텁 클래스를 배포·패키징하려면 생성된 클래스 메서드를 포함해 **75% 코드 커버리지**가 필요한데, 콜아웃 때문에 테스트가 실패하면 커버리지를 못 채운다.
- 해결책이 바로 **`WebServiceMock` 인터페이스 + `Test.setMock`** 이다. 이 둘을 쓰면 콜아웃이 실제로 나가지 않고 테스트 메서드가 지정한 가짜 응답을 돌려받는다.

> HTTP/REST 콜아웃(`Http.send`)의 실패는 `WebServiceMock`이 아니라 [[HttpCalloutMock]]으로 해결한다. 아래 비교표 참조.

---

## doInvoke() — 전체 시그니처 (소스 그대로)

`WebServiceMock` 인터페이스는 `doInvoke` 메서드 하나를 가진다. Apex 런타임이 `Test.setMock` 등록 후 web service 콜아웃이 일어날 때 이 메서드를 호출해 가짜 응답을 만든다.

```apex
global class YourWebServiceMockImpl implements WebServiceMock {
    global void doInvoke(
            Object stub,
            Object request,
            Map<String, Object> response,
            String endpoint,
            String soapAction,
            String requestName,
            String responseNS,
            String responseName,
            String responseType) {
        // Create response element from the autogenerated class.
        // Populate response element.
        // Add response element to the response parameter, as follows:
        response.put('response_x', responseElement);
    }
}
```

Apex Reference Guide의 공식 시그니처(파라미터명은 레퍼런스 표기):

```apex
public Void doInvoke(Object stub, Object soapRequest, Map<String,Object> responseMap,
    String endpoint, String soapAction, String requestName, String responseNamespace,
    String responseName, String responseType)
```

### 파라미터 9개 (전수)

| # | 파라미터 (Dev Guide 예제명 / Ref Guide명) | 타입 | 설명 |
|---|---|---|---|
| 1 | `stub` | `Object` | WSDL에서 자동 생성된 스텁 클래스의 인스턴스 |
| 2 | `request` / `soapRequest` | `Object` | 호출되는 SOAP 요청. 자동 생성 스텁 클래스의 타입 인스턴스 |
| 3 | `response` / `responseMap` | `Map<String, Object>` | 응답을 담는 key/value 맵. key는 응답 식별자, value는 자동 생성 스텁 타입의 응답 객체. **구현 시 원하는 응답을 이 맵에 넣는다** |
| 4 | `endpoint` | `String` | 요청의 엔드포인트 URL |
| 5 | `soapAction` | `String` | 요청된 SOAP 오퍼레이션 |
| 6 | `requestName` | `String` | 요청된 SOAP 오퍼레이션 이름 |
| 7 | `responseNS` / `responseNamespace` | `String` | 응답 네임스페이스 |
| 8 | `responseName` | `String` | WSDL에 정의된 응답 엘리먼트 이름 |
| 9 | `responseType` | `String` | 자동 생성 클래스에 정의된 응답 클래스 |

- 반환 타입: `Void`
- 네임스페이스: `System`
- `WebServiceMock` 구현 클래스는 **global 또는 public** 둘 다 가능하다.
- 이 클래스는 테스트 컨텍스트에서만 쓰이므로 `@isTest`로 애노테이트할 수 있고, 그러면 org의 **6 MB 코드 사이즈 한도**에서 제외된다.

## 등록 방법 — Test.setMock

`doInvoke`에서 가짜 응답 값을 지정한 뒤, 테스트 메서드에서 `Test.setMock`을 호출해 런타임이 그 응답을 보내도록 지시한다. **첫 번째 인자로 `WebServiceMock.class`, 두 번째 인자로 구현 인스턴스**를 넘긴다.

```apex
Test.setMock(WebServiceMock.class, new YourWebServiceMockImpl());
```

이 시점 이후 테스트 컨텍스트에서 web service 콜아웃이 일어나면 실제 콜아웃은 나가지 않고 `doInvoke`에 지정한 mock 응답을 받는다.

> Note: 콜아웃 코드가 managed package 안에 있으면, **같은 네임스페이스의 같은 패키지 내 테스트 메서드에서** `Test.setMock`을 호출해야 mock이 적용된다.

## 완전한 예제 — mock 클래스 + 대상 + 테스트

이 예제는 `docSample`이라는 클래스로 WSDL을 import해 생성했다고 가정한다(Generated WSDL2Apex Code 기준).

### 1) WebServiceMock 구현 (가짜 응답)

```apex
@isTest
global class WebServiceMockImpl implements WebServiceMock {
    global void doInvoke(
            Object stub,
            Object request,
            Map<String, Object> response,
            String endpoint,
            String soapAction,
            String requestName,
            String responseNS,
            String responseName,
            String responseType) {
        docSample.EchoStringResponse_element respElement =
            new docSample.EchoStringResponse_element();
        respElement.EchoStringResult = 'Mock response';
        response.put('response_x', respElement);
    }
}
```

### 2) 콜아웃을 수행하는 대상 클래스

```apex
public class WebSvcCallout {
    public static String callEchoString(String input) {
        docSample.DocSamplePort sample = new docSample.DocSamplePort();
        sample.endpoint_x = 'https://example.com/example/test';
        // This invokes the EchoString method in the generated class
        String echo = sample.EchoString(input);
        return echo;
    }
}
```

### 3) 테스트 메서드

```apex
@isTest
private class WebSvcCalloutTest {
    @isTest static void testEchoString() {
        // This causes a fake response to be generated
        Test.setMock(WebServiceMock.class, new WebServiceMockImpl());
        // Call the method that invokes a callout
        String output = WebSvcCallout.callEchoString('Hello World!');
        // Verify that a fake result is returned
        System.assertEquals('Mock response', output);
    }
}
```

## DML·비동기와 함께 쓸 때 — startTest 전에 setMock

기본적으로 같은 트랜잭션에서 **DML 이후에는 콜아웃이 허용되지 않는다**(uncommitted work가 콜아웃을 막음). 테스트에서 DML로 테스트 데이터를 넣은 뒤 콜아웃하려면 콜아웃 부분을 `Test.startTest`/`Test.stopTest`로 감싼다.

- **`Test.startTest` 문은 `Test.setMock` 문보다 먼저 와야 한다.**
- DML 호출은 `Test.startTest`/`Test.stopTest` 블록 **밖**에 있어야 한다.
- mock 콜아웃 **이후**의 DML은 허용되며 별도 변경이 필요 없다.

```apex
@isTest
private class WebSvcCalloutTest {
    @isTest static void testEchoString() {
        // 테스트 데이터 DML — startTest 밖
        Account testAcct = new Account(Name = 'Test Account');
        insert testAcct;

        Test.startTest();                                        // setMock 앞
        Test.setMock(WebServiceMock.class, new WebServiceMockImpl());
        String output = WebSvcCallout.callEchoString('Hello World!');
        System.assertEquals('Mock response', output);
        Test.stopTest();
    }
}
```

- 비동기 Apex(future·batch·scheduled)도 uncommitted work를 남기므로 같은 규칙이 적용된다. 보통 비동기 호출을 `Test.startTest`/`Test.stopTest`로 감싸 `stopTest` 이후 실행되게 하면 mock 콜아웃을 문제없이 수행할 수 있다.

## HttpCalloutMock(HTTP/REST) vs WebServiceMock(SOAP)

| 기준 | HttpCalloutMock | WebServiceMock |
|---|---|---|
| 대상 콜아웃 | `Http.send(HttpRequest)` — REST/HTTP | WSDL2Apex 스텁의 `WebServiceCallout.invoke` — SOAP |
| 구현 메서드 | `HttpResponse respond(HttpRequest req)` | `void doInvoke(stub, request, response, endpoint, soapAction, requestName, responseNS, responseName, responseType)` |
| 응답 전달 방식 | `HttpResponse` 객체를 **return** | `response` Map에 자동 생성 응답 엘리먼트를 **put** |
| 등록 | `Test.setMock(HttpCalloutMock.class, mock)` | `Test.setMock(WebServiceMock.class, mock)` |
| 네임스페이스 | `System` | `System` |
| 미사용 시 에러 | `Methods defined as testMethod do not support Web service callouts` | `Methods defined as testMethod do not support Web service callouts` |
| 응답 소스 | 임의 JSON/XML 문자열 자유 구성 | 자동 생성 스텁 타입 인스턴스로 구성 |

- 공통: 둘 다 `Test.setMock`으로 등록하고, DML/비동기와 섞을 땐 `Test.startTest` 앞(또는 감싼 블록 안 setMock 앞)에 등록해야 한다.

> [!warning] "목 미설정 에러"와 "uncommitted work 에러"를 혼동하지 말 것
> 테스트에서 **목을 설정하지 않고** 콜아웃하면 HTTP·SOAP 모두 `System.TypeException: Methods defined as testMethod do not support Web service callouts`가 난다 — 이것이 목 부재(mock-absence) 에러다.
> 반면 **"You have uncommitted work pending..."**은 목 유무와 무관한 별개의 런타임 에러로, 같은 트랜잭션에서 **DML을 커밋한 뒤(=uncommitted work가 있는 상태에서) 콜아웃**을 하면 발생한다(테스트 밖에서도 남). 이 경우 콜아웃을 `Test.startTest`/`Test.stopTest`로 감싸거나 DML 전에 수행한다.
> 근거: [Testing HTTP Callouts — Apex Developer Guide (developer.salesforce.com)](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_testing_http_callouts.htm).
